# EmbyOne

> **一个插件化的 Emby / Jellyfin 媒体服务运营系统。**
> 把现有生态里需要部署五六套工具才能完成的事，收进一个内核。

## 这是什么

自己搭 Emby 服务的人（下称"站主"），现在的部署长这样：

| 要解决的问题 | 现在用什么 |
|---|---|
| 片子从哪来 | MoviePilot |
| 谁能用、能用多久 | ember / Twilight |
| 用户怎么看进度 | emby-pulse |
| 卡不卡、走哪条线 | Meridian |
| 怎么自动保号 | emby-keeper |
| 用户看什么网页 | 各家自建门户 |

**这六类工具，没有任何一个跨过两类的边界。**

后果很具体：装六个程序、配六套账号、在 A 里封了人 B 不知道、改一个设置要改六个地方、想开第二个站就得整套重来。

EmbyOne 要做的是**垂直整合这六层**——不是做一个更好的单点，而是做一个内核加四类插件。

## 核心设计

### 三条公理

1. **人是核心，资源是能力。** 现有工具分成"管资源的"和"管人的"两派。EmbyOne 把用户当作一等公民，把"获取资源"当作可插拔的能力。
2. **内核只做装配，业务全在插件。** 内核里不出现 "Emby"、不出现 "积分"。它只认识三样东西：契约、注册表、事件。
3. **复杂度必须分期支付。** 功能最全的竞品，光插件系统就写了 7159 行。我们用四级插件模型把它摊开。

### 四级插件

| 级别 | 形态 | 上手 | 能干什么 |
|---|---|---|---|
| **L0** | 一个 YAML | 5 分钟 | 配置项、模板化事件响应、路由转发 |
| **L1** | YAML + 脚本 | 30 分钟 | L0 + 钩子里写逻辑 |
| **L2** | Go 源码 | 半天 | 全部能力 + 自带数据表 |
| **L3** | 任意语言 + RPC | 半天 | 全部能力，进程隔离 |

**九成的扩展需求只需要填一个配置文件。** 这就是本项目相对竞品的核心差异——竞品要么没有插件机制，要么只有"写一个完整的类"这一条路。

### 分层

```
L4  表现层    Web / API / Bot / SSE        ← 全部由插件注册
L3  内核      契约 + 注册表 + 事件总线 + 装配器   ← 零业务名词
L2  内置插件  identity media request billing ops insight notify bot
L1  提供者    emby jellyfin moviepilot qbittorrent telegram 115 stripe
L0  存储      SQLite（默认） / PostgreSQL
```

## 要解决的十个问题

竞品分析（读源码得出，结论带 `文件:行号`）发现的共同短板：

| # | 问题 | 证据 |
|---|---|---|
| 1 | 没有统一用户状态机 | 两个成熟项目分别用「4 个布尔值」和「整数 + 标记」拼状态，且都缺"注册后待审批"这一档 |
| 2 | 卖不出差价 | 有项目完全没有按等级控制媒体库的能力，只有一份全局硬编码黑名单 |
| 3 | 求片与入库零闭环 | 实测六个项目，**零个**做到"求片→下载→入库→自动通知" |
| 4 | 卡密残缺 | 三家全缺批次/有效期/作废；有项目用「字符串里有没有 Renew」判断类型 |
| 5 | 积分无账本 | 有项目实测经济系统净通胀，改价还要改代码 |
| 6 | 探活是一次性快照 | 延迟只存在于手点测速那一瞬间，不落库不参与调度 |
| 7 | 失败被吞 | 数据取不到时静默返回空，故障表现为"暂无数据" |
| 8 | 只能单机跑 | 三个项目全部假设单实例，多开就会重复扣费发码 |
| 9 | 邀请无关系树 | 有邀请配置，但没有"谁拉的谁"这个字段 |
| 10 | 无法扩展 | 13 个项目里只有 1 个有插件机制 |

完整分析：[分析/需求全景](分析/需求全景.md)

### 以及一个没人占据的位置

- **站主的工具**精通账号运营，但风控只做到"数一下开了几个会话"
- **白嫖者的工具**精通伪造播放行为，但完全不关心运营

而且——其中一方的工具是**专门逆向另一方的后台协议**写出来的。卖号侧与抢号侧已成攻防对偶，接触点却是几行写死的正则。

站在中间的人握着最厉害的东西：**行为基线**。站主知道正常人怎么看片，所以一眼能认出谁是机器。

**目前没有任何系统同时站在两边。**
