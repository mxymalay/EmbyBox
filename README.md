# EmbyOne

> **一个插件化的 Emby / Jellyfin 媒体服务运营系统。**
> 把现有生态里需要部署五六套工具才能完成的事，收进一个内核。
>
> **开源 · 全程 AI 协作开发（vibecoding）· 核心永久免费**

## 我们要做什么

自己搭 Emby 服务的人（下称"站主"），现在的部署长这样：

| 要解决的问题 | 现在用什么 |
|---|---|
| 片子从哪来 | MoviePilot |
| 谁能用、能用多久 | ember / Twilight |
| 用户怎么看进度 | emby-pulse |
| 卡不卡、走哪条线 | Meridian |
| 怎么自动保号 | emby-keeper |
| 用户看什么网页 | 各家自建门户 |

**这六类工具，没有任何一个跨过两类的边界。**

后果很具体：装六个程序、配六套账号、在 A 里封了人 B 不知道、改一个设置要改六个地方、想开第二个站就得整套重来。

EmbyOne 要做的是**垂直整合这六层**——不是做一个更好的单点，而是做一个内核加四类插件。

## 这是一个开源项目

**核心功能永久免费，不限用户数、不限站点数、不设功能阉割、不联网验证。**

我们相信这个领域的工具应该开源：站主的数据是自己的，不该被任何商业产品绑架。

### 免费与收费的界限

我们只对**差异化的高级功能**收费，基础能力永远开源。

完整的划分依据、时间表与我们对社区的正式承诺，见 **[docs/15 开源与商业模型](docs/15-开源与商业模型.md)**。

| | 社区版（开源，永久免费） | 专业版（付费） |
|---|---|---|
| **许可证** | AGPL-3.0 | 商业授权 |
| **用户与账号** | ✅ 统一状态机、注册审批、多档权益 | |
| **媒体服务器对接** | ✅ 多服务器、权限同步、片库授权 | |
| **到期与续费** | ✅ 自动封禁、卡密、邀请树 | |
| **求片闭环** | ✅ 状态机、多源搜索、入库自动回流 | |
| **播放统计** | ✅ 记录、观影报告、排行榜 | |
| **运维** | ✅ 反代、线路调度、流量配额、证书 | |
| **通知** | ✅ 全部渠道 | |
| **插件系统** | ✅ 四级模型、插件市场、开发能力 | |
| **行为风控** | | ✅ 基于行为基线的异常检测与自动处置 |
| **多租户** | | ✅ 一套系统服务多个独立站点 |
| **AI 能力** | | ✅ 智能识别、自动补货、自然语言运维 |
| **企业特性** | | ✅ SSO、审计增强、SLA、优先支持 |

**为什么这样分**：基础功能（开号、到期、求片、统计、反代）是这个领域的**公共基础设施**，每个站主都需要，收费没有道理。而行为风控、多租户、AI 这些是**运维效率的放大器**，只有规模化运营的站主才需要，为它们付费是合理的。

### 什么时候开始收费

**现在不是，而且基础功能做完之前都不是。**

```
M0 ─ M5   全部开源，全部免费，不设任何限制
          ↓
M6        插件生态开放，依然全免费
          ↓
M7        开始区分社区版与专业版
          社区版继续免费，专业版提供差异化能力
```

也就是说：**等到基础功能真正完善了，才会开始谈收费**。在基础能力还不完整的时候就急着变现，是对用户的不负责任。

而且**已经开源的部分不会收回**。如果 M5 完成时你已经在用，那 M5 的全部能力对你永远免费。

### 我们不会做的事

- ❌ 把已经开源的功能改成收费
- ❌ 在开源版里留后门或功能开关
- ❌ 要求联网验证许可证
- ❌ 限制用户数或站点数
- ❌ 用开源版做诱饵，把关键功能藏在付费版

## 怎么做的：全程 AI 协作

**这个项目全程使用 vibecoding。** 从竞品分析到设计文档再到代码，AI 参与几乎全部产出，人类负责定义目标、判断取舍、审查结果。

我们把这个事实写在最前面，因为它是这个项目的特征之一，也影响你该怎么看待它。

### 这对使用者意味着什么

| 好处 | 说明 |
|---|---|
| **速度快** | 设计文档 30 万字、竞品分析覆盖 16 个项目，在几天内完成 |
| **证据密度高** | 所有竞品结论都标注了源码文件与行号，可以逐条核对 |
| **决策可追溯** | 每个技术选择都写了理由与被否方案（见 [技术决策记录](docs/13-技术决策.md)） |

| 风险 | 我们怎么应对 |
|---|---|
| AI 会犯错 | 所有竞品结论提供源码位置；代码有测试门禁；关键逻辑要求人工复核 |
| 抽象可能过度 | 每个抽象必须有**当前**用例，为"将来可能需要"引入的抽象会被拒 |
| 代码风格不统一 | 强制 `gofmt`/`go vet`/CI 门禁；内核有"零业务名词"自动检查 |
| 可能不理解自己在做什么 | 决策记录强制写明"为什么"，不接受"用了 X"这种无理由的结论 |

### 我们邀请你审查

**这个项目的设计文档是公开的，欢迎挑错。**

特别希望被挑战的地方：

1. **内核抽象是否过度**——有没有为了"将来可能需要"而引入的抽象
2. **竞品结论是否属实**——所有结论都标了源码位置，欢迎逐条核查
3. **三条设计公理是否成立**——尤其是"资源是能力"这条，是否会导致什么都做不好
4. **路线图排序是否合理**——尤其是 M2 与 M3 是否该并行
5. **商业模式的划分是否合理**——免费与收费的界限是否公道

提 issue 请附上具体文档章节。

M2  自助门户    3 周   ┃ 播放记录 + 观影报告 + 通知
M3  求片闭环    4 周   ┃ 状态机 + 入库自动回流                ★ 超越竞品
M4  运营变现    4 周   ┃ 分级权益 + 卡密批次 + 积分账本        ★ 超越竞品
M5  运维网络    4 周   ┃ 反代 + 持续探活 + 流量配额            ★ 超越竞品
     ────────────────────────────────────────────────
     ↑ 到此为止，全部开源免费。基础功能完整可用。

### 每个阶段的"做完"是什么意思

我们不用"完成某某模块"这种无法验证的说法，每个阶段都有可验收的交付物。

| 阶段 | 完成标志 |
|---|---|
| **M1** | 能开号、能登录、能到期自动封号；**过期用户能登录续费但不能播放** |
| **M2** | 用户能看到自己的播放记录与观影报告；**数据取不到时明确显示"加载失败"而非"暂无数据"** |
| **M3** | 用户求片后**自动走完全程**，入库后工单自动完成并通知用户，全程进度可见 |
| **M4** | 能收钱、能分级、能对账；卡密有批次与有效期；**积分余额永远不为负且可由流水复核** |
| **M5** | 能替代第三套系统；**线路状态持续可见且真的影响调度** |
| **M6** | **一个新人在 30 分钟内写出并跑通第一个插件** |

## 核心设计

### 三条公理

1. **人是核心，资源是能力。** 现有工具分成"管资源的"和"管人的"两派。EmbyOne 把用户当作一等公民，把"获取资源"当作可插拔的能力。
2. **内核只做装配，业务全在插件。** 内核里不出现 "Emby"、不出现 "积分"。它只认识三样东西：契约、注册表、事件。
3. **复杂度必须分期支付。** 功能最全的竞品，光插件系统就写了 7159 行。我们用四级插件模型把它摊开。

### 四级插件

| 级别 | 形态 | 上手 | 能干什么 |
|---|---|---|---|
| **L0** | 一个 YAML | 5 分钟 | 配置项、模板化事件响应、路由转发 |
| **L1** | YAML + 脚本 | 30 分钟 | L0 + 钩子里写逻辑 |
| **L2** | Go 源码 | 半天 | 全部能力 + 自带数据表 |
| **L3** | 任意语言 + RPC | 半天 | 全部能力，进程隔离 |

**九成的扩展需求只需要填一个配置文件。**

### 分层

```
L4  表现层    Web / API / Bot / SSE        ← 全部由插件注册
L3  内核      契约 + 注册表 + 事件总线 + 装配器   ← 零业务名词
L2  内置插件  identity media request billing ops insight notify bot
L1  提供者    emby jellyfin moviepilot qbittorrent telegram 115 stripe
L0  存储      SQLite（默认） / PostgreSQL
```

## 要解决的十个问题

竞品分析（读源码得出，结论带 `文件:行号`）发现的共同短板：

| # | 问题 | 证据 |
|---|---|---|
| 1 | 没有统一用户状态机 | 两个成熟项目分别用「4 个布尔值」和「整数 + 标记」拼状态，且都缺"注册后待审批"这一档 |
| 2 | 卖不出差价 | 有项目完全没有按等级控制媒体库的能力，只有一份全局硬编码黑名单 |
| 3 | 求片与入库零闭环 | 实测六个项目，**零个**做到"求片→下载→入库→自动通知" |
| 4 | 卡密残缺 | 三家全缺批次/有效期/作废；有项目用「字符串里有没有 Renew」判断类型 |
| 5 | 积分无账本 | 有项目实测经济系统净通胀，改价还要改代码 |
| 6 | 探活是一次性快照 | 延迟只存在于手点测速那一瞬间，不落库不参与调度 |
| 7 | 失败被吞 | 数据取不到时静默返回空，故障表现为"暂无数据" |
| 8 | 只能单机跑 | 三个项目全部假设单实例，多开就会重复扣费发码 |
| 9 | 邀请无关系树 | 有邀请配置，但没有"谁拉的谁"这个字段 |
| 10 | 无法扩展 | 13 个项目里只有 1 个有插件机制 |

完整分析：[分析/需求全景](分析/需求全景.md)

### 以及一个没人占据的位置

- **站主的工具**精通账号运营，但风控只做到"数一下开了几个会话"
- **白嫖者的工具**精通伪造播放行为，但完全不关心运营

而且——其中一方的工具是**专门逆向另一方的后台协议**写出来的。卖号侧与抢号侧已成攻防对偶，接触点却是几行写死的正则。

站在中间的人握着最厉害的东西：**行为基线**。站主知道正常人怎么看片，所以一眼能认出谁是机器。

**目前没有任何系统同时站在两边。**
