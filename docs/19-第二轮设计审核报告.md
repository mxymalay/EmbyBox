### P01 · 【判断】支付履约：提交边界、幂等与补偿所有者

位置：docs/03-数据库设计.md:417-418、449-455、467-521；docs/05-事件目录.md:36、84、521-523；docs/02-系统架构.md:807、813。

**A：processed表示“本地权益已提交、远端补偿已可靠登记”。** 验签并核对订单、金额、币种后，用(provider,event_id)去重收件。事务锁定订单/收件，写支付事实、订单paid、各项权益与流水、履约记录、远端任务，最后同事务标processed。另用履约状态local_applied/remote_applied/failed展示远端结果；order.paid.after只观察，不承担唯一发货路径。代价：新增履约记录与状态，但本地到账可快速确认。

**B：processed保留“必需远端副作用也已确认”的严格语义。** 第一事务提交paid事实与待履约任务；worker分别记录本地grant、远端建号/权限同步结果，全部必需步骤确认后第二事务标processed。每步按业务操作幂等；received/failed不等于允许再次发权益。代价：processed可能长期未终结，需任务认领、可见进度与人工处理。

两案均应以订单及快照benefit幂等，而不是仅以第三方event_id幂等：两个不同支付事件可能对应同一订单。建议补以下关系；A/B决定state的终态和processed标记时机，关系基础相同：

~~~sql
CREATE UNIQUE INDEX uq_orders_owner ON orders(id,user_id);
CREATE UNIQUE INDEX uq_entitlement_owner ON user_entitlements(id,user_id);
CREATE TABLE order_fulfillments (
 order_id TEXT PRIMARY KEY NOT NULL REFERENCES orders(id),
 state TEXT NOT NULL CHECK(state IN ('queued','local_applied','remote_applied','failed')),
 attempts INTEGER NOT NULL DEFAULT 0 CHECK(attempts>=0),
 lease_token INTEGER NOT NULL DEFAULT 0,
 lease_until TEXT,
 last_error TEXT NOT NULL DEFAULT '',
 updated_at TEXT NOT NULL
);
CREATE TABLE order_grants (
 order_id TEXT NOT NULL,
 benefit_key TEXT NOT NULL,
 user_id TEXT NOT NULL,
 entitlement_id TEXT NOT NULL UNIQUE,
 PRIMARY KEY(order_id,benefit_key),
 FOREIGN KEY(order_id,user_id) REFERENCES orders(id,user_id),
 FOREIGN KEY(entitlement_id,user_id) REFERENCES user_entitlements(id,user_id)
);
~~~

该补充DDL在原42表内存库执行通过，错误owner插入输出“IntegrityError: FOREIGN KEY constraint failed”。它允许一个订单有多个不同benefit，不把整个source_id限制成只能一条权益。若保留orders.payment_id，另加payments UNIQUE(id,order_id)，并在重建orders时以(payment_id,id)复合外键引用payments(id,order_id)；另一方案删除该双向指针，由payments.order_id及状态决定当前支付，代价是多次支付尝试的查询语义需定义。

**远端边界及补偿归属：** 不在SQL事务中等待Emby或支付网关。operation_id稳定；上游支持幂等键则使用，不支持则持久化账号ID、在指定服务器回读后继续，不能超时后盲目再建号。权限任务携desired_revision，旧任务不可覆盖新策略。billing履约协调器拥有业务完成责任，可委托media同步worker；通知插件失败不负责补发权益。管理员重试同一履约ID，退款走独立反向操作。

**不决策后果：** 幂等收件可能锁死失败发货，也可能重投再次发权益。修订验收至少覆盖本地提交后退出、远端成功响应丢失、两个事件同订单三个中断点，权益/建号均只产生一次业务结果。

### P02 · 【判断】多服务器账号关系与Registry合法择优范围

位置：docs/01-需求规格.md:73；docs/03-数据库设计.md:249-253、293-303、636-655、672-707；docs/02-系统架构.md:164-171、807。

**A：每用户每服务器最多一个账号。** 增media_accounts；保留认证user_identities作provider/issuer+subject身份，媒体账号单独关联：

~~~sql
CREATE TABLE media_accounts (
 id TEXT PRIMARY KEY NOT NULL,
 user_id TEXT NOT NULL REFERENCES users(id),
 server_id TEXT NOT NULL REFERENCES media_servers(id),
 remote_user_id TEXT,
 desired_disabled INTEGER NOT NULL DEFAULT 1 CHECK(desired_disabled IN (0,1)),
 observed_disabled INTEGER CHECK(observed_disabled IN (0,1)),
 desired_version INTEGER NOT NULL DEFAULT 0 CHECK(desired_version>=0),
 observed_version INTEGER,
 last_observed_at TEXT,
 UNIQUE(user_id,server_id)
);
CREATE UNIQUE INDEX uq_media_account_remote
ON media_accounts(server_id,remote_user_id)
WHERE remote_user_id IS NOT NULL;
~~~

observed_disabled=NULL代表未知，不能默认0冒充远端启用。本地状态/权益决定desired，回读只更新observed，不反向覆盖人工封禁。users旧emby_user_id及全局镜像停止写入，按确定的绑定服务器迁入，不猜服务器。代价：不能表达一人在同服务器多个资料账号。

**B：允许多个账号。** 加account_slot/purpose，改UNIQUE(user_id,server_id,account_slot)，保留(server_id,remote_user_id)唯一；策略/同步/额度/删除明确account_id。代价：入口与补偿分配复杂，原user_id+server_id不足以定位。

pending任务另选：A每账号合并一条，worker每次重算最新desired policy；少记录但简单。B逐版本任务、按账号串行，跳过过时版本，提交observed时核对版本；记录完整但队列复杂。当前按reason去重允许同账号多个相反任务，不能按入队顺序盲目执行。

**Registry边界：** 先选server/account，再在同一远端目标连接中择健康实现。A服务器不健康不能将建号、禁用、itemID、片库、播放历史改投B服务器。Acquire/Status黏附原provider_id/task_id；可互换搜索源或同站线路须明确目标及授权相等。服务器绑定、server_id_remote或remote_user_id变化时冻结绑定并要求确认。

**不决策后果：** 服务器级权限已分离，账号与镜像却是单一全局值，补偿和健康切换没有可追踪的目标权威。

### P04 · 【判断】跨表不变量、快照与生命周期

位置：docs/03-数据库设计.md:235-267、377-458、467-521、533-591、723-821、943-1008；docs/02-系统架构.md:780-818；docs/11-测试计划.md:85。

**A：不可变归属用数据库约束，状态转换用服务命令。** 用P01/P02关系及复合owner外键防跨用户关联；不可变账号、订单benefit、核销operation用unique。每个命令列前置状态、锁对象、写集、终态和重放结果，条件更新/CAS同时写主记录、审计与可靠任务。主记录是当前状态权威，steps/events是历史。代价：更多关系键，但所有写入口都拒绝错配。

**B：简洁DDL，由单一业务事务维护归属。** 不增加每类typed关系，但必须禁止插件直接写核心表，所有grant/退款/删除/核销走带主体的命令，校验来源owner及状态。代价：表少，但数据库不能单独拒绝错误关系，更多约束落在服务。

两案还须分别选以下边界：

- **用户状态A：** status/status_reason为管理生命周期，can_login/can_play读取时按状态+有效权益派生。成本是策略计算。**B：** 保留能力位作缓存，新增状态/策略version，状态、权益、审计及同步任务同事务更新；禁止用缓存放宽banned/deleted。成本是失效协议。未来starts_at到达也触发重算，不能只有到期扫描。已修四条件不重报。
- **已购权益A：** 引用不可变档位/策略版本或benefit_snapshot，旧购买保持其解释；成本是多版本及片库删除后的降级规则。**B：** 订单快照只保存交易解释，实际访问按当前档位；成本是调策略会影响已购用户，需收窄“改权益不影响历史订单”的访问含义。依据docs/03-数据库设计.md:381-399、416-432、672-686与docs/01-需求规格.md:110。
- **核销A：** 同事务锁码及批次，检查时间/作废/绑定用户后条件增计数，写记录与权益/积分；重复用户唯一冲突回滚计数。**B：** 条件UPDATE合并码有效期、绑定及EXISTS有效批次，再同事务发放；SQL集中但复杂。码/批次code_type明确不可变快照或严格镜像，不能双真相。依据docs/03-数据库设计.md:543-591。
- **邀请A：** 只在注册时建立且不允许换上游，事务检root/祖先，root/depth作缓存。**B：** 允许调整，递归检查或closure表防环，同事务更新子树；成本是树锁和修复。invitee唯一不保证无环。依据docs/03-数据库设计.md:352-366。
- **删除A：** 始终软删除，保留财务/审计，按类别匿名化。**B：** 到保留期允许物理删除，先将历史转匿名主体/快照；成本是清理迁移和聚合规则。不能给所有历史表一律CASCADE，也不能只写T-18“删除无孤儿”却无各类保留预期。依据docs/03-数据库设计.md:267、469、600、831-848、979、1006。

**不决策后果：** FK只证明引用存在，不保证支付者与受益人同归属、批次有效、邀请无环，亦不保证状态缓存和历史快照解释一致。

### P05 · 【判断】账本余额、收费请求与统计去重

位置：docs/03-数据库设计.md:598-627、741-742、827-886、1088；docs/04-API规范.md:288-302；docs/11-测试计划.md:139-165、433-444；docs/12-路线图.md:193、206。

**不决策后果：** 最后一条balance_after与SUM可不同（实验+100,-10,-10可保存last=90而SUM=80）；多季部分成功、取消重投和多源采集没有一致金融结果。

### P08 · 【判断】写操作幂等、并发与一次性明文响应

### P11 · 【判断】时间存储精度

### P13 · 【判断】入库Webhook认证、去重、重放与可信回读

两案都以接收端配置/凭据绑定server_id，不信body.base_url；先持久化收件再ACK，确认工单另一个提交点。

### P15 · 【判断】插件schema、SQL迁移与L3建表权限

位置：docs/03-数据库设计.md:92-98、1018-1050；docs/06-插件规范.md:108、153-162、542-558；docs/02-系统架构.md:359、398；docs/13-技术决策.md:221。

**迁移A：统一(owner,version)账本。** schema声明只是生成迁移的前端；schema_migrations主键改(owner,version)，含name/checksum/applied_at，DDL与登记同事务。L0/L1升级L2时验证现状、生成baseline并登记接管版本，停止自动diff，只执行更高版本SQL。成本是规范化/对比/baseline导出，规则统一。

**迁移B：两种互斥引擎。** 保存schema_mode=declarative|sql、版本/checksum、handover记录；SQL首版本验证旧表而不重复创建，禁止两个引擎同时工作及未经协议降回声明式。可保留全局version主键，但必须补第三方号段分配、冲突拒绝与本地0001映射。成本是两套状态及交接测试。可关闭plugin_audit只能记录审计，不能当版本真相。

**L3 B：包可带迁移，但SQL是受信安装产物。** 管理员审核/授予db.migrate，宿主限表所有者/命名空间并登记版本；不能宣称进程隔离约束宿主执行的SQL。成本是安装审核、升级与回滚。

普通DDL及版本登记可同事务，错误时一起回滚；例外操作单独分阶段、留下可恢复标记。回滚保留既定“只前进迁移+升级前备份+相容旧二进制恢复”，不强制添加down；恢复前禁止新版本写入，防旧程序读到不兼容新schema。位置docs/03-数据库设计.md:1048-1076及docs/10-部署运维.md:219-278。

**不决策后果：** 本地0001与全局版本冲突，schema→SQL重复建表或漏版本，迁移真相可能被关闭/清理。首轮SQLite修订残留在第4节，不另算新缺陷。

### P16 · 【判断】L1权限、L2信任与L3隔离

位置：docs/06-插件规范.md:378、386、436-441、574、592-607；docs/08-安全设计.md:469；docs/13-技术决策.md:255。

**能力A：保留通用SDK，传不可伪造的主体。** 所有ctx/plugins调用携宿主生成caller_plugin_id、用户主体、grant；每个exposes方法声明所需权限，同时验调用者及资源owner。publish只允许插件自有命名空间；paid/核心状态/确认入库等保留事件仅权威模块派发，payload不是授权证明。成本是签名/权限元数据和事件owner目录。

**能力B：首版取消通用跨插件调用及任意publish。** 只提供ctx.points/user/request等逐能力校验API及自身事件，成本是扩展弹性较小、授权路径简单。

**隔离A：管理员审核L1轻脚本、可信L2，L3只承诺故障隔离。** 每任务独立Runtime，仅暴露包装函数/JSON，原生API有独立deadline、取消、并发和结果大小限制；64MB写成需原型验证的预算，不能当已证硬隔离。成本低，不接纳恶意任意代码。
**隔离B：接纳不可信插件。** JS也放worker进程；L3使用独立OS身份/容器、最小环境、只读文件系统、插件目录、默认禁网，网络经宿主受限RPC。成本是平台适配、进程/资源管理。

[Goja官方API](https://pkg.go.dev/github.com/dop251/goja#Runtime.Interrupt)明确Interrupt不打断原生Go函数（包括built-ins）。**本报告推断：** 5秒/64MB不能单凭Interrupt得到，硬限承诺需原型证据。L2只允许可信代码已经披露，不作为新增漏洞。

**不决策后果：** 直接API受限却可经暴露插件或伪造核心事件间接改变业务；进程独立也不自动限制文件/网络/环境权限。

### P17 · 【判断】插件UI Schema的数据与动作边界

**A：受限声明式首版。** source/actions仅同源所属插件版本化命名空间及白名单method，规范化路径后校验，用户令牌不发外站；后端仍真实授权。定义data.items/游标适配、stats初始来源、$ref相对manifest解析、typed row/body插值、错误/空态。首版关闭iframe/spa，或作为单独受信能力。成本是表达能力有限。

### P19 · 【判断】单实例锁、远端补偿窗口与可观测性

位置：docs/13-技术决策.md:670-685；docs/10-部署运维.md:176-177、300-316、340；docs/12-路线图.md:86-87；docs/03-数据库设计.md:691-710。

**锁A：首版单活动宿主，人工接管。** 必需锁保持至停止，冲突显示owner/启动时间；确认旧实例结束后接管，删除“改multi-instance”无前提排障捷径。成本是人工恢复。
**锁B：租约自动接管。** 每次grant有单调fencing token，续期失败停领任务/停副作用，提交验证token；外部调用仍用业务幂等。成本是暂停恢复/分区测试。租约防重复抢占，不独自保证外部恰好一次。

**禁播A：本地立即拒绝，原生客户端有界最终一致。** 定义远端同步目标如正常30秒、超过5分钟告警，失败可见/可重试；数值是待签署的验收目标。成本是接受窗口。
**禁播B：立即阻止所有新播放。** 所有入口经强制鉴权，远端直连关闭，既有流终止也需协议；成本是M5级网络与客户端兼容，不能作为无反代M1承诺。

两案增加锁持有/续期失败/租约余量，权限同步最老pending年龄/失败reason、履约失败、Webhook待确认/未匹配及最老年龄。当前“pending>100”不能发现一个永久禁用失败账号。readiness包含DB、关键身份模块、必需锁、凭据解密；媒体不可达显示降级，不必让续费/管理门户一律不可用。位置docs/10-部署运维.md:300-316。

**不决策后果：** 进程存活而锁丢失/远端未封禁仍可呈现正常；绕锁改多实例会违反插件执行假设。

### P24 · 【判断】内核抽象与“资源是能力”

位置：docs/02-系统架构.md:20、109-153、268-272；docs/13-技术决策.md:196-229、214；docs/12-路线图.md:157、261-272、309、318；分析/需求全景.md:292-294。

**B：提前完整四级扩展。** M0就以通知、资源搜索、权限策略、可靠操作至少四个非平凡插件验证L0/L1/L2/L3能力、授权及升级；排期纳入实际SDK/沙箱/进程管理成本。成本是首版较慢，换来真正的独立分发验证。不能只凭“90%只写YAML”把这些成本当已省掉。

### 5.2 全DDL检查清单：可执行性与业务不变量分开

【未验证】docs/03-数据库设计.md:69、76、81、92-1015所列DDL实际为42张表，不是38张；数量矛盾已列D19。已逐块执行、逐表检查FK/主键/唯一键及部分索引；下表是覆盖清单，不把没有FK、没有业务状态CHECK的每一行都重复报成缺陷。日志/汇总允许保留历史时无FK可能是刻意设计；必须按P04决定删除与归属策略。DDL成功、空库FK检查成功不验证服务能保持跨表不变量。
