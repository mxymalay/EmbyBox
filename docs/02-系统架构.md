## 0. 三条设计公理

这三条决定了后面所有取舍，先摆在最前面。

**公理一：人是核心，资源是能力。**
现有项目分两类：MoviePilot 管资源不管人（没有注册、积分、工单、风控）；ember / usersvr 管人不管资源（下载链要么调 MoviePilot，要么没有）。EmbyOne 把「用户」当作一等公民，把「获取资源」当作一种**可插拔的能力**接进来。

**公理二：内核只做装配，业务全在插件。**
内核（Kernel）不允许出现任何业务名词——不出现 "Emby"、"qBittorrent"、"积分"、"求片"。内核只认识三样东西：**契约、注册表、事件**。Emby 对接是插件，积分系统也是插件。

**公理三：复杂度必须分期支付。**
MoviePilot 的插件系统 7159 行，因为它在第一版就解决了所有极端情况（插件依赖包安装、代际兼容、frozen 模式、跨代克隆）。EmbyOne 用**四级插件模型**把复杂度分期：90% 的扩展只需要写 YAML。

## 1. 竞品解剖：我们凭什么秒杀

| 维度 | MoviePilot | ember | Twilight | emby-pulse | Meridian | **EmbyOne** |
|---|---|---|---|---|---|---|
| 核心定位 | 资源自动化 | 用户管理 | 用户管理 | 数据大盘 | 反代调度 | **用户 + 资源 + 运营 一体化** |
| 语言/部署 | Python 3.14 单进程 | Go+Py+Vue 三服务 | Go+Next 双服务 | Py+Jinja 单进程 | Go 单二进制 | **Go 单二进制** |
| 插件机制 | ✅ 重（7159 行） | ❌ | ⚠️ goja JS 脚本 | ❌ | ❌ | **✅ 四级轻量** |
| 用户自助门户 | ❌ | ✅ | ✅ | ⚠️ 只读 | ❌ | **✅** |
| 积分/卡密经济 | ❌ | ✅ 兑换码 | ✅ 兑换码 | ❌ | ❌ | **✅ 可插件化** |
| 求片工单 | ⚠️ 订阅制 | ✅ | ✅ | ✅ | ❌ | **✅** |
| TG Bot | ✅ | ✅ 独立服务 | ✅ | ❌ | ❌ | **✅ 内置插件** |
| 多服务器 | ✅ | ❌ | ✅ Emby+Jellyfin | ✅ | ✅ 多站点 | **✅ 原生** |
| 反代/线路调度 | ❌ | ⚠️ 115 直链 | ❌ | ❌ | ✅ | **✅ 插件** |
| 播放统计/榜单 | ✅ | ✅ | ✅ | ✅✅ | ⚠️ 流量 | **✅** |
| 面板反向代理 | ❌ | ❌ | ❌ | ❌ | ✅ | **✅** |
| 新人上手理解 | 难 | 中 | 中 | 易 | 易 | **易（目标）** |

**结论**：没有一个项目同时做好「人」+「资源」+「运营」+「插件化」。我们打的是这个空位。

## 2. 技术选型与决策理由

| 决策 | 选择 | 理由 |
|---|---|---|
| 后端语言 | **Go 1.24+** | 单二进制、并发强、部署零依赖；Meridian / ember / Twilight 验证了可行性 |
| Web 框架 | **chi**（或 stdlib mux） | 极简、无魔法、可读性最高（Gin 的 context 魔法会伤害"便于理解"） |
| ORM | **sqlc + 手写 SQL** | 生成类型安全代码，SQL 可读可审计。GORM 的隐式行为是"便于理解"的敌人 |
| 主数据库 | **SQLite**（默认）/ **PostgreSQL**（可选） | 单机零配置；写一个 Repository 接口两套实现 |
| 迁移 | **golang-migrate 风格纯 SQL** | 迁移文件是唯一真相，不搞 ORM 自动建表 |
| 前端 | **Vue 3 + TS + Vite** | 生态最成熟，插件 UI 用 schema 渲染 |
| 前端 UI 库 | **Tailwind + 自研 headless 组件** | 不锁死 Element Plus（插件作者可能想换皮） |
| 插件协议 | **进程内（原生/脚本）+ 进程外（JSON-RPC over stdio/gRPC）** | 见 §5 |
| 实时通信 | **SSE**（默认）/ WebSocket | SSE 更简单、可穿透反代；通知/进度够用 |
| 调度 | **robfig/cron + 自研 worker 池** | 简单可靠，任务持久化到 DB |
| 可观测 | **slog + Prometheus metrics 端点** | 结构化日志，运维友好 |

**为什么不用 Python 单进程（学 MoviePilot）**：Python 生态在媒体自动化上确实强（插件多、库多），但 EmbyOne 的定位是**平台**，需要单二进制交付、低内存、高并发长连接（反代/SSE）。Python 生态能力通过 **L3 外部插件**（进程外 RPC）接入——这样既拿到生态，又不被拖累。

│  └─────────────┘ └─────────────┘ └─────────────┘             │
├───────────────────────────────────────────────────────────────┤
│  L2  Built-in Plugins（内置插件 = 官方能力域）                 │

│  emby │ jellyfin │ plex │ moviepilot │ qbittorrent │ tmdb │    │
│  telegram │ 115 │ alist │ stripe │ turnstile │ ...            │
├───────────────────────────────────────────────────────────────┤

└───────────────────────────────────────────────────────────────┘

**依赖方向铁律**：L4 → L3 → L2 → L1。L3 内核永远不知道 L2/L1 里有什么具体实现，只通过注册表拿到 `Contract` 接口。

## 4. 内核设计

### 4.1 三个核心抽象

```go
// ─────────── 1. 契约（Contract）：一切能力都是接口 ───────────
// pkg/kernel/contract/capability.go

type Capability interface {
    Name() string                  // 全局唯一，如 "media-server.emby"
    Version() string
    Meta() CapabilityMeta          // 描述、作者、所需权限
}

// 媒体服务器能力
type MediaServer interface {
    Capability
    Users(ctx, ...) ([]MSUser, error)
    CreateUser(ctx, spec) (MSUser, error)
    SetPolicy(ctx, userID, Policy) error
    Libraries(ctx) ([]Library, error)
    Items(ctx, libID, page) ([]Item, error)
    Playing(ctx) ([]Session, error)         // 正在播放
    PlaybackHistory(ctx, from, to) ([]Record, error)
    ServerInfo(ctx) (ServerInfo, error)
}

// 下载器能力
type Downloader interface {
    Capability
    Add(ctx, Torrent) (TaskID, error)
    List(ctx, filter) ([]Task, error)
    Remove(ctx, id, deleteFiles bool) error
    Paths(ctx) ([]string, error)
}

// 资源提供者能力（MoviePilot / PT / 网盘 都实现它）
type ResourceProvider interface {
    Capability
    Search(ctx, Query) ([]Resource, error)
    Acquire(ctx, Resource) (AcquireResult, error)  // 下载 or 转存
    Status(ctx, AcquireID) (AcquireStatus, error)
}

// 通知能力
type Notifier interface {
    Capability
    Channels() []Channel
    Send(ctx, Channel, Message) error
}
```

**关键**：能力接口按**业务语义**定义，不按外部系统定义。新增一个"115 网盘"实现 `ResourceProvider` 就能接进求片链，内核和其他插件一行都不用改。

### 4.2 能力注册表（Registry）

```go
// pkg/kernel/registry/registry.go

type Registry struct {
    caps map[string]Entry    // name -> 实例 + 元数据 + 优先级
}

// 同类型多实现：注册表按优先级返回，插件可声明 priority
func (r *Registry) Register(c Capability) error
func (r *Registry) Get(name string) (Capability, bool)
func (r *Registry) AllOf[T Capability]() []T          // 泛型取某类能力的全部实现
func (r *Registry) Best[T Capability](ctx) (T, error) // 按优先级/健康度择优
```

内置 `health` 探针：每个 Capability 可选实现 `HealthCheck()`，注册表维护健康度，`Best()` 自动跳过不健康的实现。这是 Meridian 的多线路调度思路，但抽象到内核层。

### 4.3 事件总线（EventBus）= 钩子机制

MoviePilot 用 `ChainEventType` 枚举 + 插件订阅点，设计是对的，我们沿用并强化：

```go
// pkg/kernel/event/bus.go

type Event struct {
    Type   string             // "user.register.before"
    Data   map[string]any
    Result map[string]any     // 插件可写入，后续插件可见
}

type Bus struct{ ... }
func (b *Bus) Publish(ctx, evt Event) error          // 同步，可中断（拦截型）
func (b *Bus) Async(ctx, evt Event)                    // 异步，不阻塞
func (b *Bus) On(pattern string, h Handler, pri int)   // 插件订阅，支持通配
```

**事件命名规范**：`<领域>.<实体>.<时机>`，时机只有 4 个标准词：

| 时机 | 语义 | 能否否决 |
|---|---|---|
| `.before` | 发生前，可修改数据 | ✅ 返回 error 中断 |
| `.after` | 发生后，副作用 | ❌ |
| `.check` | 校验，可投反对票 | ✅ |
| `.provide` | 请求数据源（如"谁能提供搜索"） | ❌ 收集所有结果 |

内置事件清单（插件可订阅的扩展点）——这是**扩展点的百科全书**：

```
user.register.before / .after
user.login.before / .after / .check
user.expire.check
user.policy.provide            # 谁能提供权限策略
playback.report.provide        # 谁能提供播放记录
media.identify.before / .after # 媒体识别
media.library.sync.after
request.create.before / .after # 求片
request.search.provide         # 谁能搜资源（多 Provider 并发）
request.acquire.before / .after
request.complete.check
resource.ingest.after          # 入库完成
points.change.before / .after
order.create.before / .after
notification.provide           # 谁能发通知
schedule.job.provide           # 谁能注册定时任务
api.route.provide              # 谁能注册 HTTP 路由
ui.page.provide                # 谁能注册前端页面
```

**每个扩展点都是一次 `Publish`，插件是订阅者**。这是"便于理解"的关键：想知道系统能扩展什么，读这 30 行事件清单就够了，不用翻 7000 行代码。

### 4.4 装配器（Assembler）

```go
// pkg/kernel/assemble/assemble.go —— 内核唯一的"主流程"

func Boot(cfg Config) (*App, error) {
    reg := registry.New()
    bus := event.NewBus()

    plugins, err := loader.Discover(cfg.PluginDirs...)       // 1. 发现
    if err != nil { return nil, err }

    ordered, err := resolve.Dependencies(plugins)             // 2. 拓扑排序（依赖排序）
    if err != nil { return nil, err }

    for _, p := range ordered {                               // 3. 按序装配
        if err := p.Register(reg, bus); err != nil {          //    注册能力 + 订阅事件
            return nil, fmt.Errorf("plugin %s: %w", p.Name(), err)
        }
    }

    if err := permissions.Verify(plugins, cfg.Grants); err != nil {  // 4. 权限校验
        return nil, err
    }

    if err := app.Start(); err != nil { ... }                 // 5. 启动（含迁移、调度、HTTP）
}
```

**这就是内核的全部**：发现 → 排序 → 注册 → 鉴权 → 启动。业务代码一行都不在这。

## 5. 插件体系（核心创新）

### 5.1 四级插件模型：复杂度分期支付

| 级别 | 形态 | 能力上限 | 写什么 | 适合谁 |
|---|---|---|---|---|
| **L0 声明式** | `plugin.yaml` | 注册 Provider、配置项、路由转发、事件转发 | 只写 YAML | 90% 场景：接一个新的媒体服务器预设、加一条通知渠道 |
| **L1 脚本** | `plugin.yaml` + `hook.js` | 同 L0 + 事件钩子内写 JS 逻辑 | YAML + JS | 转换字段、条件过滤、自定义消息模板 |
| **L2 原生** | Go 插件源码，编译进主程序 | 全部能力 + 可注册自带数据表 | Go | 官方能力域、性能敏感路径 |
| **L3 外部** | 独立进程 + JSON-RPC/gRPC | 全部能力（除自带表迁移） | 任意语言 | Python 生态复用（MoviePilot 对接、爬虫、OCR） |

**为什么这样分**：MoviePilot 的问题不是设计错，是**没有台阶**——所有插件都必须是完整 Python 类，所以插件系统必须支撑完整的包安装、依赖解析、版本兼容。我们把 90% 的扩展需求压到 L0/L1，内核就不需要那 7159 行。

L3 用 Twilight 的思路（它用 goja 跑 JS），但更进一步：**进程外 RPC**，语言无关，进程隔离（插件崩了不影响宿主）。

### 5.2 插件清单格式（L0/L1）

```yaml
# plugins/emby-jellyfin-sync/plugin.yaml
apiVersion: embyone.io/v1
kind: Plugin
metadata:
  id: emby-jellyfin-sync
  name: Emby ↔ Jellyfin 双向同步
  version: 1.2.0
  author: community
  license: MIT
  description: 让 Emby 与 Jellyfin 的用户、片库、播放记录保持一致
spec:
  requires:                        # 依赖其他插件
    - id: emby-provider
      version: ">=1.0.0"
    - id: jellyfin-provider
      version: ">=1.0.0"

  permissions:                     # 能力授权清单（运行时强制校验）
    - media-server.read
    - media-server.write
    - user.read
    - http.outbound:api.example.com  # 出站域名白名单

  config:                          # 配置项 → 前端自动渲染表单
    - key: sync_interval
      type: duration
      default: 30m
      label: 同步间隔
    - key: direction
      type: enum
      options: [ bidirectional, emby_to_jellyfin, jellyfin_to_emby ]
      default: bidirectional
      label: 同步方向
    - key: conflict_policy
      type: enum
      options: [ newest_wins, emby_wins, jellyfin_wins, manual ]
      default: newest_wins
      label: 冲突策略

  hooks:                           # 订阅事件（L1 时可指向 JS）
    - event: user.register.after
      handler: ./hooks/on-user-register.js
    - event: playback.report.provide
      handler: ./hooks/provide-playback.js

  routes:                          # 注册 HTTP 路由
    - path: /api/plugins/sync/status
      file: ./handlers/status.js
      auth: user

  ui:                              # 注册前端页面（schema 驱动）
    - slot: admin.sidebar
      label: 跨服务器同步
      icon: refresh
      page:
        type: form
        fields: [ { $ref: "#/spec/config" } ]
        actions:
          - { label: 立即同步, method: POST, path: /api/plugins/sync/run }

  jobs:                            # 注册定时任务
    - id: sync-loop
      schedule: "@every {{ .config.sync_interval }}"
      handler: ./jobs/sync.js
```

**读这一份 YAML 就能完整理解这个插件做什么、要什么权限、挂在哪里**——这就是"便于理解"。

### 5.3 插件数据模型隔离

MoviePilot 让插件自带 SQLAlchemy 模型 + Alembic 迁移（设计对，但重）。

EmbyOne 方案：**表前缀强制命名空间 + 自动迁移**

```sql
-- 插件 id = emby-jellyfin-sync，表名必须带前缀
CREATE TABLE plugin_emby_jellyfin_sync__mapping (
    ...
);
```

- L0/L1 插件：在 `plugin.yaml` 里用 `schema:` 声明表结构（简单 DDL 子集），内核自动建表和演进（加列）
- L2/L3 插件：提供 SQL 迁移目录，内核按版本号依次执行
- 卸载插件 = `DROP TABLE plugin_<id>__*`（默认保留数据，可配置）

### 5.4 插件 UI：Schema 驱动

MoviePilot 让插件返回 Vuetify 组件树——有效但把插件锁死在 Vuetify 上。

EmbyOne 用**自定义 UI Schema**（借鉴 JSON Schema + 少量组件描述）：

```json
{
  "type": "page",
  "title": "跨服务器同步",
  "blocks": [
    { "type": "stat-row", "items": [
        { "label": "待同步用户", "value": "{{ stats.pending_users }}" },
        { "label": "最近同步", "value": "{{ stats.last_sync | relative_time }}" }
    ]},
    { "type": "form", "fields": [ { "$ref": "#/spec/config" } ] },
    { "type": "table", "source": "/api/plugins/sync/conflicts", "columns": [...],
      "rowActions": [ { "label": "以 Emby 为准", "method": "POST", "path": "/api/plugins/sync/resolve" } ] }
  ]
}
```

好处：① 不锁 UI 框架；② L1 插件也能出可视化页面；③ 前端只有一套渲染器（约 30 个组件类型），维护成本低。

需要完全自定义 UI 的插件走 `"type": "iframe"` 或注册独立 SPA 入口（逃生舱）。

### 5.5 插件生命周期与安全

```
Discovery → Resolve(依赖) → Grant(权限确认) → Register → Start
    → 运行中: Health / Config-Hot-Reload
    → Stop → Unload
```

- **权限清单强制校验**：插件调用 `http.outbound` 访问白名单外域名 → 拒绝并审计日志
- **L3 进程隔离**：插件进程崩溃 → 内核重启它；超时 → 熔断；CPU/内存限额
- **审计日志**：所有插件的能力调用记录到 `plugin_audit` 表（可关）
- **签名校验**（可选）：插件市场分发的插件支持签名，企业部署可强制

### 5.6 插件市场（生态飞轮）

参考 MoviePilot 的 catalog/online/local 三态：

```
plugins/
├─ installed/          # 已安装
├─ registry.yaml       # 官方索引（也可自建私有源）
└─ cache/
```

- 索引来自 GitHub Release / 自建源
- 支持「官方 / 社区 / 私有」三级信任
- 一键安装、升级、回滚（版本化目录 + 原子切换）

## 6. 核心能力域（L2 内置插件）

内核里没有业务，所有业务都在这些内置插件里。每个都可以被替换或禁用。

| 插件 | 职责 | 关键扩展点 |
|---|---|---|
| **identity** | 用户注册/登录/会话/绑定/生命周期 | `user.*` 全系列，支持外挂认证 Provider（Emby/TG/OIDC/Passkey） |
| **media** | 媒体服务器抽象、片库同步、播放上报 | 实现 `MediaServer`，提供 `playback.report.provide` |
| **request** | 求片工单：搜索→审批→获取→入库→复核 | `request.*`，下游接任意 `ResourceProvider` |
| **billing** | 计划/订单/积分/卡密/邀请码 | `order.*`、`points.*`，可外挂支付 Provider |
| **ops** | 线路/反代/节点/流量/限速/证书 | 提供 `ops.route.provide` |
| **insight** | 统计/榜单/观影报告/趋势 | 提供 `insight.dataset.provide` |

## 11. 为什么这个架构"便于理解"

对照 MoviePilot 的复杂度来源，逐条给出我们的解法：

| 理解障碍 | MoviePilot 的现状 | EmbyOne 的解法 |
|---|---|---|
| 不知道系统能扩展什么 | 翻 7159 行插件代码 | 读 `EVENT-CATALOG.md`（自动生成，30 个扩展点） |
| 不知道插件怎么写 | 实现 20+ 抽象方法 | 写一份 YAML，需要逻辑时加个 JS |
| 不知道请求怎么走的 | Chain mixin + Protocol + 动态 run_module | 一条直线：HTTP → Service → Publish(事件) → 插件响应 |
| 找不到业务代码 | 分散在 chain/application/modules 三层 | 一个功能一个目录，`plugin.go` 150 行看完注册 |
| 依赖太重装不上 | Python 3.14 + 100+ 包 + 插件还要装 pip 包 | Go 单二进制，L3 插件才需要额外运行时 |
| 改了怕崩 | 隐式依赖、跨模块副作用 | 事件驱动 + 权限清单 + 契约隔离 |

**一句话**：MoviePilot 的插件系统是「万能但需要读完 7000 行才能用」，EmbyOne 要的是「读 30 行事件清单就能开工，需要更深时再往下钻」。

## 12. 关键子系统设计要点

从 15 个项目实测中提炼的**可直接采用**的具体方案，以及必须绕开的坑。

### 12.1 反向代理内核（借鉴 Meridian，但要补上它缺的）

**采用**：

- 三层 `http.ResponseWriter` 包装链：`日志 → 限速/计量 → [图片缓存|进度合并] → ReverseProxy`。计费发生在**每次内核 write 之后**（不是 `io.Copy` 收尾），中断的流也能精确入账
- **WebSocket 不走 `httputil.ReverseProxy`**，手工 `Hijack` 手工写 request line，并强制校验 `101 + Upgrade: websocket + Connection: upgrade` 三件套才放行隧道——否则它就是一条**无限速无限额的裸通道**
- **入口分流在同一个 listener 内完成**（host / path / port / both 四模式），因此 `ReadTimeout`/`WriteTimeout` 必须设为 0；host-only 模式要有三道闸：启动期拒绝 + 运行期 403 + TLS SNI == Host 校验
- **DNS pinning 放在 dial 层**：只在与 expectedHost/Port 完全一致的 authority 上，从预校验的 pinned IP 列表按 `tcp4`/`tcp6` 分族重试；用 30+ 条 forbid 前缀挡私网/回环/CGNAT/metadata（`169.254.169.254`）

**超越（Meridian 的已知短板）**：

| 短板 | 我们的做法 |
|---|---|
| 无延迟感知调度，failover 只认 5xx | 线路状态是持续对象：`(滑动窗口成功率, P50/P95, 最近失败原因, 冷却截止)`，落库 + 定时轻量探测，`ordered()` 真正消费它 |
| 延迟只存在于手点测速的瞬间，不落库 | 探活结果写 `route_stats`，参与调度权重 |
| 单管理员、无 RBAC、无审计日志 | 内核级 RBAC + `audit_log` 全覆盖 |
| 无通用 API 限流（只有登录 5次/1min） | 按插件/用户/端点三维限流 |

### 12.2 流量配额：预留-结算协议（直接抄 Meridian）

「先累加再判断」是错的。正确做法：

```
到达请求
  → 按预期字节数【预留】配额（原子）
  → 转发，实时计量
  → 请求结束【结算】实际字节，退还差额
  → 配额不足 → 拒绝，不预留
```

配额记录带**周期代际号**（`period_generation`），防止跨计费周期污染——上周期预留、下周期才结算的流量会被正确归入上周期。

### 12.3 数据路由与降级可见性（超越 emby-pulse）

emby-pulse 的「双擎路由」（API 穿透 / 数据库直读）思路极好，但**失败被吞**：API 分支失败只 `print` 不回落，返回空 → 故障表现为「暂无数据」。

**我们的做法（两条铁律）**：

1. **降级必须可见**：任何取数失败都要产生 `degraded` 指标（计数器 + 大盘 + 通知），UI 必须区分「暂无数据」与「取数失败」，绝不静默返回空
2. **降级必须自动回落**：API 失败 → 自动回落数据库 → 再失败才报错，且回落事件记入审计

**报表数据源分层**（来自 G4 的四路线实测）：

| 层级 | 数据源 | 用途 | 代价 |
|---|---|---|---|
| A | Emby 原生聚合端点（`/Items/Counts`、`/Sessions`） | 大盘骨架，秒级 | 只有「此刻」无历史 |
| C | Playback Reporting 插件（`/user_usage_stats/*`） | **真实历史时长与趋势**（唯一途径） | 必装插件；返回结构有 `colums` 拼写坑 |
| D | 自建落库 | 业务数据（邀请/到期/积分/求片） | 只能自建 |
| B | 逐项聚合（`/Users/{id}/Items?Fields=Size`） | 单条查询、首次建库 | **全量拉取会 OOM，必须分页增量** |

未装 Playback Reporting 时，相关模块**整体降级隐藏**而不是显示 0。

### 12.4 自动删改动作必须留「失败安全出口」

来自 emby-pulse 的缺集截胡：推季包后按 `added_on < 300s` + size 匹配种子，正则提集数，`filePrio 0/1` 剔除非目标集。

**它的安全阀值得写进我们的编码规范**：

> **正则识别不出集数时，选择「放行」而不是「全删」。**

推而广之：任何自动删除/自动修改的动作，在**判定不确定时必须偏向保留**，并把不确定项写入待人工确认队列。

### 12.5 外部资源代理：用密码学替代白名单

需要代理第三方直链时（海报、115 CDN、字幕），不要做域名黑名单——做**加密 capability 令牌**：

```
原始外部 URL
  → AES-GCM 加密 → /_proxy/<capability>
     绑定：站点 + 策略版本 + 过期时间
  → 客户端附加 query 不改变签名目标
```

收益：天然带过期、策略版本绑定、可审计；无需维护黑名单规则。

**图片同源代理是刚需**（G4 实测三个项目各自实现了一遍）：HTTPS 门户 + HTTP Emby 的混合内容问题必须靠同源代理解决，且**必须带鉴权**（gaodong 漏了）。

### 12.6 求片匹配回填（修正 embyforge 的必现 bug）

embyforge 用 Emby webhook 的 `Server["Id"]` 匹配本地 `servers.id`（`gen_random_uuid()`）——**必然失败**，导致整条播报链静默失效。

**正确做法**：

```go
// webhook 解析后，用 base_url 反查本地服务器，而不是用 Emby 的 Server.Id
server, err := repo.FindServerByBaseURL(ctx, webhookServerURL)
if err != nil {
    // 不要静默 return！记 degraded 指标 + 落未匹配事件表
    metrics.WebhookUnmatched.Inc()
    return repo.SaveUnmatchedEvent(ctx, raw)
}
```

**完整回填链**（G4 指出「全组最缺的一环」）：

```
Emby webhook (item.added)
  → 事件映射（TMDB/IMDB ID + 季集号）
  → 匹配未完成工单（request_steps 里 stage=waiting_ingest）
  → 幂等回填 status=done + 通知用户
```

### 12.7 通知投递协议（直接照抄 bubble 的规范）

```
Header: X-Notification-Timestamp: <unix>
Header: X-Notification-Signature: HMAC-SHA256(timestamp + "." + rawBody, secret)
Header: X-Notification-Delivery-Id: <sourceId>:<deliveryId>     # 幂等键
```

- 重试 5 次指数退避，**优先遵从响应里的 `Retry-After`**
- 接收端按 `deliveryId` 幂等去重
- 所有出站通知走同一套协议，插件只需实现发送器

### 12.8 行为基线风控（我们的独有设计，无开源实现可抄）

G2 的关键洞察：**运营端握有正常行为基线，所以能识别自动化工具**。

对手（emby-keeper 类）的可检测特征：

| 特征 | 正常用户 | 自动化工具 |
|---|---|---|
| 播放位置上报 | 非线性、有暂停/拖动 | **严格线性递增** |
| 起播时序 | 有决策延迟 | **瞬时起播** |
| 设备标识 | 有自然变化 | **持久化固定 DeviceId** |
| 会话时长分布 | 长尾、连续剧集 | **集中在 5–10 分钟** |
| 浏览路径 | 随机、跳转 | **完整重放固定路径**（Views→ResumeItems→LatestItems） |
| 请求节奏 | 抖动大 | sleep 参数化，抖动小 |

**设计**：`risk` 插件订阅 `playback.report.after`，维护每用户的**行为基线**（滚动统计），输出异常评分，按阈值触发：观察 → 告警 → 限速 → 封禁。

同时提供**官方保活**（用户无需装第三方工具），从根上消除这类工具的动机。

### 12.9 单实例约束必须显式化

三个参考项目全部假设单实例，且只在 bubble 里显式声明（`single_instance_confirmed`）。

**我们的做法**：需要互斥的插件在清单里声明：

```yaml
spec:
  execution:
    mode: single-instance           # single-instance | multi-instance
    lock: db-advisory               # db-advisory | redis | none
```

启动时自检并获取 advisory lock，拿不到就拒绝启动并明确报错——**而不是让它在运行时变成偶发的重复扣费**。

### 12.10 用户状态模型：三态分离 + 单一写路径（本领域最该做对的一件事）

G1 实测结论：**ember 和 twilight 都没做对**——前者用 4 个 bool 拼，后者用 `Role int + Active + ExpiredAt + PendingEmby` 组合。

**正解：一个状态枚举 + 一个原因字段 + 三个正交的能力位。**

```go
type UserStatus string
const (
    StatusPending UserStatus = "pending"   // 注册后待审批 ★两者都缺这一档
    StatusActive  UserStatus = "active"
    StatusExpired UserStatus = "expired"
    StatusBanned  UserStatus = "banned"
    StatusDeleted UserStatus = "deleted"
)

type StatusReason string
const (
    ReasonManual                    StatusReason = "manual"
    ReasonSystemExpiry              StatusReason = "system:expiry"
    ReasonSystemTelegramMembership  StatusReason = "system:telegram_membership"
    ReasonSystemInviteDetach        StatusReason = "system:invite_detach"
)

type User struct {
    Status        UserStatus
    StatusReason  StatusReason
    // ── 三个正交能力位（ember 的正确洞察）──
    CanLogin      bool  // 能否登录  —— 过期用户 = true，可以登录续费
    CanPlay       bool  // 能否播放  —— 过期用户 = false
    RemoteDisabled bool // 远端镜像  —— Emby 侧的实际禁用状态
}
```

**为什么必须分开**：`CanLogin=true && CanPlay=false` 是「过期但可自助续费」的唯一表达。合成一个字段就永远做不对。

**单一写路径铁律**（学 twilight 的 `normalizeUserStateMarkers`，`store.go:253-272`）：

```go
// 所有状态变更必须走这里，禁止任何地方直接 UPDATE status
func NormalizeUserState(old, next User) User {
    next.StatusReason = deriveReason(old, next)     // 谁改的？
    next.CanLogin     = isLoginAllowed(next)
    next.CanPlay      = isPlayAllowed(next)
    next.AutoDisabled = markAutoDisabled(old, next) // 自动对账只恢复自己禁的
    return next
}
```

**关键衍生字段 `AutoDisabled`**（twilight `store.go:191-195`）：让**自动对账只恢复系统自己禁用的账号，绝不误解人工封禁**。ember 缺这一层，是明确的坑。

**远端一致性**（ember 的正解）：所有状态变更路径收敛到单一入口 `ApplyEffectiveUserPolicy(userID, reason)`，失败写 `pending` 任务表，worker 轮询重试，**用户级 advisory lock 跨实例串行**。远端操作永远不与本地事务强绑定。

### 12.11 幂等与并发：四条硬规则

| 场景 | 错误做法 | 正确做法 |
|---|---|---|
| **支付回调** | 一张表一个 `processed bool` | **四态状态机**：`received/failed`（上次崩溃，允许重试驱动履约）+ `processed/skipped`（真幂等，直接返回）。同一事件重放不会重复发放权益 |
| **下单** | 直接创建 | **占位行 + `Idempotency-Key=checkout:<id>`**，并发重复下单被唯一约束挡住 |
| **改密踢下线** | session 黑名单 | **`pwdSig` 密码指纹写进 JWT**，改密/重置/停用即时失效全部令牌，零额外存储 |
| **跨进程状态** | 进程内 map | **乐观并发**：`version` 列 + UPSERT 命中 0 行即回滚重试 |

**订单必须不可变快照**：`order.benefits` 落库后永不修改，改价只影响新订单。否则调价会篡改历史订单的权益解释。

### 12.12 调度器形态：DB 租约队列（取 twilight，不取 ember）

| | ember | twilight | 我们 |
|---|---|---|---|
| 形态 | 硬编码 cron 表达式 | DB 租约队列 | **DB 租约队列** |
| 改调度 | 要重启 | 运行时可改 | 运行时可改 |
| 参数 | 无 | `runtime_params`（`dry_run` / `breaker_percent` / `breaker_max`） | 同 twilight |
| 重试 | 无 | 失败重试 15min，**只重试可安全重放的每日任务** | 同 twilight |
| 抢占 | 无 | 30s 租约 + 2s 心跳 | 租约 + 心跳 + advisory lock |
| 告警 | 无 | 失败/恢复双向告警 | 同 twilight |

**`dry_run` 是运维刚需**：所有破坏性任务必须能空跑演练一次再真跑。

### 12.13 反枚举：安全工程化（ember 做得好，直接抄）

**核心手法：未注册邮箱也要消耗限流配额。**

```
忘记密码请求
  → 无论邮箱是否存在，都【消耗一次限流配额】
  → 无论内部发生什么错误，都返回【同一句 200 文案】
  → 攻击者无法通过 200 vs 429 的差异枚举已注册邮箱
```

同样适用于：登录、注册、TG 绑定（四条命令统一中性文案）。

**这是一条编码规范，不是什么高级技巧**——但它决定了一个站点会不会被拖库式枚举。

### 12.14 明确不要抄的东西

| 反面教材 | 出处 | 为什么 |
|---|---|---|
| **单行 JSONB 存全局状态** | twilight `store.go` 5975 行 God Object | 全量读改写、不可 SQL 查询、无法行级隔离。它的「整体快照导出」（`twilight-export/v1` + Argon2id + AES-256-GCM）可以吸收为**运维功能**，但不能作为**存储形态** |
| **同进程 JS 沙箱** | twilight Goja | 「进程堆 256MB + 8s 墙钟 + 512 条状态」是止损不是隔离，且按整进程算内存可能误杀。我们的 L3 走**进程外 RPC** |
| **CSRF 整体禁用** | twilight（`csrf.go.disabled` + 硬编码"严禁修改"） | 配合 CORS 的 `allow_credentials=true` + 反射任意 Origin → 可被第三方带凭据跨站读写 |
| **v1/v2 双路由表并存** | twilight（337 + 380 = 717 条路由） | 维护地狱。版本化靠**参数兼容 + 弃用周期**，不靠复制路由表 |
| **无版本化迁移** | twilight（靠 `ADD COLUMN IF NOT EXISTS` 补列） | 无法回滚、无法审计。我们用带序号的 SQL 迁移 |
| **文档与代码冲突** | twilight 有 9403 行文档仍出现 6 处硬冲突（`/admin/whitelist` 语义完全写反） | **文档必须能被验证**——ember 的做法值得抄：每个能力标注 `file:path:line` 索引；我们额外让 `EVENT-CATALOG.md` 从代码自动生成 |
| **图片代理无鉴权** | gaodong `/api/media/image/{id}/{type}` | 混合内容问题的解法不能顺便把鉴权也丢了 |
| **明文密码入库** | sakura-embyboss | `pwd`/`pwd2` 明文，webhook 还把 `bot_token` 当 API token |
| **默认凭据** | 多个项目 | `admin/admin`、JWT 默认密钥、`ProxyFix x_for` 硬编码。唯一做对的是 emby-register-enhanced：`FLASK_SECRET_KEY` 缺失即 `raise` |

### 12.15 出站安全：统一一个校验组件

twilight 出现了**沙箱 fetch 严、通用出站松**的两套标准。我们必须：

```go
// 全系统唯一的出站校验入口
func ValidateOutboundURL(raw string, allowedHosts []string) (*url.URL, error)
```

- L1 脚本的 `ctx.http`、L3 插件的 RPC 代理、内置插件的 HTTP 客户端，**全部走这一个函数**
- 拒绝：非 http(s) 协议、内网地址段（`127.0.0.0/8`、`10/8`、`172.16/12`、`192.168/16`、`169.254/16` 含 metadata、`::1`、`fc00::/7`）、带凭据的 URL、未在白名单内的域名
- DNS 解析后二次校验（防 DNS rebinding），并用 pinned IP 建连

## 13. 待定问题（需要一起拍板）

1. **L1 脚本引擎选型**：goja（纯 Go，Twilight 在用）vs QuickJS 绑定 vs 直接上 Wasm——影响性能和生态

6. **ORM 选型确认**：sqlc（类型安全、SQL 可控）vs ent（图式建模、代码生成强）
