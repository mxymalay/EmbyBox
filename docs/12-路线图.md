# EmbyOne 设计文档 · 12 路线图

> 每个里程碑都给出**可验收的交付物**，而不是"完成某某模块"这种无法判断的说法。

---

## 1. 总览

```
M0 内核骨架   2 周  ┃ 契约 + 注册表 + 事件总线 + 装配器
M1 身份闭环   3 周  ┃ 统一状态机 + 注册审批档位 + 到期封禁     ★ 打平竞品
M2 自助门户   3 周  ┃ 播放记录 + 观影报告 + 通知
M3 求片闭环   4 周  ┃ 状态机 + 入库自动回流                    ★ 超越竞品
M4 运营变现   4 周  ┃ 分级权益 + 粒度授权 + 卡密批次 + 积分账本  ★ 超越竞品
M5 运维网络   4 周  ┃ 反代 + 持续状态探活 + 流量配额            ★ 超越竞品
M6 生态开放   4 周  ┃ L0/L1 插件 + 插件市场 + 文档站            ★ 护城河
M7 差异化     持续  ┃ 行为风控 + 多租户 + AI Agent
```

**关键路径**：M0 → M1 → M3 → M4。M2 可与 M3 并行。

---

## 2. M0 · 内核骨架

**周期**：2 周
**目标**：一个能启动、能装配插件、能提供 HTTP 服务的空壳。

### 交付物

| 交付物 | 验收标准 |
|---|---|
| `pkg/kernel/contract` | 定义 `Capability` / `MediaServer` / `Notifier` / `Authenticator` / `Route`，**零业务名词** |
| `pkg/kernel/registry` | 支持注册、查询、按 Kind 过滤、按优先级 + 健康度择优；重名注册报错 |
| `pkg/kernel/event` | 支持四种时机、通配订阅、优先级、`Publish`/`Notify`/`Collect` 三种派发方式 |
| `pkg/kernel/plugin` | 清单解析与校验、四级模型、权限清单、拓扑排序、循环依赖检测 |
| `pkg/kernel/assemble` | 五步装配流程跑通；启动失败时明确报错并回滚 |
| `pkg/kernel/store` | SQLite 连接、迁移执行、事务辅助、方言适配 |
| `pkg/kernel/schedule` | 5 字段 cron + `@every` 解析；租约抢占；`dry_run`；panic 隔离 |
| `pkg/kernel/httpapi` | 中间件链、统一响应信封、限流、从事件总线收集路由并挂载 |
| `plugins/example-hello` | 一个 L0 示例插件，能被加载、校验、在后台可见 |
| 测试 | 上述每个包有单元测试；迁移测试通过 |

### 验收

```bash
$ ./embyone
{"level":"INFO","msg":"装配完成","插件数":1,"能力数":0,"事件订阅数":0}
{"level":"INFO","msg":"HTTP 服务已启动","addr":"[::]:8080"}

$ curl localhost:8080/healthz
{"code":200,"message":"success","data":{"status":"ok"}}

$ curl localhost:8080/api/v1/system/events | jq 'length'
31                       # 扩展点清单可查询

$ go test ./... -race
ok
$ ./scripts/check-kernel-purity.sh
PASS                     # 内核里没有业务名词
```

### 风险

| 风险 | 缓解 |
|---|---|
| 内核抽象过度，为将来预留太多 | 每个抽象都必须有**当前**的用例；没有用例的不写 |
| 权限系统过早复杂化 | M0 只做"声明 + 校验 + 记日志"，不做动态授权 UI |

## 3. M1 · 身份闭环 ★

**周期**：3 周
**目标**：能开号、能登录、能到期封号。**这一步做完即打平竞品**。

### 交付物

| 交付物 | 验收标准 |
|---|---|
| `internal/provider/emby` | 完整实现 `MediaServer`；连接测试、建号、改权限、禁用、查片库 |
| `internal/plugin/identity` | 用户 CRUD、会话、密码、状态机 |
| **统一状态机** | 单一 `status` 枚举 + `status_reason`；`can_login` 与 `can_play` 分离 |
| **状态变更唯一入口** | 所有写入走 `NormalizeUserState`；`auto_disabled` 标记生效 |
| 注册三档 | 开放 / 邀请码 / **待审批**（竞品两个都缺） |
| 到期扫描 | 定时任务：扫描 → 远端禁用 → 本地变更 → 通知 |
| Policy 同步队列 | 远端失败进补偿队列，有 worker 重试，状态对用户可见 |
| 登录/注册/找回 | 实现 §[04-API规范](04-API规范.md) 列出的全部认证接口 |
| 反枚举 | 四条路径的失败响应一致；失败消耗限流配额 |

### 验收

通过 [11-测试计划](11-测试计划.md) §5.1 的**用户生命周期全流程**（16 步）。

关键断言：
- 过期用户能登录、能看个人中心、能续费，**但不能播放**
- 自动任务不会误解封人工封禁的账号
- 远端建号成功但本地落库失败时，有补偿不留孤儿号

### 风险

| 风险 | 缓解 |
|---|---|
| Emby API 行为有坑（如 `CopyFromUserId` 被静默忽略） | 建号后**回读校验**，而不是假设成功 |
| 远端与本地的双向同步出现抖动 | 不做双向实时同步，只做**本地为准 + 单向推送 + 对账任务** |

## 4. M2 · 自助门户

**周期**：3 周（可与 M3 并行）
**目标**：用户能自己看数据、自己管自己。

### 交付物

| 交付物 | 验收标准 |
|---|---|
| 播放记录采集 | 支持三种数据源，可配置切换 |
| **降级可见** | 取数失败与"确实没有数据"可区分；降级有指标与 UI 提示 |
| 播放记录查询 | 用户能看到自己的播放历史 |
| 观影报告 | 按时长、趋势、类型分布生成报告 |
| 排行榜 | 日榜 / 周榜 / 月榜 |
| 通知中心 | 站内通知与公告 |
| 前端用户中心 | 首页、播放、报告、个人中心四个页面 |
| 图片同源代理 | 带鉴权、带签名、解决混合内容 |

### 验收

- 未安装统计插件时，观影报告模块**整体降级隐藏**而不是显示 0
- 媒体服务器不可达时，页面显示明确的降级提示而非"暂无数据"

### 风险

| 风险 | 缓解 |
|---|---|
| 播放记录全量拉取导致内存爆掉 | 只做**分页增量**，首次建库分批导入；绝不全量扫 |
| 统计口径不一致 | 明确一个口径（播放时长以服务端上报为准）并写进文档 |

---

## 5. M3 · 求片闭环 ★

**周期**：4 周
**目标**：求片能自动走完全程。**这一步做完即超越竞品**（六个项目零个做到）。

### 交付物

| 交付物 | 验收标准 |
|---|---|
| 求片工单 | 提交、列表、详情、撤销、顶帖 |
| **状态机** | 至少覆盖 queued → searching → selected → acquiring → transferring → waiting_ingest → completed，以及 failed / no_resource / waiting_auth / waiting_manual |
| **步骤流水** | 每一步落库，用户能看到真实进度 |
| `request.search.provide` | 多源并发搜索、结果合并、择优 |
| **入库自动回流** | 媒体服务器 webhook → 匹配工单 → 自动置完成 → 通知用户 |
| 未匹配事件记录 | 匹配失败不静默丢弃，落库待查 |
| 积分联动 | 提交扣分、撤销返还 |
| `internal/provider/moviepilot`（L3） | 通过进程外 RPC 调用 MoviePilot 完成下载 |
| 下载器插件 | qBittorrent 至少一个 |

### 验收

通过 [11-测试计划](11-测试计划.md) §5.2 的**求片全流程**（11 步）。

关键断言：
- 入库 webhook 触发后，工单**自动**置完成，无需人工
- 步骤流水完整可回溯
- 匹配失败的事件被记录而不是静默丢弃

### 风险

| 风险 | 缓解 |
|---|---|
| MoviePilot API 返回值语义不统一 | 明确契约；HTTP 200 但业务失败的返回也要识别；提供人工补偿入口 |
| 外部下载器状态回传延迟大 | 状态机**超时自动降级**到待人工，而不是无限等待 |
| L3 插件协议未定 | **这是 M0 就要预留接口的决策项**（见 [13-技术决策](13-技术决策.md)） |

---

## 6. M4 · 运营变现 ★

**周期**：4 周
**目标**：能收钱、能分级、能对账。

### 交付物

| 交付物 | 验收标准 |
|---|---|
| 权益档位 | 多档并行，独立到期，可升级降级 |
| **粒度授权** | 按档位控制：片库、线路、下载、转码、并发、家长分级 |
| 套餐与订单 | 订单快照不可变；进度可查 |
| 支付接入 | 至少一个渠道；**回调幂等**（四态状态机） |
| **卡密批次** | 批次、类型、有效期、上限、作废、生成记录 |
| **积分账本** | 全量流水 + 余额可重算 + 对账任务 |
| 积分规则可配 | 后台可改，不需改代码 |
| **邀请关系树** | 记录层级与来源，支持统计 |
| 公告与工单 | 公告已读回执；用户与管理员双向沟通 |
| 积分与体验交互 | 签到、免费顶帖、撤销返还 |

### 验收

通过 [11-测试计划](11-测试计划.md) §5.3 的**卡密全流程**（9 步）。

关键断言：
- 并发兑换同一卡密只成功一次
- 支付回调重复投递不重复发放权益
- 积分余额永远不为负，且可由流水重算复核
- 卡密有批次、有效期、可作废

### 风险

| 风险 | 缓解 |
|---|---|
| 支付渠道差异大 | 抽象 `PaymentProvider` 能力；首个渠道先做透，不并行铺开 |
| 积分经济失衡（竞品实测有净通胀案例） | 提供**对账与模拟**工具：能算出"当前规则下系统每天净发多少分" |

## 7. M5 · 运维网络 ★

**周期**：4 周
**目标**：把网络层收进来，替代第三套系统。

### 交付物

| 交付物 | 验收标准 |
|---|---|
| 反向代理 | 路径分流、流式转发、图片缓存、限速计量 |
| **WebSocket 隧道** | 手工 Hijack + 强制校验升级头，不接受裸通道 |
| **持续状态探活** | 线路状态是持续对象（成功率、延迟分位、失败原因、冷却），参与调度 |
| **流量配额** | 预留-结算协议 + 周期代际号 |
| 多入口模式 | 按域名 / 路径 / 端口分流 |
| 证书自动化 | DNS-01 泛域名申请与续期 |
| 出站安全 | 统一 `ValidateOutboundURL`，DNS pinning，重定向逐跳校验 |
| 备份恢复 | 加密备份 + 带回滚的恢复协议 |
| 可观测 | 指标端点、降级计数器、健康探针 |

### 验收

- 线路状态在后台持续可见（滑动窗口），且**真的影响调度**
- 媒体服务器不可达时，流量自动切换到健康线路，且切换事件有记录
- 配额不会被并发请求突破

### 风险

| 风险 | 缓解 |
|---|---|
| 反代本身是高风险面（SSRF、请求走私） | 目标地址白名单；逐跳校验；升级头严格校验 |
| 流量计费影响性能 | 计量在 write 回调里做，不做额外拷贝 |

---

## 8. M6 · 生态开放 ★

**周期**：4 周
**目标**：别人能写插件。**这是护城河。**

### 交付物

| 交付物 | 验收标准 |
|---|---|
| **L0 声明式插件** | 一份 YAML 完成配置项、事件订阅、路由注册；加载失败有明确报错 |
| **L1 脚本插件** | 事件钩子里可写脚本；沙箱受限（无文件、无进程、无任意网络） |
| UI Schema 渲染器 | 前端能渲染插件提供的页面定义 |
| 插件市场 | 索引、安装、升级、回滚；三级信任 |
| 插件数据隔离 | 表名前缀强制；卸载可精确清理；PG 下独立 schema |
| **文档站** | 快速开始、插件开发指南、事件目录、示例插件集 |
| 示例插件 | 至少 5 个可用的 L0/L1 插件 |
| 脚手架 | `embyone plugin init` 生成骨架；`dev` 热重载；`audit` 权限审计 |

### 验收

**一个新人在 30 分钟内写出并跑通第一个插件。** 这是唯一标准。

### 风险

| 风险 | 缓解 |
|---|---|
| 脚本沙箱逃逸 | 用成熟引擎；限制能力而非限制语法；L1 只给受限 ctx |
| 插件市场审核成本高 | 先做官方 + 私有源，社区源后置 |
| 文档跟不上实现 | **事件目录从代码自动生成**，这是硬约束 |

## 9. M7 · 差异化

**周期**：持续
**目标**：建不可复制的壁垒。

| 方向 | 内容 | 为什么别人抄不走 |
|---|---|---|
| **行为风控** | 基于播放行为基线识别自动化工具，分级处置 | 需要**同时站在运营端和风控端**，而这两侧的工具生态目前互不相通 |
| **多租户** | 一套程序服务多个独立站点 | 全生态空白；且需要近乎所有表结构配合，后做代价极大 |
| **AI Agent** | 插件能力注册为 LLM 工具；智能识别、自动补货、自然语言运维 | 需要插件生态成熟 |
| **官方保活** | 用户无需第三方工具即可维持账号活跃 | 与行为风控互补：**有了正规渠道，第三方工具就失去动机** |

## 10. 里程碑依赖

```
M0 ──┬── M1 ──┬── M2 ──┐
     │        │        ├── M5
     │        └── M3 ──┤
     │                 └── M4 ── M6 ── M7
     └────────────────────────────────┘
              （M0 定的接口影响全局）
```

**M0 的接口决策会锁住后面所有阶段**，因此 M0 阶段必须把三个待定项（脚本引擎、L3 协议、多租户粒度）定下来。

---

## 11. 全局风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 范围蔓延导致长期做不完 | 高 | 每个里程碑都有明确验收；**不通过不开下一个** |
| 内核抽象过度 | 高 | 抽象必须有当前用例；新抽象进评审 |
| 外部系统（Emby/MoviePilot）API 变动 | 中 | 能力抽象隔离；适配层单独可测 |
| 三大决策（脚本引擎/协议/租户）后改代价大 | 高 | M0 必须先定；接口预留可替换 |
| 单人项目精力分散 | 中 | 按里程碑推进，不并行铺开 |
| 竞品快速跟进 | 低 | 护城河在插件生态与行为风控，不是功能数量 |

---

## 12. 待确认事项

- 【待定】是否需要在 M1 就提供迁移工具（从现有系统导入用户）——影响真实用户的迁移成本
- 【待定】M2 与 M3 是否真的并行（单人项目并行可能反而更慢）
- 【待定】M4 的支付渠道优先做哪个（Stripe 面向海外，国内需要易支付类）
