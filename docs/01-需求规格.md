# EmbyOne 设计文档 · 01 需求规格

> 这份文档回答三个问题：**要做什么、优先级是什么、怎么算做完了。**
> 每一条需求都有编号、验收标准与来源依据，便于逐条核对。

---

## 1. 优先级定义

| 级别 | 含义 | 判断标准 |
|---|---|---|
| **P0** | 基线 | 不做就没法用。竞品实测中「两个独立项目都各自实现了一遍」的功能都属此列 |
| **P1** | 运营 | 不做能用，但赚不到钱或留不住人 |
| **P2** | 差异化 | 做了才能赢，现有开源基本空白 |
| **P3** | 护城河 | 长期壁垒，别人抄不走 |

## 2. 用户角色

| 角色 | 描述 | 主要诉求 |
|---|---|---|
| **站主** | 部署并运营整个服务的人，通常也是唯一的技术负责人 | 少装软件、少改配置、出事能查、能赚钱 |
| **管理员** | 被站主授权的运营人员，可能多人 | 开号、续费、改权限、处理工单，不求人 |
| **付费用户** | 已经付过钱的人 | 别卡、别掉线、求片有反馈、到期有提醒 |
| **试用用户** | 还在体验期的人 | 快速上手，知道能看什么 |
| **访客** | 未登录的陌生人 | 知道这是什么、怎么加入 |

## 3. 功能需求

编号规则：`FR-<域>-<三位序号>`。「来源」列指向竞品分析中的事实依据。

### 3.1 身份与账号 `FR-AUTH`

| FR-USER-005 | P0 | 到期自动封禁 | 定时任务扫描到期用户 → 远端禁用 → 本地状态变更 → 通知用户 | G1 |
| FR-USER-006 | P0 | 手动启停 | 管理员可封禁/解封，操作带原因，记审计 | G1 |
| FR-USER-007 | P1 | **分级权益** | 支持多档会员，每档独立到期时间；升级/降级/叠加不互相覆盖 | G1（ember 唯一做对的） |
| FR-USER-008 | P1 | **粒度授权** | 按等级控制：可见片库、可用线路、能否下载、能否转码、并发数、家长分级 | G0（商业系统实证） |
| FR-USER-009 | P1 | 延长与续期 | 支持「延长 N 天」「指定到期日」「设为永久」三种操作；已过期从当前时间起算 | G1 |
| FR-USER-010 | P1 | 批量操作 | 批量续期、批量封禁、批量重置密码、批量同步权限 | G3 |
| FR-USER-011 | P2 | 邀请关系树 | 记录谁邀请了谁；支持连带处理与层级统计 | G1（**评为"最普遍的功能债"**） |
| FR-USER-012 | P2 | 配对账号 | 一个用户绑定多个身份，可一键切换 | G0（商业系统独有） |

| FR-USER-014 | P2 | 签到 | 每日签到获得积分；有连签奖励机制 | G1 / G2 |

## 4. 非功能需求 `NFR`

| 编号 | 需求 | 验收标准 |
|---|---|---|
| NFR-001 | **单二进制交付** | 一个可执行文件 + 一个数据库文件即可运行；前端资源内嵌，无需 Node 环境 |
| NFR-002 | **零外部依赖启动** | 默认使用 SQLite 与内存状态；不需要 Redis、不在启动时联网 |
| NFR-003 | 启动时间 | 冷启动（含迁移）< 3 秒 |
| NFR-004 | 内存占用 | 空闲时 < 100 MB |
| NFR-005 | 并发能力 | 单实例支撑 1000 用户、100 并发播放会话的管理操作 |
| NFR-006 | **降级可见性** | 任何取数失败都产生可观测的降级事件；不存在"静默返回空"的代码路径 |
| NFR-007 | **幂等性** | 所有对外的写操作支持重复执行不产生副作用（尤其是扣费与发码） |
| NFR-008 | 数据一致性 | 远端操作（建号、改权限）与本地事务不做强绑定；失败进补偿队列 |
| NFR-009 | 可审计性 | 所有状态变更、权限变更、资金变动可追溯到人、时间、原因 |
| NFR-010 | **可理解性** | 新人读事件目录即可了解系统全部扩展点；功能域代码集中在单一目录，单个入口文件 < 200 行 |
| NFR-011 | 可测试性 | 核心逻辑有单元测试；关键流程有集成测试；测试不需要外部服务 |
| NFR-012 | 向后兼容 | 数据库迁移只前进、不破坏；API 变更走弃用周期而非直接替换 |
| NFR-013 | 安全基线 | 无默认密码、无默认密钥；敏感配置加密存储；出站请求经统一校验器 |
| NFR-014 | 时区正确 | 所有日期边界（到期、周期、签到）共用同一业务时区配置 |

## 5. 需求追溯

每一条需求都能追到竞品分析中的具体事实或明确的设计选择：

| 需求簇 | 主要来源 | 关键证据 |
|---|---|---|
| FR-USER-001/002/003 | G1 | ember 用 4 个 bool 拼状态、Twilight 用 Role int，两者都缺"待审批"档 |
| FR-USER-007/008 | G1 + G0 | Twilight 只有全局硬编码黑名单，卖不出差价；商业系统有完整粒度授权字段 |
| FR-REQ-002/003 | G0 + G4 | 商业系统有 11 状态机；六个开源项目零个做到自动推进 |
| FR-BILL-002/003 | G2 | sakura 用字符串子串判断卡密类型；三家都没有积分账本 |
| FR-MEDIA-004/005 | G3 + G4 | emby-pulse 的 `except: pass` 让故障表现为"暂无数据" |
| FR-OPS-005 | G3 | Meridian 的延迟只存在于手点测速的瞬间，不落库不参与调度 |
| FR-OPS-003 | G3 | 三个项目全部假设单实例，只有 bubble 把它显式化 |
| FR-USER-015 | G2 | keeper 类工具的伪造特征可被行为基线识别；无人同时持两端 |
| FR-PLUGIN-* | G5 + G1 | MoviePilot 插件系统 7159 行过重；Twilight 的 JS 沙箱是止损不是隔离 |

## 6. 明确不做

| 不做 | 理由 |
|---|---|
| 自己实现下载与整理 | 这是 MoviePilot 多年积累的领域，通过 L3 插件调用 |
| 自己做媒体服务器 | 价值在客户端生态，对接而非重写 |
| 内置资源站 | 法律风险 + 站点地址频繁变化，必须用户自配 |
| 破解媒体服务器授权 | 只做运营层 |
| 兼容 MoviePilot 的 Python 插件 | 会把"插件包管理"这套重家伙搬进来，与轻量内核目标冲突。**改用 L3 进程外调用它的能力** |
