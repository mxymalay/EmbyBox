# EmbyBox 设计文档 · 09 开发规范

> 目标不是"规范得多严格"，而是**让新人在不看源码的情况下能猜到代码在哪**。

---

## 1. 目录约定

```
embybox/
├─ cmd/embybox/main.go          # 唯一入口（规划中，尚未实现）
├─ pkg/kernel/                  # ★ 内核：零业务名词
│  ├─ contract/                 #   契约定义（接口）
│  ├─ registry/                 #   能力注册表
│  ├─ event/                    #   事件总线
│  ├─ plugin/                   #   插件清单、发现、权限
│  ├─ assemble/                 #   装配器
│  ├─ config/                   #   启动期配置
│  ├─ store/                    #   存储与迁移
│  ├─ schedule/                 #   调度器
│  ├─ httpapi/                  #   HTTP 基础设施
│  └─ logx/                     #   日志
├─ internal/                    # ★ 业务：不出这个模块
│  ├─ plugin/                   #   内置插件（L2）
│  │  └─ identity/              #   一个功能域一个目录
│  │     ├─ plugin.go           #     注册（能力/事件/路由/迁移）—— 入口，< 200 行
│  │     ├─ service.go          #     业务逻辑
│  │     ├─ repo.go             #     数据访问
│  │     ├─ model.go            #     数据模型
│  │     ├─ api.go              #     HTTP handler
│  │     ├─ hook.go             #     事件处理
│  │     └─ migrations/         #     本域迁移
│  └─ provider/                 #   提供者插件（L1/L3）
│     └─ emby/
├─ web/                         # 前端
├─ migrations/                  # 内核迁移
├─ plugins/                     # 社区插件（L0/L1）
└─ docs/                        # 设计文档
```

### 铁律

**一、`pkg/kernel/` 里不允许出现业务名词。**
不出现 "emby"、"user"、"points"、"request"。判断方法：把内核单独编译，应该能在任何领域复用。

**二、`internal/` 不出模块。**
Go 的 `internal` 语义保证外部无法 import。防止别人依赖你的内部结构，也方便重构。

**三、一个功能域一个目录，入口文件 < 200 行。**
想知道"身份系统有哪些能力"，读 `identity/plugin.go` 就够了。这是「便于理解」的硬指标，评审时会被检查。

**四、依赖方向单向。**
```
cmd → internal → pkg/kernel
```
反向依赖（内核 import 业务）是不可接受的。插件依赖内核的其他包也有约束：**插件只应 import `contract` / `event` / `logx`**，其他能力从 `plugin.Env` 取。

## 2. 命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| 包名 | 小写单词，不用下划线 | `httpapi`、`registry` |
| 文件名 | 小写下划线 | `user_service.go` |
| 导出类型 | PascalCase | `MediaServer` |
| 非导出 | camelCase | `buildEnv` |
| 接口 | 名词或 `-er` 后缀 | `Notifier`、`Authenticator` |
| 错误变量 | `Err` 前缀 | `ErrNotFound` |
| 常量 | PascalCase | `KindMediaServer` |
| 测试文件 | `_test.go` | `store_test.go` |

### 接口命名

**按业务语义命名，不按实现命名。**

```go
// ❌ 按实现命名 —— 会绑死到具体系统
type EmbyClient interface { ... }

// ✅ 按业务语义命名 —— 任何媒体服务器都能实现
type MediaServer interface { ... }
```

## 3. 代码风格

### 3.1 通用

- 遵循 `gofmt` / `goimports`，提交前必须跑
- 开启 `go vet`，CI 阻断
- 行宽不强制，但**函数不超过 60 行**，超过就拆
- 圈复杂度 > 10 的函数需要评审时说明理由

### 3.2 注释

**注释写"为什么"，不写"是什么"。**

```go
// ❌ 复述代码
// 遍历用户列表
for _, u := range users {

// ✅ 说明原因
// 这里必须倒序遍历：删除元素时正序会导致索引错位，
// 而这个 bug 在用户数少于 2 时不会暴露。
for i := len(users) - 1; i >= 0; i-- {
```

**导出符号必须有文档注释**，格式为 `// Name 做什么。`。

**每个包必须有包注释**，说明这个包的职责与边界。

### 3.3 错误处理

```go
// ✅ 包装错误，保留调用链
if err != nil {
    return fmt.Errorf("创建用户失败: %w", err)
}

// ❌ 吞掉错误
if err != nil {
    return nil
}

// ❌ 只打印不返回
if err != nil {
    log.Error(err)
}
```

**用哨兵错误 + `errors.Is` 表达可预期的失败**：

```go
// 契约层定义
var ErrNotFound = errors.New("contract: not found")

// 调用方判断
if errors.Is(err, contract.ErrNotFound) {
    // 走"记录不存在"的分支，而不是当成故障
}
```

**不允许解析错误字符串做分支判断。**

### 3.4 panic

**只在"程序无法继续且这是编程错误"时 panic**，例如启动期配置非法。

**运行期的请求处理绝不允许 panic 逃逸**——HTTP 中间件有 recover，但插件调用、任务执行也要各自 recover。竞品实测中有项目的定时任务 panic 会导致整个调度器停摆。

## 4. 日志规范

### 4.1 结构化，不拼字符串

```go
// ✅
log.Info("用户创建成功", "user_id", u.ID, "emby_user_id", u.EmbyID, "plugin", "identity")

// ❌
log.Info(fmt.Sprintf("用户 %s 创建成功，emby id = %s", u.ID, u.EmbyID))
```

### 4.2 级别使用

| 级别 | 用途 |
|---|---|
| `Debug` | 排障细节，生产默认关闭 |
| `Info` | 状态变化、启动停止、关键业务动作 |
| `Warn` | 可恢复的异常、降级、配置可疑 |
| `Error` | 需要人介入的失败 |

**判断标准**：如果这条日志在生产环境每天出现超过 100 次，它就不是 `Error`。

### 4.3 禁止

- 记录密码、Token、API Key、完整信用卡号
- 记录完整请求体（可能含机密）
- 在循环里打日志（会淹没日志）

### 4.4 降级必须打日志

```go
// 任何降级路径都要有痕迹
log.Warn("播放统计插件不可用，降级为原生聚合端点",
    "err", err, "fallback", "native_aggregate", "user_id", userID)
```

配合 `media.server.degraded` 事件，让降级在指标里可见。

## 5. 数据库规范

| 规则 | 说明 |
|---|---|
| 表结构由迁移文件定义 | 不用 ORM 自动建表 |
| 迁移只前进 | 已发布的不修改 |
| 全部参数化查询 | 无例外 |
| 多步骤写操作必须事务 | `store.InTx` |
| 状态流转用条件更新 | `UPDATE ... WHERE status = ?` 判断影响行数 |
| 时间存 UTC | 展示时转 |
| 金额存整数分 | 不用浮点 |
| 索引覆盖高频查询 | 新查询先在文档 §12 的索引表里核对 |

### 并发安全的三条硬规则

```go
// ❌ 读-改-写：并发下必然出错
balance := getBalance(userID)
setBalance(userID, balance - cost)     

// ✅ 条件更新
res := db.Exec("UPDATE users SET points = points - ? WHERE id = ? AND points >= ?", cost, userID, cost)
if res.RowsAffected() == 0 { return ErrInsufficientPoints }

// ✅ 或事务 + 行锁
db.InTx(ctx, func(tx *sql.Tx) error {
    // SELECT ... FOR UPDATE (PG) / 串行写连接 (SQLite)
})
```

## 6. 测试要求

### 6.1 分层

| 层 | 覆盖目标 | 要求 |
|---|---|---|
| 单元测试 | 纯函数、业务逻辑 | 核心逻辑覆盖率 ≥ 70% |
| 集成测试 | 数据库交互、HTTP 接口 | 关键路径必须覆盖 |
| 端到端 | 完整流程 | 至少覆盖"注册 → 建号 → 到期 → 封禁" |

### 6.2 规则

- **测试不使用外部服务**。媒体服务器、支付、通知全部用 mock 或内存实现
- **测试可重复**。不允许依赖执行顺序；每次跑用全新内存数据库
- **测试表名与生产一致**。用同一个迁移文件建表，避免"测试过了线上挂了"
- 时间相关的逻辑要可注入时钟，不直接调 `time.Now()`

### 6.3 必须写测试的地方

| 场景 | 原因 |
|---|---|
| 计费与积分 | 出错就是资金事故 |
| 卡密核销 | 并发超发是真实风险 |
| 状态机流转 | 状态错乱难以排查 |
| 权限判定 | 越权是安全问题 |
| 反枚举逻辑 | 细微差异就会泄露 |
| 迁移脚本 | 在已有数据的库上跑通才算过 |

## 7. Git 规范

### 7.1 提交信息

```
<类型>(<范围>): <简述>

<可选：为什么这么改，而不是改了什么>
```

| 类型 | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修复 |
| `refactor` | 重构（不改变行为） |
| `perf` | 性能 |
| `docs` | 文档 |
| `test` | 测试 |
| `chore` | 构建、依赖 |

示例：

```
feat(identity): 支持注册后人工审批

竞品实测中两个成熟项目都没有这一档，但规模上来后必须要有。
实现为 status=pending 状态，管理员放行后转 active。
```

### 7.2 分支

- `main` 始终可发布
- 功能分支 `feat/<简述>`
- 修复分支 `fix/<简述>`

### 7.3 不允许提交

`.env` / `*.db` / `data/` / 构建产物 / IDE 配置 / 任何真实凭据

## 8. 代码评审清单

评审者逐条核对。

### 架构一致性

- [ ] 新代码放在正确的目录（内核 vs 业务）
- [ ] 内核里没有出现业务名词
- [ ] 依赖方向正确（无反向依赖）
- [ ] 业务逻辑没有写进内核

### 正确性

- [ ] 并发下有保护（条件更新/事务/锁）
- [ ] 写操作幂等
- [ ] 错误被正确包装与传递
- [ ] 边界条件处理了（空列表、零值、超长输入）

### 安全

- [ ] 对照 [08-安全设计](08-安全设计.md) §11 的自查清单

### 可理解性

- [ ] 入口文件 < 200 行
- [ ] 函数 < 60 行
- [ ] 复杂逻辑有"为什么"的注释
- [ ] 新增能力/事件已登记到文档

### 可观测性

- [ ] 关键路径有日志
- [ ] 降级有告警
- [ ] 失败可定位（日志含足够上下文）

### 测试

- [ ] 核心逻辑有测试
- [ ] 测试不依赖外部服务
- [ ] 迁移在空库与有数据的库上都跑通

## 9. 依赖管理

### 引入新依赖的评审问题

1. 标准库能否实现？如果能，就不引
2. 这个库多久没更新了？
3. 它的依赖树多大？（会拖进来多少间接依赖）
4. 它有没有已知 CVE？
5. 能不能只引它的一小块功能？

### 当前依赖（刻意保持极少）

| 依赖 | 用途 | 为什么不用标准库 |
|---|---|---|
| `modernc.org/sqlite` | SQLite 驱动 | 标准库没有，且它是纯 Go（无 CGO，跨平台编译友好） |
| `gopkg.in/yaml.v3` | 解析插件清单 | 标准库没有 YAML |
| `golang.org/x/crypto` | bcrypt | 标准库没有 |

**明确拒绝引入**：

| 库类 | 拒绝理由 |
|---|---|
| Web 框架（Gin/Echo） | Go 1.22+ 的 `net/http` 已支持路由模式，"框架的魔法"损害可读性 |
| ORM（GORM/Ent） | 隐式行为不可审计；SQL 应显式可读 |
| 依赖注入框架 | 显式装配（`assemble` 包）比容器更易理解 |
| 日志库（zap/logrus） | `log/slog` 已够用 |
| 配置库（viper） | 环境变量 + 少量代码即可 |

**每引入一个依赖，都要在本表登记并说明理由。**

## 10. CI 检查项

提交时自动执行：

```
1. gofmt -l                    格式检查
2. go vet ./...                静态检查
3. golangci-lint               lint
4. go test ./... -race         测试（含竞态检测）
5. go build ./...              构建
6. 迁移在空库上跑通              scripts/test-migrations.sh
7. 文档链接检查                  scripts/check-docs.sh
8. 内核无业务名词检查            scripts/check-kernel-purity.sh
```

第 8 项是本项目特有的：扫描 `pkg/kernel/` 下的代码，出现业务关键词（`emby`、`jellyfin`、`user`、`points`、`order` 等）即失败。
