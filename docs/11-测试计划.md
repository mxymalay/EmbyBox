# EmbyOne 设计文档 · 11 测试计划

> 测试的目标不是"覆盖率好看"，而是**把竞品踩过的坑提前踩一遍**。
> 本文件中的用例大部分直接对应竞品实测中发现的具体缺陷。

---

## 1. 测试策略

### 1.1 三层

| 层 | 范围 | 运行速度 | 依赖 |
|---|---|---|---|
| **单元测试** | 纯函数、业务逻辑、状态机 | 毫秒级 | 无 |
| **集成测试** | 数据库读写、HTTP 接口、迁移、插件加载 | 秒级 | 内存数据库 |
| **端到端测试** | 完整业务流程 | 十秒级 | 内存数据库 + mock 外部服务 |

### 1.2 不以覆盖率作为目标

覆盖率是**参考指标**，不是验收标准。本项目的验收标准是：

1. [§4 列出的关键场景](#4-关键测试用例)全部通过
2. 计费、积分、卡密、权限四类逻辑有测试覆盖
3. 每个历史 bug 修复都补一个回归测试

### 1.3 铁律

**一、测试不依赖外部服务。**
媒体服务器、支付、通知、TMDB 全部用 mock 或内存实现。测试必须能在离线环境跑通。

**二、测试可重复。**
不依赖执行顺序；每个测试用全新的内存数据库（`file::memory:?cache=shared` 或临时文件）。

**三、测试用与生产一致的建表方式。**
用同一份迁移文件建表。不允许在测试里手写 `CREATE TABLE`——那样测的是另一套 schema。

**四、时间可注入。**
不直接调 `time.Now()`。到期判定、签到周期、冷却期这类逻辑必须能注入时钟，否则无法测边界。

## 4. 关键测试用例

### 4.1 并发类（最容易出事）

#### T-01 并发兑换同一张卡密

```go
func TestRedeemCode_Concurrent(t *testing.T) {
    // 一张只能使用 1 次的卡密
    code := createCode(t, maxUses: 1)

    var wg sync.WaitGroup
    var success int32
    for i := 0; i < 20; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            _, err := svc.Redeem(ctx, code.Code, userID)
            if err == nil {
                atomic.AddInt32(&success, 1)
            }
        }()
    }
    wg.Wait()

    // 断言：只能成功一次
    if success != 1 {
        t.Fatalf("期望 1 次成功，实际 %d 次 —— 存在超发", success)
    }
    // 断言：使用计数正确
    if got := getUsedCount(t, code.ID); got != 1 {
        t.Fatalf("used_count 期望 1，实际 %d", got)
    }
    // 断言：只产生一条兑换记录
    if n := countRedeemRecords(t, code.ID); n != 1 {
        t.Fatalf("兑换记录期望 1 条，实际 %d 条", n)
    }
}
```

**实现要点**：核销必须用条件更新，不能先查后改。

```sql
UPDATE redeem_codes
SET used_count = used_count + 1
WHERE id = ? AND used_count < max_uses AND status = 'active'
```

```go
func TestPoints_ConcurrentDeduct(t *testing.T) {
    givePoints(t, userID, 100)

    var ok, fail int32
    var wg sync.WaitGroup
    for i := 0; i < 20; i++ {   // 每次扣 10，共尝试扣 200

        t.Fatalf("余额期望 0，实际 %d", bal)
    }
}
```

#### T-05 幂等键

```go
func TestGrantEntitlement_Idempotent(t *testing.T) {
    opID := "op-" + uuid.NewString()

    e1, err := svc.Grant(ctx, userID, planID, 30, opID)
    require.NoError(t, err)

    // 用同一个幂等键重放
    e2, err := svc.Grant(ctx, userID, planID, 30, opID)
    require.NoError(t, err)          // 重放不应报错
    require.Equal(t, e1.ID, e2.ID)   // 应返回同一个结果

    // 关键断言：只发了一次
    require.Equal(t, 1, countEntitlements(t, userID, planID))
}
```

### 4.2 状态机类

#### T-06 过期用户能登录但不能播放

```go
func TestExpiredUser_CanLoginCannotPlay(t *testing.T) {
    u := createUser(t, withExpiry(time.Now().Add(-time.Hour)))

    // 1. 能登录
    resp := login(t, u.Username, u.Password)
    require.Equal(t, 200, resp.Code)

    // 2. 响应里标记为过期
    require.True(t, resp.Data.User.Expired)
    require.False(t, resp.Data.User.CanPlay)

    // 3. 能访问个人中心
    require.Equal(t, 200, get(t, "/api/v1/user/profile", token).Code)

    // 4. 不能访问需要播放权限的接口
    r := get(t, "/api/v1/user/playback/stream", token)
    require.Equal(t, 403, r.HTTPStatus)
    require.Equal(t, "expired", r.Data.Kind)

    // 5. 能访问续费接口
    require.Equal(t, 200, get(t, "/api/v1/user/entitlements", token).Code)
}
```

> 这条用例直接对应竞品缺陷：两个成熟项目都把"能否登录"与"能否播放"合成一个字段，导致过期用户连付钱入口都找不到。

#### T-08 求片入库自动完成 ★

```go
func TestRequest_AutoCompleteOnIngest(t *testing.T) {
    // 1. 用户求片
    req := submitRequest(t, userID, mediaType: "tv", tmdbID: "1399", season: 1)
    require.Equal(t, "queued", req.Status)

    // 2. 模拟后续步骤推进（实际由各 provider 插件完成）
    advanceTo(t, req.ID, "waiting_ingest")

    // 3. 模拟媒体服务器入库 webhook
    publishIngest(t, IngestData{
        TMDBID: "1399", MediaType: "tv", Season: 1, ItemID: "item-123",
    })

    // 4. 关键断言：工单自动完成
    got := getRequest(t, req.ID)
    require.Equal(t, "completed", got.Status)
    require.Equal(t, "item-123", got.MatchedItemID)

    // 5. 断言：步骤流水有记录
    steps := getSteps(t, req.ID)
    require.Equal(t, "completed", steps[len(steps)-1].Stage)

    // 6. 断言：用户收到通知
    require.Equal(t, 1, countNotifications(t, userID, "request_completed"))
}
```

### 4.3 安全类

#### T-13 账号枚举

```go
func TestLogin_NoUserEnumeration(t *testing.T) {
    existing := createUser(t, username: "alice", password: "correct-pass")

    r1 := loginRaw(t, "alice", "wrong-pass")      // 存在但密码错
    r2 := loginRaw(t, "nobody", "wrong-pass")     // 不存在

    require.Equal(t, r1.Message, r2.Message)
    require.Equal(t, r1.Data["kind"], r2.Data["kind"])

    require.InDelta(t, r1.Duration.Seconds(), r2.Duration.Seconds(), 0.05)
}
```

```go
func TestValidateOutboundURL(t *testing.T) {
    cases := []struct{ url string; wantErr bool }{
        {"http://example.com/a.jpg", false},
        {"https://api.tmdb.org/x", false},
        {"http://127.0.0.1:8080/admin", true},          // 回环
        {"http://169.254.169.254/latest/meta-data/", true}, // 云元数据
        {"http://10.0.0.5/internal", true},             // 私网

        {"http://example.com@evil.com/", true},         // 伪装
    }
    for _, c := range cases {
        _, err := ValidateOutboundURL(c.url, allowed)
        require.Equal(t, c.wantErr, err != nil, c.url)
    }
}
```

## 5. 端到端验收测试

### 5.1 用户生命周期全流程

```
1. 启动服务 → 自动建库、建管理员
2. 管理员登录
3. 创建会员档位："普通会员"（能看到 movie 片库）
4. 创建会员档位："VIP"（能看全部片库 + 可下载）
5. 创建一个用户 → 自动在 mock 媒体服务器建号
6. 断言：远端账号存在，且策略包含 movie 片库
7. 用户登录 → 看到自己的会员信息
8. 管理员把用户升到 VIP
9. 断言：远端策略被更新（包含全部片库 + 允许下载）
10. 把用户到期时间改到过去
11. 跑到期扫描任务
12. 断言：本地状态变 expired，远端被 disabled，用户收到通知
13. 用户仍然能登录 → 访问续费页面
14. 用户兑换一张续期卡密
15. 断言：权益恢复、远端被启用、能播放了
16. 断言：每一步都有审计日志
```

**这一条通过，M1 就算完成。**

### 5.2 求片全流程

```
1. 用户登录
2. 搜索"权力的游戏" → 返回 TMDB 结果
3. 提交第 1、2 季求片 → 扣积分 100
4. 断言：积分流水有两条记录，工单状态为 queued
5. mock 资源提供者返回 3 个候选
6. 内核择优选中 1 个 → 状态推进到 acquiring
7. mock 获取成功 → transferring
8. mock 入库 webhook 触发
9. 断言：工单自动置完成，用户收到通知
10. 断言：步骤流水完整（queued → searching → selected → acquiring → transferring → completed）
11. 用户尝试撤销已完成的工单 → 拒绝
```

**这一条通过，M3 就算完成。**

### 5.3 卡密全流程

```
1. 管理员生成 100 张续期卡密（批次 A）
2. 断言：返回 100 个码，批次统计正确
3. 用户兑换一张 → 权益到账
4. 同一用户再次兑换同一张码 → 拒绝（already_redeemed）
5. 另一用户兑换同一张码 → 拒绝（code_exhausted）
6. 管理员作废批次 A
7. 断言：批次内未使用的码状态变为 revoked
8. 第三用户尝试兑换已作废的码 → 拒绝（code_revoked）
9. 断言：所有操作有审计
```

**这一条通过，M4 的卡密部分就算完成。**

## 9. 缺陷回归约定

**每一个 bug 修复都必须附带一个能在修复前失败的测试。**

流程：
1. 先写测试，确认它复现了 bug（红）
2. 修代码
3. 测试通过（绿）
4. 提交时在信息里说明对应的场景编号（如 `fix(billing): 修复并发兑换超发 (T-01)`）

这条约定是防止"同一个 bug 修三次"的唯一有效手段。
