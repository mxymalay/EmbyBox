# EmbyBox 设计文档 · 03 数据库设计

> 动表结构之前必看。这份文档是表结构的**唯一真相**，

## 1. 设计原则

### 1.1 五条铁律

**一、表结构由 SQL 迁移文件定义，不用 ORM 自动建表。**
自动建表在开发期很爽，上线后是灾难：你不知道线上表结构到底是什么，也无法回滚。所有结构变更必须是一个带序号的迁移文件。

**二、迁移只前进，不改历史。**
`0001_init.sql` 一旦发布就不再修改。要改结构就加 `0002_xxx.sql`。修改已发布迁移会导致不同环境的结构不一致，而这种不一致极难排查。

**三、所有时间存 UTC，展示时转业务时区。**
存本地时间会在跨时区部署、夏令时边界、容器迁移时出一堆无法复现的 bug。业务时区只用在「今天是几号」这类计算上，且必须来自统一配置。

**四、资金与积分类数据只记流水，余额由流水推导。**
余额字段是缓存，流水才是真相。改余额必须同时写流水，两者对不上时以流水为准并告警。

**五、外键约束在 SQLite 下必须显式开启。**
`PRAGMA foreign_keys=ON`。这是 SQLite 的历史包袱，不开的话外键定义形同虚设。

### 1.2 命名约定

| 对象 | 约定 | 示例 |
|---|---|---|
| 表名 | 小写下划线，单数 | `user` 还是 `users`？→ **统一用复数**：`users` |
| 列名 | 小写下划线 | `created_at`、`emby_user_id` |
| 主键 | 统一叫 `id` | 字符串用 ULID，整数用自增 |
| 时间列 | 统一 `_at` 后缀，存 UTC 的 RFC3339 文本 | `created_at`、`expires_at` |
| 布尔列 | 统一 `is_` 或 `allow_` 前缀 | `is_active`、`allow_download` |
| 索引 | `idx_<表>_<列列表>` | `idx_users_status` |
| 唯一索引 | `uniq_<表>_<列列表>` | `uniq_users_username` |
| 外键 | `<单数表名>_id` | `user_id`、`server_id` |

**关于大小写**：用户名与邮箱的唯一性判断必须大小写不敏感。做法是在应用层统一 `lower()` 后比较，**并在数据库层建基于函数的唯一索引**兜底——只靠应用层判断在并发下会出重复账号。

### 1.3 表的前缀规则

| 来源 | 前缀 | 示例 | 说明 |
|---|---|---|---|
| 内核 | 无 | `jobs`、`audit_log`、`kv` | 横切关注点 |
| 内置插件 | 无 | `users`、`orders`、`requests` | 它们是系统本体，加前缀反而难读 |
| 第三方插件 | `plugin_<id转下划线>__` | `plugin_emby_sync__mapping` | 强制隔离，卸载可精确清理 |

### 1.4 类型约定（以 SQLite 为准，PostgreSQL 映射见 §6）

| 语义 | SQLite 类型 | 说明 |
|---|---|---|
| 主键（字符串） | `TEXT` | ULID，26 字符，含时间戳前缀，天然有序 |
| 主键（自增） | `INTEGER PRIMARY KEY AUTOINCREMENT` | 仅用于日志类表 |
| 布尔 | `INTEGER` | 0/1，配 `CHECK (col IN (0,1))` |
| 时间 | `TEXT` | RFC3339 UTC，如 `2026-10-05T10:12:33Z` |
| 金额 | `INTEGER` | **以分为单位存整数**，绝不用浮点 |
| 积分 | `INTEGER` | 整数 |
| JSON | `TEXT` | 应用层序列化，SQLite 支持 `json_extract()` 查询 |
| 枚举 | `TEXT` | 存字符串而非数字，可读性优先 |

**约束必须写进 DDL，不能只写在应用层**：SQLite 的 `INTEGER` 亲和性会接受 `2` 存进布尔列、`1.5` 存进金额列（第二轮 D01 实测）。因此布尔列一律带 `CHECK (col IN (0,1))`；金额/积分列一律带 `CHECK (typeof(col) = 'integer')` 与合法范围检查；积分 `delta` 只约束类型不约束符号（支出为负是合法值）。

**为什么主键用 ULID 而不是自增整数**：自增 ID 会泄露"你有多少用户"（注册一个账号看 ID 就知道了），而且在多实例或数据迁移时容易冲突。ULID 随机的后 80 位避免了枚举，前 48 位的时间戳让它在索引上仍然有序。

## 3. 内核域

### 3.1 `schema_migrations`

**用途**：记录已执行的迁移。没有它就无法判断"这个库是什么版本"。
**它也是插件迁移的唯一版本账本**：校验和与 DDL 同事务登记，内容漂移即拒绝启动；
插件迁移按 `owner` 区分登记在本表，**不依赖可关闭的审计表**（第二轮 D17）。

```sql
CREATE TABLE schema_migrations (
    owner      TEXT    NOT NULL,            -- 'kernel' 或插件 ID
    version    INTEGER NOT NULL,            -- owner 内的序号，严格递增（段位约定见 §11.1）
    name       TEXT    NOT NULL,
    checksum   TEXT    NOT NULL,            -- 迁移文件内容哈希；已执行迁移的 checksum 不匹配即拒绝启动
    applied_at TEXT    NOT NULL,
    PRIMARY KEY (owner, version)
);
```

### 3.2 `kv`

**用途**：有命名空间的键值存储。用于缓存、临时状态、插件自带的小数据。没有它，每个插件都要自己建一张 KV 表。

```sql
CREATE TABLE kv (
    namespace  TEXT NOT NULL,   -- 隔离命名空间，如插件 ID
    key        TEXT NOT NULL,
    value      TEXT NOT NULL,
    expires_at TEXT,            -- 可空；非空时到期即视为不存在
    updated_at TEXT NOT NULL,
    PRIMARY KEY (namespace, key)
);
CREATE INDEX idx_kv_expires ON kv (expires_at);
```

**注意**：不要把业务数据塞进 KV。KV 无法建立关系、无法索引特定字段，未来做统计时会很痛苦。它的定位是"不值得建表的碎数据"。

### 3.3 `settings`

**用途**：管理员可在后台修改的运行期配置。与启动期配置（环境变量）严格分开——**这里的值改了立即生效，不需要重启**。

```sql
CREATE TABLE settings (
    key         TEXT PRIMARY KEY NOT NULL,
    value       TEXT NOT NULL,
    value_type  TEXT NOT NULL DEFAULT 'string',  -- string|int|bool|json|secret
    description TEXT NOT NULL DEFAULT '',
    updated_by  TEXT NOT NULL DEFAULT '',
    updated_at  TEXT NOT NULL
);
```

**敏感值处理**：`value_type='secret'` 的项在写入前加密，读取时解密，接口返回时打码（只保留首尾各 2 字符）。

### 3.4 `audit_log`

**用途**：审计。谁在什么时候改了谁、结果如何。竞品普遍缺失这一层，导致多管理员场景下出了事查不出责任人。

```sql
CREATE TABLE audit_log (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    actor_type TEXT NOT NULL DEFAULT 'system',  -- system|user|admin|apikey|plugin
    actor_id   TEXT NOT NULL DEFAULT '',
    action     TEXT NOT NULL,                   -- 如 user.ban、order.refund
    target     TEXT NOT NULL DEFAULT '',        -- 如 user:<id>
    detail     TEXT NOT NULL DEFAULT '',        -- JSON，变更前后值
    ip         TEXT NOT NULL DEFAULT '',
    user_agent TEXT NOT NULL DEFAULT '',
    ok         INTEGER NOT NULL DEFAULT 1 CHECK (ok IN (0,1)),
    created_at TEXT NOT NULL
);
CREATE INDEX idx_audit_created ON audit_log (created_at DESC);
CREATE INDEX idx_audit_actor   ON audit_log (actor_type, actor_id, created_at DESC);
CREATE INDEX idx_audit_action  ON audit_log (action, created_at DESC);
```

**保留策略**：默认保留 180 天，由定时任务清理。清理动作本身也记审计。

### 3.5 `jobs` / `job_runs`

**用途**：调度器。用数据库租约队列而不是进程内 cron，原因是站长要能在后台改调度而不用重启，且多实例部署时同一任务只能跑一个。

```sql
CREATE TABLE jobs (
    id               TEXT PRIMARY KEY NOT NULL,       -- 如 "identity.expire-scan"
    plugin_id        TEXT NOT NULL DEFAULT 'kernel',
    name             TEXT NOT NULL DEFAULT '',
    schedule         TEXT NOT NULL,          -- "*/5 * * * *" 或 "@every 30m"
    singleton        INTEGER NOT NULL DEFAULT 1 CHECK (singleton IN (0,1)),
    enabled          INTEGER NOT NULL DEFAULT 1 CHECK (enabled IN (0,1)),
    timeout_secs     INTEGER NOT NULL DEFAULT 300,
    max_retries      INTEGER NOT NULL DEFAULT 0,
    params           TEXT NOT NULL DEFAULT '{}',  -- 运行期参数，含 dry_run
    next_run_at      TEXT,
    lease_owner      TEXT NOT NULL DEFAULT '',
    lease_until      TEXT,
    last_status      TEXT NOT NULL DEFAULT '',
    last_error       TEXT NOT NULL DEFAULT '',
    last_run_at      TEXT,
    last_duration_ms INTEGER NOT NULL DEFAULT 0,
    run_count        INTEGER NOT NULL DEFAULT 0,
    fail_count       INTEGER NOT NULL DEFAULT 0,
    created_at       TEXT NOT NULL,
    updated_at       TEXT NOT NULL
);
CREATE INDEX idx_jobs_next ON jobs (enabled, next_run_at);

CREATE TABLE job_runs (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    job_id      TEXT NOT NULL,
    started_at  TEXT NOT NULL,
    finished_at TEXT,
    status      TEXT NOT NULL DEFAULT 'running', -- running|success|failed|timeout
    duration_ms INTEGER NOT NULL DEFAULT 0,
    error       TEXT NOT NULL DEFAULT '',
    dry_run     INTEGER NOT NULL DEFAULT 0 CHECK (dry_run IN (0,1))
);
CREATE INDEX idx_job_runs_job ON job_runs (job_id, id DESC);
```

**租约机制**：抢占时执行 `UPDATE jobs SET lease_owner=?, lease_until=? WHERE id=? AND (lease_until IS NULL OR lease_until < now)`，根据影响行数判断是否抢到。这是多实例不重复执行的保证。

**`params.dry_run`**：任何会删数据或发钱的任务都必须支持空跑演练。

### 3.6 `instance_locks`

**用途**：需要独占运行的插件在启动期获取锁，拿不到就拒绝启动。

```sql
CREATE TABLE instance_locks (
    name        TEXT PRIMARY KEY NOT NULL,
    owner       TEXT NOT NULL,   -- hostname#pid
    acquired_at TEXT NOT NULL,
    expires_at  TEXT NOT NULL    -- 让进程被 kill 后锁能自动过期
);
```

**为什么必须启动期硬失败**：重复扣费、重复发码这类事故一旦发生就无法撤销。宁可第二个实例起不来，也不要它带着错误的假设跑起来。

### 3.7 `plugin_audit`

**用途**：插件能力调用的审计流水（http.outbound、kv 读写、事件收发等）。注意：**插件迁移的版本真相在 `schema_migrations`，不在本表**——本表是运营审计，可在设置中关闭记录（见 docs/02-系统架构.md 安全层），关闭只影响审计，不影响迁移账本（第二轮 D17）。

```sql
CREATE TABLE plugin_audit (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    plugin_id   TEXT NOT NULL,
    capability  TEXT NOT NULL,              -- http.outbound|kv.read|kv.write|db.migrate|event.publish|...
    subject     TEXT NOT NULL DEFAULT '',   -- 目标，如 URL、key、事件名
    ok          INTEGER NOT NULL DEFAULT 1 CHECK (ok IN (0,1)),
    detail      TEXT NOT NULL DEFAULT '',   -- JSON，请求摘要/错误
    created_at  TEXT NOT NULL
);
CREATE INDEX idx_plugin_audit_plugin ON plugin_audit (plugin_id, id DESC);
CREATE INDEX idx_plugin_audit_cap    ON plugin_audit (capability, created_at DESC);
```

**保留策略**：与 `audit_log` 相同，默认 180 天，由定时任务清理。

## 4. 身份域

### 4.1 `users` ★核心表

**用途**：系统的主体。**这张表的设计正确性决定了整个项目能否「卖得出差价」。**

```sql
CREATE TABLE users (
    id            TEXT PRIMARY KEY NOT NULL,            -- ULID
    username      TEXT NOT NULL,
    email         TEXT NOT NULL DEFAULT '',
    password_hash TEXT NOT NULL DEFAULT '',    -- bcrypt

    -- ── 状态机（★ 单一枚举 + 原因，不用多个布尔拼）──
    status        TEXT NOT NULL DEFAULT 'pending',
        -- pending   注册后待审批
        -- active    正常
        -- expired   已到期（能登录、不能播放）
        -- banned    被封禁（不能登录）
        -- deleted   已删除（软删除）
    status_reason TEXT NOT NULL DEFAULT '',
        -- manual | system:expiry | system:telegram_membership | system:invite_detach | system:payment
    status_changed_at TEXT,

    -- ── 两个正交能力位（★ 必须分开）──
    can_login     INTEGER NOT NULL DEFAULT 1 CHECK (can_login IN (0,1)),  -- 能否登录。过期用户 = 1，可以进来续费
    can_play      INTEGER NOT NULL DEFAULT 0 CHECK (can_play IN (0,1)),  -- 能否播放。过期用户 = 0
    remote_disabled INTEGER NOT NULL DEFAULT 0 CHECK (remote_disabled IN (0,1)),-- 远端媒体服务器的实际禁用状态（镜像）

    -- ── 远端身份 ──
    emby_user_id  TEXT,
    emby_username TEXT,

    -- ── 外部身份 ──
    telegram_id   TEXT,
    avatar_type   TEXT NOT NULL DEFAULT 'default',  -- default|builtin|upload
    avatar_value  TEXT NOT NULL DEFAULT '',

    -- ── 审计字段 ──
    auto_disabled INTEGER NOT NULL DEFAULT 0 CHECK (auto_disabled IN (0,1)),  -- ★ 是否由系统自动禁用。自动任务只恢复自己禁的号
    disabled_reason TEXT NOT NULL DEFAULT '',
    last_login_at TEXT,
    last_login_ip TEXT NOT NULL DEFAULT '',
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL,
    deleted_at    TEXT
);

-- 用户名唯一且大小写不敏感
CREATE UNIQUE INDEX uniq_users_username ON users (lower(username));
-- 邮箱唯一（空邮箱不参与唯一性约束，否则多个空邮箱会冲突）
CREATE UNIQUE INDEX uniq_users_email ON users (lower(email)) WHERE email != '';
-- 远端 ID 唯一
CREATE UNIQUE INDEX uniq_users_emby_id ON users (emby_user_id) WHERE emby_user_id IS NOT NULL;
CREATE UNIQUE INDEX uniq_users_telegram ON users (telegram_id) WHERE telegram_id IS NOT NULL;

CREATE INDEX idx_users_status   ON users (status, created_at DESC);
-- ★ 到期扫描走 user_entitlements 的 idx_entitlements_expire；此处原有一条 users(expires_at) 索引，但 users 无该列（迁移会报 no such column），已移除
```

**为什么 `can_login` 与 `can_play` 必须分开**：
这是竞品分析里最重要的一条结论。把两者合成一个字段，就永远无法表达「过期用户可以登录、可以进个人中心、可以付钱续费，但就是不能看片」。这是留存的关键路径。

**为什么需要 `auto_disabled`**：
自动对账任务（如"把已过期的号在 Emby 里禁用"）在恢复时必须是可逆的。如果它不知道"这个号是我禁的还是管理员手动禁的"，就会出现「管理员封了人，定时任务又给解封了」这种事故。

### 4.2 `user_identities`

**用途**：一个用户可绑定多种外部身份。把身份从 `users` 表里拆出来，是为了新增登录方式时不用改主表。

```sql
CREATE TABLE user_identities (
    id           TEXT PRIMARY KEY NOT NULL,
    user_id      TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    provider     TEXT NOT NULL,   -- emby|telegram|oidc|passkey|...
    external_id  TEXT NOT NULL,
    -- 该身份携带的元数据，如 OIDC 的 claims、Passkey 的公钥
    metadata     TEXT NOT NULL DEFAULT '{}',
    created_at   TEXT NOT NULL,
    last_used_at TEXT
);
CREATE UNIQUE INDEX uniq_identities_provider_ext ON user_identities (provider, external_id);
CREATE INDEX idx_identities_user ON user_identities (user_id);
```

### 4.3 `sessions`

**用途**：登录会话。

```sql
CREATE TABLE sessions (
    id          TEXT PRIMARY KEY NOT NULL,          -- ULID
    user_id     TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    -- 只存令牌的哈希，不存明文。数据库泄露时攻击者无法直接冒用会话
    token_hash  TEXT NOT NULL,
    -- 密码指纹：改密后所有旧会话立即失效，无需维护黑名单
    pwd_sig     TEXT NOT NULL DEFAULT '',
    ip          TEXT NOT NULL DEFAULT '',
    user_agent  TEXT NOT NULL DEFAULT '',
    created_at  TEXT NOT NULL,
    expires_at  TEXT NOT NULL,
    revoked_at  TEXT
);
CREATE UNIQUE INDEX uniq_sessions_token ON sessions (token_hash);
CREATE INDEX idx_sessions_user    ON sessions (user_id, expires_at DESC);
CREATE INDEX idx_sessions_expires ON sessions (expires_at);
```

**`pwd_sig` 的妙处**：会话里存一个密码哈希的指纹。验证时比对当前用户密码哈希的指纹，一致则会话有效。改密后指纹变了，所有旧会话自动失效——**不需要维护任何黑名单**。

### 4.4 `invites` / `invite_relations`

**用途**：邀请码与邀请关系树。

竞品分析把「邀请无关系树」列为该领域最普遍的功能债：有邀请配置，却没有"谁拉的谁"这个字段，导致无法做连带处理、返利与层级统计。

```sql
CREATE TABLE invites (
    id          TEXT PRIMARY KEY NOT NULL,
    code        TEXT NOT NULL,
    created_by  TEXT NOT NULL REFERENCES users(id),
    max_uses    INTEGER NOT NULL DEFAULT 1,
    used_count  INTEGER NOT NULL DEFAULT 0,
    expires_at  TEXT,
    note        TEXT NOT NULL DEFAULT '',
    created_at  TEXT NOT NULL
);
CREATE UNIQUE INDEX uniq_invites_code ON invites (code);

-- ★ 邀请关系树：这张表是竞品普遍缺失的
CREATE TABLE invite_relations (
    id          TEXT PRIMARY KEY NOT NULL,
    inviter_id  TEXT NOT NULL REFERENCES users(id),
    invitee_id  TEXT NOT NULL REFERENCES users(id),
    invite_id   TEXT REFERENCES invites(id),
    depth       INTEGER NOT NULL DEFAULT 1,   -- 层级，1 = 直接邀请
    root_id     TEXT NOT NULL,                -- 顶级邀请人，便于按树聚合
    created_at  TEXT NOT NULL
);
CREATE UNIQUE INDEX uniq_invite_relations_invitee ON invite_relations (invitee_id);
CREATE INDEX idx_invite_relations_inviter ON invite_relations (inviter_id, depth);
CREATE INDEX idx_invite_relations_root    ON invite_relations (root_id);
```

**`root_id` 的作用**：做"某条线带来的全部用户"统计时，不需要递归查询整棵树，一次索引扫描即可。

## 5. 权益域

### 5.1 `plan_groups` / `plans`

**用途**：会员档位与套餐。

```sql
CREATE TABLE plan_groups (
    id               TEXT PRIMARY KEY NOT NULL,
    name             TEXT NOT NULL,          -- 如 "普通会员" "VIP" "SVIP"
    description      TEXT NOT NULL DEFAULT '',
    -- 权益等级：数值大的优先。用户同时持有多档时，取等级最高的作为当前生效档
    entitlement_rank INTEGER NOT NULL DEFAULT 0,
    -- 该档位的权限模板（JSON），含片库、转码、下载、并发等
    policy_template  TEXT NOT NULL DEFAULT '{}',
    is_default       INTEGER NOT NULL DEFAULT 0 CHECK (is_default IN (0,1)),
    sort_order       INTEGER NOT NULL DEFAULT 0,
    created_at       TEXT NOT NULL,
    updated_at       TEXT NOT NULL
);

CREATE TABLE plans (
    id            TEXT PRIMARY KEY NOT NULL,
    plan_group_id TEXT NOT NULL REFERENCES plan_groups(id),
    name          TEXT NOT NULL,             -- 如 "VIP 月卡"
    duration_days INTEGER NOT NULL DEFAULT 30,  -- 0 表示永久
    price_cents   INTEGER NOT NULL DEFAULT 0 CHECK (typeof(price_cents) = 'integer' AND price_cents >= 0),   -- 以分为单位
    currency      TEXT NOT NULL DEFAULT 'CNY',
    -- ★ 权益快照模板：下单时复制进订单，之后改价改权益不影响历史订单
    benefits      TEXT NOT NULL DEFAULT '{}',
    is_active     INTEGER NOT NULL DEFAULT 1 CHECK (is_active IN (0,1)),
    sort_order    INTEGER NOT NULL DEFAULT 0,
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL
);
CREATE INDEX idx_plans_group ON plans (plan_group_id, is_active);
```

### 5.2 `user_entitlements`

**用途**：用户持有的权益，每档独立到期。这是「卖得出差价」的落地。

```sql
CREATE TABLE user_entitlements (
    id            TEXT PRIMARY KEY NOT NULL,
    user_id       TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    plan_group_id TEXT NOT NULL REFERENCES plan_groups(id),
    source        TEXT NOT NULL,     -- order|redeem|admin|trial|invite
    source_id     TEXT NOT NULL DEFAULT '',  -- 订单号/兑换码 ID
    starts_at     TEXT NOT NULL,
    expires_at    TEXT,              -- NULL 表示永久
    revoked_at    TEXT,
    is_active     INTEGER NOT NULL DEFAULT 1 CHECK (is_active IN (0,1)),
    created_at    TEXT NOT NULL
);
CREATE INDEX idx_entitlements_user   ON user_entitlements (user_id, is_active, expires_at);
CREATE INDEX idx_entitlements_expire ON user_entitlements (is_active, expires_at);
```

**为什么不把到期时间放在 `users` 表上**：
竞品用「用户行上的单个到期时间」表达会员，导致三个问题：无法同时持有两档会员、无法表达"升级后旧档还剩 10 天"、无法追溯"这个权益是哪来的"。

**当前生效档的判定**：取该用户所有满足 `is_active = 1 AND starts_at <= now AND (expires_at IS NULL OR expires_at > now) AND revoked_at IS NULL` 的权益中 `entitlement_rank` 最高的那个。四个条件缺一不可——只看 `is_active` 与 `expires_at` 会把「未来生效」与「已撤销」的权益算成当前生效。这是一个纯读操作，结果缓存在 `users` 上可以，但必须能从这张表重算。

### 5.3 `entitlement_events`

**用途**：权益变更流水。用于审计与"我的会员为什么少了三天"这类问题。

```sql
CREATE TABLE entitlement_events (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id         TEXT NOT NULL,
    entitlement_id  TEXT,
    action          TEXT NOT NULL,   -- grant|extend|revoke|expire|upgrade
    plan_group_id   TEXT,
    days_delta      INTEGER NOT NULL DEFAULT 0,
    expires_at_before TEXT,
    expires_at_after  TEXT,
    operator        TEXT NOT NULL DEFAULT 'system',
    operation_id    TEXT,            -- 幂等键：同一操作重放不会重复发放
    reason          TEXT NOT NULL DEFAULT '',
    created_at      TEXT NOT NULL
);
CREATE INDEX idx_ent_events_user ON entitlement_events (user_id, id DESC);
-- ★ 幂等：同一个 operation_id 只能成功一次
CREATE UNIQUE INDEX uniq_ent_events_op ON entitlement_events (operation_id) WHERE operation_id IS NOT NULL;
```

**`operation_id` 是这套设计的核心**：管理员点"延长 30 天"，浏览器超时后重试，如果没有幂等键，用户会白得 30 天。有了它，重复请求直接被唯一索引挡下。

### 6.2 `payment_events`（Webhook 幂等）

**用途**：接收第三方支付回调。这是最容易出事故的地方——回调可能重复、可能乱序、可能在我们处理到一半时崩溃。

```sql
CREATE TABLE payment_events (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    provider      TEXT NOT NULL,
    event_id      TEXT NOT NULL,       -- 第三方的事件 ID
    event_type    TEXT NOT NULL,
    payload       TEXT NOT NULL,
    -- ★ 四态而非简单的 bool
    status        TEXT NOT NULL DEFAULT 'received',
        -- received  已收到，尚未处理（或上次处理时崩溃了）
        -- processed 处理成功，且**已产生副作用** —— 真正的幂等态
        -- skipped   已判定为无需处理（如非目标事件类型）
        -- failed    处理失败，可重试
    attempts      INTEGER NOT NULL DEFAULT 0,
    last_error    TEXT NOT NULL DEFAULT '',
    received_at   TEXT NOT NULL,
    processed_at  TEXT
);
CREATE UNIQUE INDEX uniq_payment_events ON payment_events (provider, event_id);
```

**为什么不能用 `processed bool`**：
一个布尔值无法区分「已经处理完了」和「正在处理时崩溃了」。前者重放会导致重复发货，后者不重放会导致用户付了钱没到账。四态状态机让两者可辨。

### 6.3 卡密体系 `redeem_code_batches` / `redeem_codes` / `redeem_records`

**用途**：卡密。竞品在这里的实现普遍残缺——有项目用「字符串里有没有 Renew 这个词」判断卡密类型。

```sql
    used_count  INTEGER NOT NULL DEFAULT 0,

    revoked_by  TEXT NOT NULL DEFAULT '',

    created_by  TEXT NOT NULL,

);

CREATE TABLE redeem_codes (

CREATE TABLE redeem_records (
    id            TEXT PRIMARY KEY NOT NULL,

    code          TEXT NOT NULL,
    user_id       TEXT NOT NULL REFERENCES users(id),
    -- 兑换时的权益快照：之后改批次参数不影响已兑换的记录

    ip            TEXT NOT NULL DEFAULT '',

);
-- ★ 同一用户同一码只能兑换一次

CREATE INDEX idx_redeem_records_user ON redeem_records (user_id, created_at DESC);
```

**核销的原子性**：必须用 `UPDATE redeem_codes SET used_count = used_count + 1 WHERE id = ? AND used_count < max_uses AND status = 'active'`，根据影响行数判断成功。**读-改-写在并发下必然超发。**

### 6.4 `points_ledger` / `points_rules`

**用途**：积分账本。竞品普遍只有余额字段，导致积分无法对账、经济系统通胀无感。

## 8. 求片域

### 8.1 `requests` / `request_steps`

**用途**：求片工单。**状态机 + 步骤流水是这块的核心设计。**

竞品实测：六个项目零个做到"求片 → 入库 → 自动置完成"。关键就在于没有步骤流水，无从判断"现在走到哪了、该不该推进"。

```sql
CREATE TABLE requests (
    id            TEXT PRIMARY KEY NOT NULL,
    user_id       TEXT NOT NULL REFERENCES users(id),
    -- 媒体标识
    media_type    TEXT NOT NULL,        -- movie|tv
    tmdb_id       TEXT NOT NULL DEFAULT '',
    imdb_id       TEXT NOT NULL DEFAULT '',
    title         TEXT NOT NULL,
    year          TEXT NOT NULL DEFAULT '',
    season        INTEGER NOT NULL DEFAULT 0,   -- 0 = 电影或整剧
    episode       INTEGER NOT NULL DEFAULT 0,
    poster_url    TEXT NOT NULL DEFAULT '',
    -- 状态机
    status        TEXT NOT NULL DEFAULT 'queued',
        -- queued|searching|selected|acquiring|transferring|waiting_ingest|
        -- completed|failed|no_resource|waiting_auth|waiting_manual|cancelled
    status_message TEXT NOT NULL DEFAULT '',    -- 给用户看的人话
    -- 积分
    points_cost   INTEGER NOT NULL DEFAULT 0,
    points_refunded INTEGER NOT NULL DEFAULT 0,
    -- 处理
    admin_note    TEXT NOT NULL DEFAULT '',
    matched_item_id TEXT,               -- 入库后匹配到的媒体条目 ID
    -- 时间
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL,
    completed_at  TEXT
);
-- 去重：同一用户对同一媒体同一季**同一集**只能有一个未完成的求片（整季/整剧请求 episode = 0，与单集请求互不冲突）
CREATE UNIQUE INDEX uniq_requests_active
    ON requests (user_id, media_type, tmdb_id, season, episode)  -- ★ 必须含 episode，否则同季第二个单集请求会被唯一约束拒绝
    WHERE status NOT IN ('completed', 'failed', 'cancelled');
CREATE INDEX idx_requests_status ON requests (status, created_at);
CREATE INDEX idx_requests_user   ON requests (user_id, created_at DESC);
CREATE INDEX idx_requests_tmdb   ON requests (tmdb_id, media_type, season);

-- 步骤流水：每一次状态推进都留一条记录
CREATE TABLE request_steps (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    request_id  TEXT NOT NULL REFERENCES requests(id) ON DELETE CASCADE,
    stage       TEXT NOT NULL,          -- 与 status 对应
    status      TEXT NOT NULL,          -- started|success|failed|skipped
    detail      TEXT NOT NULL DEFAULT '',   -- 如"搜索到 12 个候选，选中 1 个"
    operator    TEXT NOT NULL DEFAULT 'system',
    started_at  TEXT NOT NULL,
    finished_at TEXT,
    duration_ms INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_request_steps ON request_steps (request_id, id);
```

**为什么步骤流水不可省**：
1. 用户看到的是"解锁中 → 转存中 → 等待入库"这样的真实进度，而不是笼统的"处理中"——这是竞品对比后最明显的体验差距
2. 排障时能看出具体卡在哪一步
3. 超时自动重试需要知道"这一步已经试了几次"

## 10. 运维域

### 10.1 `routes` / `route_stats`

**用途**：线路。**关键设计：线路状态是持续对象，而不是一次性快照。**

竞品实测：一个成熟的反代面板，延迟只存在于"管理员手点测速"的那一瞬间，既不落库也不参与调度。

```sql
CREATE TABLE routes (
    id            TEXT PRIMARY KEY NOT NULL,
    name          TEXT NOT NULL,
    kind          TEXT NOT NULL,        -- direct|proxy|relay
    target        TEXT NOT NULL,        -- 上游地址
    -- 权重与择优
    weight        INTEGER NOT NULL DEFAULT 100,
    priority      INTEGER NOT NULL DEFAULT 0,
    region        TEXT NOT NULL DEFAULT '',
    -- 权限：哪些等级可用
    required_plan_group TEXT,
    is_exclusive  INTEGER NOT NULL DEFAULT 0 CHECK (is_exclusive IN (0,1)),   -- 独占线路
    -- ★ 持续健康状态（滑动窗口的结果）
    health_status TEXT NOT NULL DEFAULT 'unknown',  -- healthy|degraded|down|unknown
    success_rate  REAL NOT NULL DEFAULT 0,      -- 最近 N 次探测成功率
    latency_p50_ms INTEGER NOT NULL DEFAULT 0,
    latency_p95_ms INTEGER NOT NULL DEFAULT 0,
    last_error    TEXT NOT NULL DEFAULT '',

    updated_at    TEXT NOT NULL
);
```

## 11. 迁移策略

### 11.1 版本号分配

| 范围 | 归属 |
|---|---|
| 1 - 999 | 内核 |
| 1000 - 8999 | 内置插件（按插件分配段位） |
| 9000+ | 第三方插件（每个插件用自己的子段） |

**当前已分配**：

| 插件 | 段位 |
|---|---|
| 内核 | 1-999 |
| identity | 1000-1099 |
| media | 1100-1199 |
| billing | 1200-1299 |
| request | 1300-1399 |
| ops | 1400-1499 |

**唯一性**：`schema_migrations` 主键为 `(owner, version)`，段位仅用于执行顺序与阅读；同一 owner 内 version 必须严格递增，已执行迁移的 checksum 不匹配即拒绝启动（第二轮 D17）。

### 11.2 迁移文件规范

```
migrations/
├─ 0001_kernel_base.sql
├─ 0002_kernel_audit.sql
├─ 0003_kernel_jobs.sql
├─ 0004_kernel_instance_locks.sql
└─ 1000_identity_users.sql
```

- 文件名：`<4位序号>_<描述>.sql`
- 一个迁移只做一件事
- **已发布的迁移文件不允许修改**，要改就加新文件
- 迁移必须在空库和已有数据的库上都能跑通
- 加列时必须给默认值，否则老数据会变成 NULL

### 11.3 向后兼容规则

| 操作 | 是否允许 | 做法 |
|---|---|---|
| 加表 | ✅ | 直接加 |
| 加列 | ✅ | 必须有默认值 |
| 加索引 | ✅ | 大表上用 `CREATE INDEX CONCURRENTLY`（PG） |
| 改列类型 | ⚠️ | 加新列 + 数据迁移 + 停用旧列，分三个版本完成 |
| 删列 | ❌ 立即删 | 先停用（代码不再读写），至少一个版本后再删 |
| 删表 | ❌ 立即删 | 先改名为 `_deprecated_<表>_<日期>`，观察一个版本 |

### 11.4 SQLite → PostgreSQL 的差异

| 方面 | SQLite | PostgreSQL |
|---|---|---|
| 占位符 | `?` | `$1 $2` |
| 自增 | `AUTOINCREMENT` | `GENERATED ALWAYS AS IDENTITY` |
| 布尔 | `INTEGER` 0/1 | `BOOLEAN` |
| JSON | `TEXT` + `json_extract()` | `JSONB` + `->>` |
| 部分索引 | 支持 | 支持 |
| 函数索引 | 支持 | 支持 |
| 并发写 | 串行 | 真并发 |
| 迁移事务 | 支持（例外仅 VACUUM / `PRAGMA journal_mode` / ATTACH；`PRAGMA foreign_keys` 在事务内为 no-op，须在事务外设置） | 支持 |

**代码侧的统一处理**：所有 SQL 用 `?` 占位符书写，由 `store.DB.Rebind()` 在运行期转成目标方言。这样业务代码不用关心底层是什么数据库。

## 12. 常见查询与索引覆盖

列出高频查询，确保索引能覆盖，避免上线后发现慢查询。

| 场景 | 查询 | 使用的索引 |
|---|---|---|
| 到期扫描（每 5 分钟） | `SELECT id FROM user_entitlements WHERE is_active=1 AND expires_at < ?` | `idx_entitlements_expire` |
| 用户列表（后台首页） | `SELECT * FROM users WHERE status=? ORDER BY created_at DESC LIMIT 20` | `idx_users_status` |
| 积分余额 | `SELECT balance_after FROM points_ledger WHERE user_id=? ORDER BY id DESC LIMIT 1` | `idx_points_user` |
| 求片队列（用户端） | `SELECT * FROM requests WHERE user_id=? ORDER BY created_at DESC` | `idx_requests_user` |
| 待处理求片（后台） | `SELECT * FROM requests WHERE status IN (...) ORDER BY created_at` | `idx_requests_status` |
| 入库匹配 | `SELECT * FROM requests WHERE tmdb_id=? AND media_type=? AND season=? AND status='waiting_ingest'` | `idx_requests_tmdb` |
| 播放排行 | `SELECT user_id, SUM(watch_seconds) FROM playback_daily WHERE date BETWEEN ? AND ? GROUP BY user_id ORDER BY 2 DESC LIMIT 10` | `idx_playback_daily_date` |
| 审计检索 | `SELECT * FROM audit_log WHERE actor_id=? ORDER BY created_at DESC LIMIT 50` | `idx_audit_actor` |
| 卡密校验 | `SELECT * FROM redeem_codes WHERE code=?` | `uniq_redeem_codes_code` |
| 批量开号判重 | `SELECT username FROM users WHERE lower(username) IN (...)` | `uniq_users_username` |
