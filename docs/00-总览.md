# EmbyBox 设计文档 · 00 总览

> 本文档是所有设计文档的入口。想知道"这个项目是什么、做到哪一步、文档在哪看"，从这一份开始。

---

## 1. 一句话定位

**EmbyBox 是一个插件化的 Emby / Jellyfin 媒体服务运营系统，用一个程序覆盖现有生态里需要部署五六套工具才能完成的事。**

"运营系统"这个词是刻意的。它不是播放器，不是下载器，也不是单纯的用户管理后台——它是把**用户、资源、运维、数据**四件事放在同一个内核里，用插件把它们串起来的那一层。

---

## 2. 为什么要做它

### 2.1 现状：六套互不相通的半成品

自己搭 Emby 服务的人（下称"服主"），实际部署长这样：

| 要解决的问题 | 现在用什么 | 换个说法 |
|---|---|---|
| 片子从哪来 | MoviePilot | 自动找资源、下载、整理、入库 |
| 谁能用、谁能看多久 | ember / Twilight | 开号、到期、续费、封号 |
| 用户怎么看进度 | emby-pulse | 数据大盘、观影报告 |
| 卡不卡、走哪条线 | Meridian | 反向代理、多线路调度 |
| 怎么自动保号 | emby-keeper | 假装看视频骗过系统 |
| 用户看什么网页 | 各家自建门户 | 求片、反馈、个人中心 |

这六类工具，**没有任何一个跨过两类的边界**。

后果是具体的：

- 装六个程序，配六套账号密码
- 在 A 里封了个用户，B 不知道，还在给他算数据
- 改一个设置要改六个地方
- 想开第二个站？整套再来一遍

### 2.2 差距清单：现有工具的共同短板

以下每条结论都来自实际阅读源码（见 [分析/](../分析/) 下的六份报告，全部带文件行号依据）：

**结构性的（改不动，只能重做）**

1. **没有统一的用户状态机。** 用户到底是"过期"还是"被封"还是"待审批"，系统自己说不清——两个最成熟的项目分别用「4 个布尔值」和「一个整数 + 若干标记」拼凑，两者都没有"注册后人工审批"这一档。
2. **卖不出差价。** 想实现"普通会员看一半片库、VIP 看全部"，做不到。其中一个项目甚至只有一份全局硬编码的黑名单，没有任何按等级授权的能力。
3. **求片与入库零闭环。** 实测六个项目，**零个**做到"求片 → 下载 → 入库 → 自动通知用户"。其中一个项目有全部零件却断在最后一步，还有个项目的通知链因为一个必然失败的 ID 匹配而静默失效。
4. **卡密停留在"一张表一个已用字段"。** 没有批次、没有有效期、没有作废、没有对账。有个项目判断卡密类型用的是「字符串里有没有 Renew 这个词」。
5. **积分没有账本。** 签到送分、消费扣分，但不记流水。有项目的经济系统实测是净通胀的，改价还要改代码。

**工程性的（能做对，但没人做）**

6. **测速是一次性的。** 点一下测一下，测完就忘，不落库、不参与调度。下次该走哪条线还是瞎猜。
7. **出错了不吭声。** 数据取不到就显示"暂无数据"，用户和管理员都不知道是真没有还是坏了。
8. **只能单机跑。** 想多开一个实例分担负载，会重复扣费、重复发码。
9. **拉人统计不了。** 有邀请配置，但数据库里没有"谁拉的谁"这个字段。
10. **没法扩展。** 十三个项目里只有一个有插件机制，而那个用的是"同进程里跑第三方 JS"这种等于没有隔离的方案。

### 2.3 一个没人占据的位置

这条是分析竞品时最意外的发现：

- **服主的工具**精通账号运营，但风控只做到"数一下这个用户开了几个会话"
- **白嫖者的工具**精通伪造播放行为，但完全不关心运营

而且——**其中一方的工具是专门逆向另一方的后台协议写出来的**。卖号侧和抢号侧已经形成了攻防对偶，两边的接触点却是几行写死的正则。

站在中间的那个人手里握着最厉害的东西：**行为基线**。服主知道正常人是怎么看片的——什么时候点播放、看多久、会不会拖进度条、用什么设备。所以他一眼就能看出谁是机器。

**现在没有任何一个系统同时站在两边。** 这既是能力空白，也是商业空白。

## 3. 我们做什么

### 3.1 一句话

**一个内核 + 四类插件，覆盖用户、资源、运维、数据。**

### 3.2 三个设计公理

这三条决定了后面所有取舍，先摆在最前面。

**公理一：人是核心，资源是能力。**
现有工具分成"管资源的"和"管人的"两派。EmbyBox 把用户当作一等公民，把"获取资源"当作一种**可插拔的能力**接进来——想接 MoviePilot 就接，想接 PT 站就接，想接网盘就接，换成什么都不影响用户体系。

**公理二：内核只做装配，业务全在插件。**
内核不允许出现任何业务名词。不出现 "Emby"、不出现 "积分"、不出现 "求片"。内核只认识三样东西：**契约、注册表、事件**。Emby 对接是插件，积分系统也是插件。

**公理三：复杂度必须分期支付。**
那个功能最全的竞品，光插件系统就写了七千多行——因为它第一版就解决了所有极端情况（插件要装依赖包、要处理版本代际兼容、要支持冻结运行模式）。我们用一个**四级插件模型**把复杂度摊开：九成的扩展需求只需要填一个配置文件。

### 3.3 四级插件模型

| 级别 | 形态 | 上手 | 能干什么 | 典型场景 |
|---|---|---|---|---|
| **L0** | 一个 YAML | 5 分钟 | 配置项、模板化事件响应、路由转发 | 加个通知渠道、接一个媒体服务器预设 |
| **L1** | YAML + JS | 30 分钟 | L0 全部 + 钩子里写逻辑、读写插件自带 KV | 字段转换、条件过滤、自定义消息 |
| **L2** | Go 源码 | 半天 | 全部能力 + 注册自带数据表 | 官方能力域、性能敏感路径 |
| **L3** | 任意语言 + RPC | 半天 | 全部能力（除自带表迁移） | 复用 Python 生态、爬虫、OCR |

**这是本项目的核心差异化。** 竞品要么没有插件机制，要么只有"写一个完整的类"这一条路。

## 4. 项目范围

### 4.1 MVP 做（M1 交付）

一个能真正用起来的最小闭环：

- 启动一个服务，自动建库、建管理员
- 管理员登录后台
- 管理员创建用户 → 自动在 Emby 建号 → 落库
- 用户登录用户中心 → 看到自己的信息
- 定时任务扫描到期 → 自动在 Emby 禁用该用户
- L0 声明式插件能被加载、校验、在后台可见

### 4.2 后续里程碑做

见 [12-路线图](12-路线图.md)。简表：

| 里程碑 | 内容 |
|---|---|
| M1 | 身份闭环（统一状态机、注册审批档位） |
| M2 | 自助门户（播放记录、观影报告） |
| M3 | 求片闭环（状态机 + 入库回流自动置完成） |
| M4 | 运营变现（分级权益、粒度授权、卡密批次、积分账本、邀请树） |
| M5 | 运维网络（反代、持续状态探活、流量配额、证书） |
| M6 | 生态开放（L0/L1 插件、插件市场、文档站） |
| M7 | 差异化（行为风控、多租户、AI Agent 工具暴露） |

### 4.3 明确不做

划清边界比列出功能更重要。

| 不做 | 理由 |
|---|---|
| **自己下载和整理片子** | 这是 MoviePilot 十年积累的活，通过 L3 插件调用它，而不是重写 |
| **自己当媒体服务器** | Emby / Jellyfin 的价值在播放器和客户端生态，我们只对接 |
| **做播放器** | 同上 |
| **内置影片资源站** | 版权与法律风险，且站点会变，必须由用户自己配置 |
| **支持盗版破解 Emby** | 本项目只做运营层，不碰媒体服务器的授权机制 |

## 5. 成功标准

怎么算做成了？不是"功能数量超过竞品"，而是这三条：

1. **一个人能在半小时内从零跑起一个可用的站**——不需要读源码、不需要装六套东西。
2. **新人能在三十分钟内写出第一个插件**——读事件目录，写一个 YAML，看到效果。
3. **站主的日常操作在一个界面里完成**——开号、续费、改权限、看数据、处理求片，不用切窗口。

## 7. 术语速查

完整的在 [14-附录](14-附录.md)，这里放最常用的几个。

| 词 | 意思 |
|---|---|
| **服主 / 站主** | 自己搭 Emby 服务并运营的人 |
| **内核（Kernel）** | 不含任何业务逻辑的骨架，只做装配 |
| **插件（Plugin）** | 提供功能或能力的扩展单元 |
| **能力（Capability）** | 内核认识的一类接口，如"媒体服务器""通知渠道" |
| **提供者（Provider）** | 某个能力的具体实现，如 Emby 是"媒体服务器"的一个提供者 |
| **契约（Contract）** | 接口定义，插件通过实现契约接入内核 |
| **生命周期** | 插件被加载（Register）→ 启动（Start）→ 停止（Stop）的过程 |
| **求片** | 用户请求某部影片入库 |
| **KTV / 线路** | 用户访问媒体服务器的不同网络入口 |

## 8. 文档约定

为保证这套文档能被机器审核、也便于人快速核对，全篇遵守以下约定：

- 所有结论必须可验证：涉及竞品的判断标注来源文件与行号
- 所有设计必须给出理由：不写"用 Go"而要写"用 Go，因为……"，被否的方案写在 [13-技术决策](13-技术决策.md)
- 所有接口必须有示例：请求与响应都给出可直接复制的样例
- 所有表结构必须有用途说明：每张表写清楚"没有它会怎样"
- 不确定的地方显式标注 `【待定】`，不写模糊表述
