## 1. 术语表

### 1.1 领域词

| 术语 | 英文 | 含义 |
|---|---|---|
| **站主 / 服主** | operator | 自己搭建并运营 Emby 服务的人。本项目的目标用户 |
| **Emby** | — | 一款媒体服务器软件，负责管理影片库并提供多端播放。同类产品还有 Jellyfin、Plex |
| **媒体服务器** | media server | 通称，本项目对其做了能力抽象，不绑定具体产品 |
| **求片** | media request | 用户请求把某部影片加入库 |
| **线路** | route / line | 用户访问媒体服务器的不同网络入口，用于分流与加速 |
| **反代** | reverse proxy | 反向代理。把用户请求转发到后端的媒体服务器 |
| **直链** | direct link | 网盘资源的直连播放地址 |
| **转存** | transfer | 把网盘上的资源保存到自己的网盘 |
| **保活** | keep-alive | 通过模拟播放行为维持账号活跃，避免被系统清理 |
| **卡密** | redeem code | 用于兑换会员时长或积分的凭证 |
| **顶帖** | bump | 提醒管理员处理求片，不创建新工单 |
| **配额** | quota | 资源使用上限，如求片次数、流量、并发数 |

### 1.2 本项目特有词

| 术语 | 含义 |
|---|---|
| **内核**（Kernel） | 不含任何业务逻辑的骨架。只做发现、排序、注册、鉴权、启动五件事 |
| **契约**（Contract） | 内核定义的接口。插件通过实现契约接入 |
| **能力**（Capability） | 内核认识的一类接口，如"媒体服务器""通知渠道" |
| **提供者**（Provider） | 某个能力的具体实现。如 Emby 是"媒体服务器"能力的一个提供者 |
| **插件**（Plugin） | 提供功能或能力的扩展单元 |
| **模块**（Module） | 能力提供者在旧术语里的叫法，与 Provider 同义 |
| **注册表**（Registry） | 内核记录"系统里有哪些能力"的地方 |
| **事件总线**（EventBus） | 插件间解耦协作的机制 |
| **装配**（Assemble） | 发现插件 → 排序 → 注册 → 鉴权 → 启动 的全过程 |
| **清单**（Manifest） | `plugin.yaml`，声明插件是什么、要什么权限、挂在哪里 |
| **扩展点** | 即事件类型。想知道系统能扩展什么，读事件目录 |
| **降级**（Degrade） | 依赖不可用时的降级行为。**必须可见**，不允许静默失败 |
| **权限清单** | 插件声明的能力授权列表。未声明的调用直接失败 |

### 1.3 四级插件模型

| 级别 | 形态 | 上手成本 | 能做什么 |
|---|---|---|---|
| **L0** | 一个 YAML | 5 分钟 | 配置项、模板化事件响应、路由转发 |
| **L1** | YAML + 脚本 | 30 分钟 | L0 全部 + 钩子里写逻辑 |
| **L2** | Go 源码 | 半天 | 全部能力 + 注册自带数据表 |
| **L3** | 任意语言 + RPC | 半天 | 全部能力（除自带表迁移） |

### 1.4 事件时机

| 时机 | 语义 | 订阅者能否改变流程 |
|---|---|---|
| `before` | 发生前 | ✅ 可改写数据、可中断 |
| `after` | 发生后 | ❌ 只记日志 |
| `check` | 校验点 | ✅ 可否决 |
| `provide` | 数据源征集 | ❌ 收集所有结果，单个失败不影响其他 |

## 2. 参考项目索引

本项目在设计前对 15 个生态内项目做了源码级分析。**这些项目没有被包含在本仓库中**（各自的 git 历史与许可证独立，体积合计 170 MB）。

用以下脚本拉取到本地：

```bash
./scripts/fetch-references.sh
```

拉取后目录结构：

```
参考项目/
├─ moviepilot/              资源自动化中枢
├─ ember/                   用户管理系统（最完整）
├─ twilight/                用户管理 + JS 扩展
├─ meridian/                反向代理与线路调度
├─ emby-pulse/              数据大盘与缺集补货
├─ bubble-emby-admin/       功能文档（100+ 功能点）
├─ sakura-embyboss/         TG 运营后台
├─ lemon-emby-bot/          群内快操作与经济系统
├─ emby-keeper/             自动签到保活（用户侧）
├─ embyforge/               多服务器管理
├─ emby-tools/              周边工具集
├─ emby-request-ui/         求片站
├─ emby-register-enhanced/  注册管理
├─ emby-manager-gaodong/    媒体门户
└─ usersvr/                 用户管理设想（无代码）
```

### 2.1 分析报告

每份报告都基于实际读源码，结论带 `文件:行号` 依据。

| 报告 | 对象 | 关键结论 |
|---|---|---|
| [需求全景](../分析/需求全景.md) | 汇总 | 分层需求、十大结构性缺陷、五个无人占位的机会点 |
| [G0 商业系统逆向](../分析/G0-实战样本-KiTi逆向.md) | 某在运营的付费站 | 真实付费需求快照：47 个端点、11 状态求片机、四级账号体系 |
| [G1 用户系统](../分析/G1-用户系统.md) | ember、twilight | **两者都没有统一状态机**；twilight 卖不出差价 |
| [G2 TG机器人](../分析/G2-TG机器人.md) | sakura、lemon、keeper | **卡密三家全缺批次/有效期/作废**；积分无账本；无人同时持有运营端与风控端 |
| [G3 运维面板](../分析/G3-运维面板.md) | meridian、emby-pulse、bubble | **探活是一次性快照**；失败被吞；三者能力几乎不重叠 |
| [G4 外围工具](../分析/G4-外围工具.md) | 六个项目 | **求片与入库零闭环**；报表数据源四条路线 |
| [G5 MoviePilot](../分析/G5-MoviePilot核心引擎.md) | moviepilot | 双层扩展模型值得借鉴；**插件系统 7159 行过重** |

## 6. 文档维护约定

| 约定 | 说明 |
|---|---|
| **单一真相** | 每份内容只在一处维护。事件目录从代码常量生成，表结构以 03 文档为准 |
| **结论可验证** | 涉及竞品的判断标注来源文件与行号 |
| **设计给理由** | 不写"用 Go"，而写"用 Go，因为……" |
| **接口给示例** | 请求与响应都给出可直接复制的样例 |
| **不确定就标注** | 写 `【待定】`，不写模糊表述 |
| **改了代码就改文档** | 文档更新纳入评审清单 |
