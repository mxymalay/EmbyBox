# EmbyBox 设计文档 · 13 技术决策记录（ADR）

> 记录每个关键选择的**理由与被否方案**。
>
> 只写"用了什么"的文档没有价值——半年后没人知道为什么，于是有人"顺手"改掉，然后踩回同一个坑。

---

## 格式说明

每条决策包含：

- **状态**：已定 / 待定 / 已废弃
- **背景**：面临什么问题
- **决策**：选了什么
- **理由**：为什么
- **被否方案**：考虑过什么，为什么不选
- **影响**：这个决策会约束什么

## ADR-001 · 后端语言选 Go

**状态**：已定

**背景**
需要选一门语言实现一个单实例承载千人规模、含反向代理与长连接的运营系统。

**决策**
Go 1.25+。

**理由**

| 因素 | 说明 |
|---|---|
| 单二进制交付 | 前端资源 `embed` 进二进制，用户下载一个文件就能跑。这是"半小时跑起来"目标的前提 |
| 低内存 | 空闲 < 100 MB。很多站主跑在 1–2 GB 的小机器或 NAS 上 |
| 并发模型 | 反代、SSE 推送、批量任务都需要大量并发，goroutine 模型天然适配 |
| 交叉编译 | 一条命令出全平台产物，发版简单 |
| 生态验证 | 竞品中三个用 Go 的项目（Meridian、ember、Twilight）都验证了可行性 |

**被否方案**

| 方案 | 否决理由 |
|---|---|
| **Python**（学 MoviePilot） | 生态确实最强（爬虫、OCR、媒体处理库多），但单进程部署重、内存高、GIL 限制并发长连接。**结论：不选它做宿主，而是用 L3 进程外插件复用它** |
| Node.js / TypeScript | 前后端同语言有吸引力，但 CPU 密集型任务（反代流量计量、批量用户同步）表现弱，且部署需要 Node 运行时 |
| Rust | 性能最好，但开发速度与生态成熟度不匹配"快速迭代"的目标 |
| Java | 部署重（JVM），与"单二进制"目标冲突 |

**影响**

- 内核零依赖，业务插件用 Go 编写（L2）
- Python 生态通过 L3 进程外插件接入，而非重写
- 插件系统需要同时支持进程内（L2）与进程外（L3）

## ADR-002 · 不用 Web 框架，用标准库 net/http

**状态**：已定

**背景**
Go 生态有 Gin、Echo、Chi、Fiber 等成熟框架。

**决策**
只用标准库 `net/http`，配合 Go 1.22+ 的 `ServeMux` 模式语法（`"GET /api/v1/users/{id}"`）。

**理由**

| 因素 | 说明 |
|---|---|
| 可读性 | 本项目的首要目标是"便于理解"。框架的中间件链、上下文封装、绑定魔法都会增加理解成本 |
| 路由能力已够用 | Go 1.22 起标准库支持方法与路径参数，不再需要第三方路由 |
| 零依赖 | 少一个依赖，少一份需要理解的东西，也少一个 CVE 来源 |
| 可控的中间件 | 自己写 6 个中间件（recover / requestID / 日志 / 安全头 / 限流 / 鉴权）比学框架的约定更快 |

**被否方案**

| 方案 | 否决理由 |
|---|---|
| **Gin** | `gin.Context` 会渗透到每个 handler 签名里，与内核抽象耦合；绑定/校验的"魔法"难以调试 |
| Echo / Chi | 比 Gin 轻，但功能上标准库已覆盖，引入无净收益 |
| Fiber | 基于 fasthttp，与标准库生态（`http.Handler`、中间件）不兼容，插件作者需要额外学习 |

**影响**

- 所有 handler 签名是标准的 `func(http.ResponseWriter, *http.Request)`
- 插件注册的路由也用标准签名，无框架耦合
- 需要自己实现：路径参数解析（标准库已提供）、请求体解析（已实现 `DecodeJSON`）、限流（已实现）

## ADR-003 · 不用 ORM，用显式 SQL

**状态**：已定

**背景**
Go 生态的 ORM 有 GORM、Ent、sqlc 等。

**决策**
手写 SQL + `database/sql`，表结构由迁移文件唯一定义。

**理由**

| 因素 | 说明 |
|---|---|
| 可审计 | 线上问题排查时能直接复制 SQL 去跑。ORM 生成的 SQL 需要额外步骤才能拿到 |
| 可读 | 本项目的查询不复杂，手写比 ORM 的 DSL 更直观 |
| 无隐式行为 | ORM 的懒加载、级联、自动建表在生产环境都是坑 |
| 表结构真相明确 | 迁移文件是唯一真相，不会出现"代码里改了但库没变" |

**被否方案**

| 方案 | 否决理由 |
|---|---|
| **GORM** | 隐式行为多（`AutoMigrate` 在生产环境尤其危险）；字段映射靠约定，改名容易出错 |
| Ent | 图式建模强大但引入代码生成步骤，增加构建复杂度 |
| sqlc | 类型安全很好，但需要生成步骤；本项目查询数量不多，收益不足以抵消复杂度 |
| 竞品 Twilight 的单行 JSONB 方案 | **反面教材**：6000 行 God Object、全量读写、不可 SQL 查询、无法行级隔离 |

**影响**

- 需要处理 SQLite / PostgreSQL 的方言差异（已实现 `Rebind`）
- 每个功能域自己写 `repo.go`
- 迁移必须手写，不能自动生成

## ADR-004 · SQLite 为默认，PostgreSQL 为可选

**状态**：已定

**背景**
目标用户多为个人站主，机器可能是 VPS、NAS 或家用服务器。

**决策**
默认 SQLite（纯 Go 驱动 `modernc.org/sqlite`），可选 PostgreSQL。

**理由**

| 因素 | 说明 |
|---|---|
| 零配置 | SQLite 就是一个文件，备份就是复制一个文件 |
| 无需 CGO | `modernc.org/sqlite` 是纯 Go 实现，交叉编译无障碍（`mattn/go-sqlite3` 需要 CGO） |
| 性能足够 | 1000 用户、日常并发下完全够用 |
| 平滑升级 | 数据量大或需要多实例时切 PG，业务代码不变（方言已抽象） |

**被否方案**

| 方案 | 否决理由 |
|---|---|
| 只支持 PostgreSQL | 把"半小时跑起来"变成"先装数据库"，与目标冲突 |
| 只支持 SQLite | 多实例部署时会重复扣费、重复发码 |
| `mattn/go-sqlite3` | 需要 CGO，交叉编译麻烦，Docker 镜像也要带编译工具链 |

**影响**

- 写连接限制为 1（SQLite 的并发写是串行的），避免 `database is locked`
- 必须开 WAL 与 `busy_timeout`
- 需要单实例锁机制（已实现 `instance_locks`）
- 迁移在 SQLite 下无法用 DDL 事务，逐语句执行

## ADR-005 · 两级扩展模型：Module + Plugin

**状态**：已定

**背景**
需要同时支持"对接一个新外部系统"与"增加一个新功能"这两类扩展。

**决策**
分为两层：

- **Module（能力提供者）**：实现内核定义的契约，如 `MediaServer`、`Notifier`
- **Plugin（功能扩展包）**：注册能力、订阅事件、提供 UI

**理由**
来源是 MoviePilot 的实践验证。它把这两层分开后，新增一个媒体服务器不需要改任何业务代码。

**被否方案**

| 方案 | 否决理由 |
|---|---|
| 只有 Plugin 一层 | 对接新外部系统时要写完整插件，门槛高；且能力与功能混在一起，难以择优（如"用哪台 Emby"） |
| 只有 Module 一层 | 无法支持"加一个求片玩法"这类纯功能扩展 |

**影响**

- 注册表需要按 Kind 管理多实现并支持择优
- 插件清单需要同时声明"提供什么能力"与"订阅什么事件"

## ADR-006 · 四级插件模型（L0-L3）

**状态**：已定

**背景**
MoviePilot 的插件系统写了 7159 行——因为它在第一版就解决了所有极端情况：插件要装 pip 依赖、要处理版本代际兼容、要支持冻结运行模式、要支持跨代克隆。

**决策**
用四个级别把复杂度分期支付：

| 级别 | 形态 | 上手 |
|---|---|---|
| L0 | 一个 YAML | 5 分钟 |
| L1 | YAML + 脚本 | 30 分钟 |
| L2 | Go 源码 | 半天 |
| L3 | 任意语言 + RPC | 半天 |

**理由**
九成的扩展需求（加通知渠道、接一个预设、字段转换）根本不需要写代码。把它们压到 L0/L1，内核就不需要支撑"插件依赖包管理"那一整套重家伙。

**被否方案**

| 方案 | 否决理由 |
|---|---|
| 只有 L2 原生插件（编译进主程序） | 插件必须重新编译整个项目，第三方无法独立分发 |
| 只有 L3 外部插件 | 简单插件也要起一个进程，太重；且无法注册数据表迁移 |
| 照搬 MoviePilot 的单层模型 | 7159 行插件系统，理解成本过高 |
| **兼容 MoviePilot 的 Python 插件** | 白捡生态的诱惑很大，但必须把它的包管理、依赖解析、代际兼容整套搬进来，与"轻内核"目标正面冲突。**改用 L3 调用它的能力** |

**影响**

- M0/M1 只实现 L0（声明式）与 L2（原生）
- L1 需要脚本引擎（见 ADR-007）
- L3 需要进程间协议（见 ADR-008）

## ADR-007 · L1 脚本引擎选型

**状态**：**【待定】—— M0 前必须决定**

**背景**
L1 插件需要在事件钩子里执行用户写的逻辑。需要嵌入式脚本引擎。

**候选**

| 方案 | 优点 | 缺点 |
|---|---|---|
| **goja**（纯 Go 的 ES5.1 实现） | 纯 Go、无 CGO、Twilight 已用；生态有先例 | 只支持 ES5.1 + 部分 ES6；性能一般 |
| **QuickJS 绑定** | 支持完整 ES2020；性能好 | 需要 CGO；跨平台编译复杂 |
| **Wasm**（如 wazero） | 语言无关（Rust/Go/AssemblyScript/TinyGo 都能编）；隔离性最好 | 插件开发门槛高；每次调用有编译/实例化开销 |
| **表达式引擎**（如 expr、cel） | 极轻、安全 | 只能写表达式，无法写多步逻辑 |

**倾向**
goja。理由是**纯 Go + 无 CGO** 与本项目其余技术选择一致，且 L1 的定位本就是"简单逻辑"，不需要完整 ES2020。

**影响**

- L1 的能力边界受限于 goja 的语法支持
- 沙箱必须在引擎之外做（限制 ctx 能力，而非限制语法）
- 接口需在 M0 预留，即使 M6 才实现

## ADR-008 · L3 插件协议

**状态**：**【待定】—— M0 前必须决定**

**背景**
L3 插件是独立进程，需要与宿主通信。

**候选**

| 方案 | 优点 | 缺点 |
|---|---|---|
| **stdio + JSON-RPC**（LSP 风格） | 最简单；无需端口；天然进程隔离；调试直观 | 只能父子进程；无多路复用；大 payload 效率低 |
| **gRPC** | 强类型；跨语言生成客户端；支持流 | 需要 protobuf 工具链；依赖较重 |
| **HTTP + JSON** | 最好调试；可用 curl 手测 | 需要端口管理；认证要另做；防火墙问题 |

**倾向**
stdio + JSON-RPC。理由是它最符合"插件是宿主的子进程"这个心智模型，无需端口管理与认证，且与 LSP 生态的成熟实践一致。

**影响**

- 需要实现分帧协议（`Content-Length` 头 + JSON body）
- 需要握手流程（`initialize` 上报能力与权限）
- 需要超时、崩溃重启、资源限额
- 接口需在 M0 预留

## ADR-009 · 多租户粒度

**状态**：**【待定】—— M0 前必须决定，代价最大**

**背景**
竞品分析结论：**多租户是全生态空白**。一个人开三个 Emby 站（电影站 / 剧集站 / 二次元站），现在要部署三套系统。

**两个层次**

| 方案 | 含义 | 表结构影响 |
|---|---|---|
| **A. 单实例多服务器** | 一套系统管多台媒体服务器，用户池共享 | 现有设计已支持，无需改动 |
| **B. 真多租户** | 一套系统服务多个独立站点，用户池、计费、配置全隔离 | **几乎所有表都要加 `tenant_id`**，且所有唯一索引要加租户前缀 |

**代价分析**

方案 B 如果**事后**再做，代价极大：
- 每张表加列 + 重建索引
- 所有查询加租户过滤条件
- 所有唯一约束改为复合约束
- 登录时需要先确定租户

**倾向**
先做 A，把 B 的接口预留好：
- 所有表设计时**不加** `tenant_id`，但把所有唯一索引写成"可加前缀"的形式
- 数据访问层统一走一层 `scope` 抽象，将来插入租户条件时只改一处
- 在 ADR 里明确记录这个取舍，避免将来有人以为"漏了"

**风险**
如果最终要做 B，仍有可观的返工。需要在 M0 前评估：**目标用户里有多少人真的需要多租户？**

**影响**
- 影响 [03-数据库设计](03-数据库设计.md) 的所有表
- 影响认证流程（是否需要租户识别）
- 影响前端路由（是否需要租户前缀）

## ADR-010 · 事件驱动而非直接调用

**状态**：已定

**背景**
插件之间如何协作？求片插件需要通知用户，但它不该 import 通知插件。

**决策**
用事件总线。插件通过订阅事件介入流程，不直接互相调用。

**理由**

| 因素 | 说明 |
|---|---|
| 解耦 | 拆掉任何插件，其他插件照常工作 |
| 可发现性 | 读事件目录就知道系统能扩展什么，不需要读源码 |
| 可扩展 | 加一个新的资源搜索源，不用改内核或其他插件 |
| 验证充分 | MoviePilot 用这套机制支撑了整个插件生态 |

**被否方案**

| 方案 | 否决理由 |
|---|---|
| 直接函数调用 | 插件互相 import，形成网状依赖，无法独立分发 |
| 接口注册 + 遍历调用 | 可行但表达力弱：难以表达"四个时机"的语义差异 |
| 消息队列（Redis/RabbitMQ） | 引入外部依赖，与"零依赖启动"冲突；单机场景无必要 |

**影响**

- 事件类型必须稳定，变更要有弃用周期
- 需要 `EVENT-CATALOG.md` 自动生成，防止文档漂移
- 事件命名要严格遵循 `<领域>.<实体>.<时机>`

## ADR-011 · 用户状态：单一枚举 + 分离能力位

**状态**：已定

**背景**
竞品实测结论：**两个最成熟的用户管理系统都没做对**。

- ember：用 `IsActive` + `ResourceAccessGranted` + `EmbyDisabled` + `EmbyAccessDisabled` 四个布尔拼
- Twilight：用 `Role int` + `Active` + `ExpiredAt` + `PendingEmby` 组合

两者都缺"注册后人工审批"这一档。

**决策**

```go
status: pending | active | expired | banned | deleted
status_reason: manual | system:expiry | system:telegram_membership | ...
// 三个正交能力位
can_login: 能否登录
can_play:  能否播放
remote_disabled: 远端镜像状态
auto_disabled: 是否由系统自动禁用
```

**理由**

1. 单一枚举让状态可预期、可穷举、可校验
2. `status_reason` 让"谁改的、为什么"可追溯，自动任务因此能区分"我禁的"与"人禁的"
3. **`can_login` 与 `can_play` 必须分开**：这是表达"过期用户可以登录续费但不能播放"的唯一方式。合成一个字段就永远做不对

**被否方案**

| 方案 | 否决理由 |
|---|---|
| 多个布尔值组合 | 状态空间不可穷举，组合出非法状态时无法发现 |
| 单个 `expires_at` 表达会员 | 无法同时持有两档会员、无法表达升级后旧档剩余时长 |
| 单一 `status` 不分离能力位 | 无法表达"能登录但不能播放" |

**影响**

- 所有状态写入必须走 `NormalizeUserState` 唯一入口
- 前端 403 处理必须区分 `unauthenticated`（跳登录）与 `expired`（跳续费）
- 自动对账任务必须先检查 `auto_disabled`

## ADR-012 · 求片状态机 + 步骤流水

**状态**：已定

**背景**
竞品实测：**六个项目零个做到"求片 → 下载 → 入库 → 自动通知用户"**。

断点在于：没有步骤流水，系统无从判断"现在走到哪、该不该推进"。

**决策**

1. 工单有明确状态机（queued → searching → selected → acquiring → transferring → waiting_ingest → completed）
2. 每次状态推进都写一条 `request_steps` 流水
3. 媒体服务器入库 webhook 触发 `resource.ingest.after` 事件 → 匹配未完成工单 → 自动置完成

**理由**

| 需求 | 由什么满足 |
|---|---|
| 用户看到真实进度 | 步骤流水（前端展示"解锁中 → 转存中"而不是"处理中"） |
| 排障定位卡点 | 步骤流水 |
| 超时自动重试 | 步骤流水里的时间戳 |
| 入库自动闭环 | 事件驱动 + 匹配回填 |

**被否方案**

| 方案 | 否决理由 |
|---|---|
| 单一状态字段，不记流水 | 无法展示进度、无法排障、无法实现自动推进 |
| 完全人工处理 | 竞品里就是这样，体验差且不可扩展 |

**影响**

- `requests` 与 `request_steps` 两张表
- 必须有 webhook 接收与 ID 匹配逻辑（注意：竞品此处有一个**必然失败**的 ID 匹配 bug）
- 匹配失败必须记录而非静默丢弃

## ADR-013 · 积分用账本而非余额字段

**状态**：已定

**背景**
竞品实测：三个 TG 机器人项目的卡密与积分体系都有问题，其中积分**没有账本、无法对账**，有项目的经济系统实测为净通胀。

**决策**
`points_ledger` 流水表 + 余额快照。余额可由流水重算。

**理由**

| 需求 | 由什么满足 |
|---|---|
| 对账 | 流水求和 = 余额 |
| 审计 | 每笔变动有原因、时间、操作者 |
| 纠错 | 发现错误可以追加一条冲正记录 |
| 经济分析 | 可算出"当前规则下每天净发多少分" |

**被否方案**

| 方案 | 否决理由 |
|---|---|
| 只存余额字段 | 无法对账、无法审计、出错无法追溯 |
| 只存流水不算余额 | 每次查余额都要全表扫描，性能不可接受 |

**影响**

- 余额是缓存，流水是真相
- 需要定期对账任务
- 所有变动需要幂等键（防重放导致重复发放）

---

## ADR-014 · 卡密必须有批次

**状态**：已定

**背景**
竞品实测：三个项目的卡密都是"一张表一个 used 字段"。有项目判断卡密类型用**字符串里有没有 `Renew` 这个词**。

**决策**
批次表 + 单码表 + 兑换记录表。批次持有类型、权益参数、有效期、作废状态；单码可覆盖批次的部分字段。

**理由**

| 需求 | 由什么满足 |
|---|---|
| "这次活动发了多少张、用了几张" | 批次统计 |
| "把这次活动的码全部作废" | 批次级作废 |
| "这个码是谁兑换的" | 兑换记录 |
| "同一码不能被同一人兑换两次" | 唯一索引 `(code_id, user_id)` |

**影响**

- 三张表：`redeem_code_batches` / `redeem_codes` / `redeem_records`
- 核销必须用条件更新防超发
- 卡密明文只在生成时返回一次

## ADR-015 · 线路状态是持续对象

**状态**：已定

**背景**
竞品实测：一个成熟的反代面板，**延迟只存在于管理员手点测速的那一瞬间**，既不落库也不参与调度。另一个项目反而做得对——用"最近 10 次检测结果"聚合出三态。

**决策**
线路健康状态是持续对象：

```
(滑动窗口成功率, P50/P95 延迟, 最近失败原因, 冷却截止时间)
```

定时轻量探测，结果落库，**调度真正消费它**。

**被否方案**

| 方案 | 否决理由 |
|---|---|
| 只在手动测速时探测 | 调度没有依据，故障切换靠猜 |
| 只在请求失败后标记 | 被动发现，用户已经受了影响 |
| 每次调度前实时探测 | 引入额外延迟，且探测本身可能超时 |

**影响**

- `routes` 表带健康字段
- `route_stats` 记录每日统计
- 需要探测任务（默认 30s 一次轻量 HEAD）

---

## ADR-016 · 降级必须可见

**状态**：已定

**背景**
竞品实测的最大通病：**失败被吞掉**。

- 有项目的 `except: pass` 遍布，双擎路由失败时静默返回空 → 故障表现为"暂无数据"
- 有项目的健康探测把 4xx/5xx 判为可达

**决策**
三条硬规矩：

1. 任何取数失败必须产生降级指标（计数器 + 大盘 + 通知）
2. UI 必须区分"确实没有数据"与"加载失败"
3. 降级路径必须有结构化日志与 `media.server.degraded` 事件

**理由**
"静默返回空"是最难排查的一类故障——用户以为真的没数据，管理员以为系统正常，直到有人发现数据对不上。

**影响**

- 需要 `degraded_total` 指标
- 每个数据获取点都要处理"失败"与"空"两种情况
- 前端空态组件分三种（无数据 / 加载失败 / 降级中）

## ADR-017 · 默认不开启 CORS

**状态**：已定

**背景**
竞品实测发现一个项目同时存在两个问题：**CSRF 中间件被整体禁用**（代码里还注释"严禁修改"），且 CORS 配置在 `origin` 为空或 `*` 时**反射任意来源 + `allow_credentials=true`**。

两者叠加 = 任何网站都能带着用户的 Cookie 读写该站接口。

**决策**
默认同源部署，**不开启 CORS**。需要跨域时由运维在反代层显式配置白名单。

**明确禁止**
`Access-Control-Allow-Origin` 反射任意来源 + `Access-Control-Allow-Credentials: true` 的组合。

**影响**

- 前端必须同源部署（或由反代统一）
- 插件不能假设可以跨域调用站点接口
- L3 外部插件通过 stdio 而非 HTTP 通信

---

## ADR-018 · 单一出站校验入口

**状态**：已定

**背景**
本项目需要主动发起大量外部请求：调用媒体服务器、调用 MoviePilot、图片代理、插件出站、Webhook 投递。

竞品实测发现 Twilight 存在**沙箱内 fetch 严格、通用出站宽松**的两套标准。

**决策**
全系统唯一入口：

```go
func ValidateOutboundURL(raw string, allowedHosts []string) (*url.URL, error)
```

所有出站请求（含 L1 脚本的 `ctx.http`、L3 插件的代理、内置插件的客户端）**无一例外**都走它。

**理由**
两套标准 = 一定有漏洞。一处严格一处宽松，攻击者只会走宽松的那条。

**影响**

- 需要实现内网地址段检测、DNS pinning、重定向逐跳校验
- 插件必须声明 `allowed_hosts`
- 图片代理改用加密 capability 令牌而非域名黑名单

---

## ADR-019 · 调度用数据库队列而非进程内 cron

**状态**：已定

**背景**
竞品实测：Twilight 用数据库租约队列（支持运行期改调度、`dry_run`、熔断告警），ember 用硬编码 cron 表达式（改完要重启）。前者明显更好。

**决策**
数据库租约队列。

**理由**

| 需求 | 由什么满足 |
|---|---|
| 站长在后台改调度时间 | 调度存在数据库，运行期可改 |
| 多实例不重复执行 | 租约抢占（条件更新） |
| 危险任务先演练 | `params.dry_run` |
| 执行历史可查 | `job_runs` 表 |
| 失败可诊断 | `last_error` / `fail_count` |

**被否方案**

| 方案 | 否决理由 |
|---|---|
| 进程内 cron（robfig/cron） | 改调度要重启；多实例会重复执行 |
| 外部调度器（systemd timer / K8s CronJob） | 用户需要额外配置；无法感知业务状态 |

**影响**

- `jobs` / `job_runs` 两张表
- 需要租约续期与过期清理
- 所有破坏性任务必须支持 `dry_run`

---

## ADR-020 · 单实例约束显式化

**状态**：已定

**背景**
竞品实测：三个项目**全部假设单实例运行**（failover 状态在进程本地、`scan_state` 是模块级全局变量），只有其中一个用 `single_instance_confirmed` 开关把约束写出来了。

**决策**
需要独占的插件在清单里声明：

```yaml
spec:
  execution:
    mode: single-instance
    lock: db-advisory
```

启动时获取数据库锁，**拿不到就拒绝启动并说明原因**。

**理由**
重复扣费、重复发码这类事故一旦发生就无法撤销。宁可第二个实例起不来，也不要它带着错误的假设跑起来。

**被否方案**

| 方案 | 否决理由 |
|---|---|
| 运行期兜底（如去重窗口） | 兜底逻辑本身要处理并发，复杂度不低于分布式锁 |
| 文档里写"请勿多开" | 约定无法强制，出事时已经晚了 |

**影响**

- `instance_locks` 表
- 锁带过期时间（进程被 kill 后自动释放）
- 装配阶段就要检查

---

## ADR-021 · 前端自建 headless 组件而非用组件库

**状态**：已定

**背景**
需要选前端 UI 方案：Element Plus / Naive UI / Ant Design Vue / 自建。

**决策**
自建约 25 个 headless 组件 + Tailwind + CSS 变量主题。

**理由**

| 因素 | 说明 |
|---|---|
| 插件不锁 UI 框架 | 插件返回 UI Schema，由我们的渲染器渲染。若用组件库，插件就被绑死在那个库上 |
| 体积可控 | 组件库全量引入通常 > 500 KB |
| 换皮成本 | 用 CSS 变量，换主题只改一个文件 |

**被否方案**

| 方案 | 否决理由 |
|---|---|
| Element Plus | 竞品 ember / Twilight / emby-tools / emby-manager 全都在用，但它是**按需引入也偏重**，且视觉被锁死 |
| Vuetify | MoviePilot 用的方案，但插件被绑死在 Vuetify 的组件树上 |
| 完全不引 Tailwind | 布局代码会显著变多；但 Tailwind 也增加构建链一层（见待定项） |

**影响**

- 需要自己写约 25 个组件（工作量换自由度）
- 插件 UI Schema 的组件类型由我们定义（约 30 种）
- 主题必须走 CSS 变量，禁止硬编码颜色

---

## ADR-022 · 前端资源内嵌进二进制

**状态**：已定

**背景**
前端是 SPA，需要部署静态资源。

**决策**
用 Go 的 `embed` 把构建产物打进二进制。

**理由**

- 用户下载一个文件就能跑，不需要配 Nginx 托管静态资源
- 版本不会错配（前端与后端永远同一次构建）
- 与"单二进制交付"目标一致

**影响**

- 构建流程：先构建前端 → 再编译 Go（需要 Makefile 编排）
- 开发期用 Vite dev server，通过代理连后端
- 二进制体积增加（前端产物约几百 KB）
