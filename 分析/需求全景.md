## 1. 生态全景：这个领域有六种角色

```
                        ┌─────────────────────────────┐
   [6] 门户层            │  emby-manager / request-ui   │  用户自助入口（薄）
                        └─────────────────────────────┘
                        ┌─────────────────────────────┐
   [2] 用户管理层         │  ember / Twilight / usersvr  │  账号、权益、工单、计费（厚）
                        │  sakura / lemon / register   │
                        └─────────────────────────────┘
                        ┌─────────────────────────────┐
   [4] 数据洞察层         │  emby-pulse / bubble / tools │  播放统计、缺集、报表（中）
                        └─────────────────────────────┘
                        ┌─────────────────────────────┐
   [1] 资源自动化层       │  MoviePilot                  │  搜索→下载→整理→入库（极厚）
                        └─────────────────────────────┘
                        ┌─────────────────────────────┐
   [3] 运维网络层         │  Meridian / ProxyHub         │  反代、线路、流量、证书（中）
                        └─────────────────────────────┘
                        ┌─────────────────────────────┐
   [5] 用户自动化层       │  emby-keeper                 │  自动签到保活（用户侧，灰色）
                        └─────────────────────────────┘
```

**致命事实**：这六层**没有任何一个项目跨过两层以上**。站主要部署 5–6 套系统，配 5–6 套账号体系，改 5–6 个配置文件，还互不知情。

**EmbyOne 的战略就是垂直整合这六层**——不是做一个更好的单点，而是做**一个内核 + 六类插件**。

## 2. 需求分层

按「不做会死 / 做了才活得下去 / 做了才能赢」三档分级。

### P0 · 基线需求（15 项，缺任何一项用户会投诉）

来自 G1 的实测：**这 15 项被两个独立项目各自实现了一遍**，是这个领域的物理定律。

| 需求 | 现状成熟度 | 已知坑 |
|---|---|---|
| Emby 账号自动建号/绑定 | 🟢 | 建号与落库非原子 → 孤儿号，需补偿 |
| 到期检查 → 自动封禁 | 🟢 | 到期与下次 cron 之间状态不一致 |
| 兑换码 / 注册码 | 🟢 | 并发重复兑换；永久码与限时码混用；旧码作废兼容 |
| 邮箱验证码 | 🟡 | 限流维度、反枚举语义、SMTP 未配置降级 |
| 登录认证 + 反枚举 | 🟢 | 登录/注册/找回/TG 四条路径要统一文案 + 统一限流 |
| Telegram Bot 集成 | 🟢 | 多副本重复消费（需租约锁）；消息编辑同步 |
| 求片 → 自动下载 | 🟢 | 外部下载器语义不统一（HTTP 200 + `success=false`） |
| 播放记录采集与排行 | 🟡 | Emby 原生无此能力，依赖 Playback Reporting 插件，未装时要降级 |
| 设备管理与踢下线 | 🟢 | 共享账号治理的必要手段 |
| 媒体库统计 | 🟢 | — |
| 后台配置中心 | 🟢 | 「空值=关闭/回退/继承」的语义设计 |
| 管理 API Key | 🟢 | 权限位 + 限速 + **禁止自提权** |
| 审计日志 | 🟡 | 多管理员场景下的问责基础 |
| 定时任务调度 | 🟡 | ember 硬编码 cron（改完重启）；Twilight 的 DB 队列 + 重试 + 熔断才对 |
| 前端门户 | 🟢 | — |

## 3. 现有项目的十大结构性缺陷（我们的靶子）

每条都有代码依据，不是体感。

### 缺陷 1 · 没有统一用户状态机 ★最严重

- **ember**：用 4 个 bool 拼状态（`isActive` / `isExpired` / `planGroup` / `resourceAccessGranted`）
- **Twilight**：`Role int` + `Active` + 若干标记位
- **G1 结论**：**双方都没做对**，是本领域最严重的结构性缺陷

**正解**：
```
status: pending | active | expired | banned | deleted
statusReason: manual | system:expiry | system:telegram_membership | system:invite_detach
```
外加 ember 的正确洞察：**「能不能登录」与「能不能播放」必须是两个独立字段**（过期用户可以登录续费，但不能播放）。

### 缺陷 2 · 卖不出差价：按等级控制媒体库/线路/转码的能力缺失

G1 原话：「**这是唯一能卖出差价的机制**」。G0 实证了商业系统怎么做的——`allowed_libraries`、`allowed_routes`、`route_exclusive`、`allow_video_transcode`、`max_concurrent`、`max_parental_rating` 一整套粒度授权。开源项目里只有 ember 做到了分组级模板。

### 缺陷 3 · 求片与入库零闭环 ★全组最缺的一环

G4 实测：**六个项目零个做到自动推进状态**。
- embyforge 有全部零件（webhook → 事件映射 → EventLog → 事件总线）但没接匹配回填
- 更糟的是它的 webhook 有必现 bug：用 Emby 的 `Server["Id"]` 匹配本地 `servers.id`（`gen_random_uuid()`），**必然失败** → 整条播报链静默失效
- emby-request-ui 的 `progress_token` 是死代码

**商业系统做对了**（G0 实证）：11 个状态的完整状态机 + 工单流水落库 + 用户可见真实进度。

**我们的设计**：`request_steps` 表记录每一步（阶段、状态、详情、时间戳），状态机由事件驱动自动推进（`resource.ingest.after` → 匹配回填 → 置 done）。

### 缺陷 4 · 卡密停留在「一表一 used 字段」

G2 实测三个项目：
- sakura 类型靠 **`"Renew" in code` 子串判断**，无批次/无有效期/无作废
- lemon 无 `expires_at`
- **三家全缺：批次、有效期、作废、使用上限、对账**

### 缺陷 5 · 积分经济无账本无配平

- sakura 观影榜**无上限发币，纯通胀**
- lemon 的抽奖概率硬编码（`database.py:224`），期望值测算：**积分净消耗 9.5 分/次，系统净通胀**，唯一通缩源是抽奖
- 改价要改代码

**正解**：`points_ledger` 流水表 + 规则表（可配）+ 余额快照。可审计、可对账、可回滚。

### 缺陷 6 · 探活是一次性快照，不是持续状态

G3 实测：
- meridian：延迟只存在于手点测速的瞬间，**不落库、不参与调度**；failover 只认 5xx
- emby-pulse：`/check` 是请求即刻探测
- **只有 bubble 做对**：滑动窗口最近 10 次 → 正常/离线/波动三态

**正解**：线路状态是 `(滑动窗口成功率, P50/P95 延迟, 最近失败原因, 冷却截止)` 的**持续对象**，落库 + 定时轻量探测，调度真正消费它。

### 缺陷 7 · 失败被吞掉，「无数据」与「取数失败」不分

- emby-pulse：`except: pass` 遍布，双擎路由静默降级 → **故障表现为「数据为空」而非「报错」**
- meridian：`probeTargetHealth` 把 4xx/5xx 判为 `reachable`（`diagnostics.go:330`），存在误导

**正解**：两种空结果必须区分；降级/回退事件当作**一等指标**暴露（计数器 + 大盘 + 通知）。

### 缺陷 8 · 单实例假设贯穿全部项目

- meridian：failover 状态在进程本地
- emby-pulse：`scan_state` 是模块级全局，多 worker 必然错乱
- sakura/lemon：内存态队列与计数 → **多副本必重复扣费发码**
- **只有 bubble 把它显式化**（`single_instance_confirmed` 开关）

**正解**：需要单实例的地方**显式声明 + 启动自检**（advisory lock），而不是让它在运行时偶发。

### 缺陷 9 · 邀请无关系树

G1：具有关系树的项目 = 0；G2：sakura 有 invite 配置但 `Rcode` 表无 `inviter` 字段，**谁拉谁不可统计**。

后果：无法做连带封禁、返利、层级统计、推荐排名。

### 缺陷 10 · 插件机制要么没有，要么过重

- 13 个项目里只有 **Twilight** 有（goja JS 沙箱）——但 G1 评价：「进程堆 256MB 中断 + 单次 8s + 内存交互状态 512 条上限」是**止损不是隔离**，方向对但形态错
- MoviePilot 有完整插件系统但 **7159 行**（`manager.py` 单文件 1477 行），且要处理 pip 包安装、代际兼容、frozen 模式

**我们的靶子**：既要有（G1 称其为"最被低估的需求"），又要轻（90% 场景收敛到 YAML）。

## 4. 五个无人占位的机会点（真正的秒杀点）

### 机会 1 · 同时持有「运营端」与「风控端」★★★

G2 的核心洞察，值得完整引用：

> sakura/lemon 精于运营管理，但风控只到「数会话数」；keeper 精于伪造播放，但零风控。**两者唯一接触点是 keeper 里写死的 sakura 正则**。
>
> 能同时持有两端的系统**目前无人占位**：运营端握有正常行为基线，所以能识别 keeper 类异常，也能做官方保活。

**具体怎么做**：
- 运营端天然握有**正常行为基线**（tick 线性度、起播时序、设备分布、时长分布）
- keeper 类工具的行为特征**可被检测**：持久化固定 DeviceId、严格线性的 tick、瞬时起播、时长集中在 5–10 分钟、完整重放人类浏览路径
- 所以 EmbyOne 可以做：**行为基线 → 异常评分 → 风控策略**，同时提供**官方保活**（用户不用装 keeper）

这是唯一需要"站在两侧"才能做的能力，别人抄不走。

### 机会 2 · 一个人管四层（网络 + 数据 + 用户 + 资源）

G3 的结论：

```
meridian   ── 网络层：入口/反代/线路/字节计费/证书
emby-pulse ── 数据层：播放分析/缺集/内容运营
bubble     ── 运营层：账号生命周期/权限/积分/工单
MoviePilot ── 资源层：搜索/下载/整理/入库
```

**四者能力几乎不重叠**（唯一交集是流量统计，且口径不同：字节 vs 时长），一个完整平台 = 四者并集。现状是站主要部署 4–5 套系统。

EmbyOne 用**一个内核 + 四类插件**吃掉全部。

### 机会 3 · 轻量插件化

| 方案 | 现状 | 我们 |
|---|---|---|
| MoviePilot | 完整但 7159 行，要求 Python 3.14 + 100 依赖 | 内核 < 3000 行，四级插件模型 |
| Twilight | goja 沙箱，但同进程跑第三方 JS，隔离性不足 | **进程外 RPC 隔离**（L3） |
| 其他 13 个 | 无插件机制 | — |

**关键设计**：L0（纯 YAML，5 分钟）/ L1（JS 钩子，30 分钟）/ L2（Go 原生）/ L3（任意语言 RPC）。90% 的扩展需求落在 L0/L1。

### 机会 4 · 多租户

G2 明确判定：「**多租户完全空白**，三个项目都是『一实例服务一站』」，且列为最大空白。

现实需求：一个人开了 3 个 Emby 站（电影站/剧集站/二次元站），现在要部署 3 套系统。多租户能让一套系统服务多站，每站独立用户池、独立计费、独立配置。

### 机会 5 · 用户侧体验闭环

G0 实证商业系统在用户侧做了大量细节，开源世界几乎全是空白：

- 求片进度可见（不是"处理中"，而是"解锁中 → 转存中 → 等待入库"）
- 撤销工单 + 自动返还积分
- 免费顶帖（12 小时一次，不重复扣分）
- 多季合并工单 + 整组撤销
- 配对账号一键切换
- 线路自助选择 + 等级匹配
- 观影报告可视化

**这些都是"把用户当人看"的设计**，成本不高，但开源项目集体忽略了。

## 8. 一句话结论

现有生态是**五套互不相通的半成品**，每套都在自己的那一层做得不错，但都在同一个地方栽跟头：**把「非功能性需求」（状态一致性、降级可见性、多实例、扩展性）当成实现细节而不是产品能力**。

EmbyOne 的机会不是"把某个功能做得更好"，而是：

1. **垂直整合**六层角色，一套系统解决
2. **把非功能性需求产品化**（统一状态机、降级可观测、持续探活、插件化）
3. **补上商业系统验证过、开源世界集体缺失的用户侧体验**
4. **靠插件生态和租户隔离建护城河**
