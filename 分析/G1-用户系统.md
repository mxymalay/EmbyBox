## 1. ember

### 1.1 项目定位与技术栈

Ember 是**面向付费 Emby 私服的商业化用户管理系统**：注册门控 → 自动建 Emby 号 → 试用/计费 → 到期封禁 → 兑换/支付续期 → 求片 → 排行 → 115 直连播放加速。

| 层 | 技术 | 依据 |
|---|---|---|
| 后端 | Go 1.23 + Gin + GORM + PostgreSQL 15/16 | `services/api/go.mod`；`docs/system-architecture.md:40-47` |
| 前端 | Vue 3 + TypeScript + Element Plus + Tailwind + Pinia | `services/web/src/plugins/element-plus.ts`、`services/web/src/store/` |
| Bot | Python 3.11 + python-telegram-bot + FastAPI | `services/bot/app/server.py` |
| 支付 | Stripe Checkout + Webhook | `services/api/internal/services/payment/service.go` |
| 调度 | robfig/cron/v3 | `services/api/internal/app/cron.go:23` |
| 部署 | 单二进制双子命令 `api` / `gateway`；Compose profile 隔离 `bot` / `gateway` | `services/api/cmd/ember/main.go`、`internal/entrypoint/` |

关键形态：**一个 `ember` 二进制、两个进程角色**。`api` 跑控制面（JWT/cron/Bot），`gateway` 跑播放面（Emby 透明代理 + 115 302 加速），gateway 启动序为 `InitDB → Migrate → VerifySchema → load LOG_LEVEL → ConfigService → GET /emby/System/Info → listen`，刻意不初始化 JWT、Bot、cron（`docs/system-architecture.md:863`）。

规模：`services/api` 473 个 `.go`、`services/web` 60 个 `.vue`、`services/bot` 约 10 个 `.py`。

### 1.2 解决的痛点（具体到用户故事）

1. **站长手工建号**：过去站长在 Emby 后台点「新建用户 → 设密码 → 记到期日 → 到点手动 Disable」。Ember 把它自动化成一条链：注册时调 `POST /emby/Users/New` 建号，到期由 cron 调 `POST /emby/Users/{id}/Policy` 设 `IsDisabled`（`services/api/internal/integrations/emby/emby.go:290,658`；`internal/services/system/expiry.go:60-170`）。
2. **卖卡密续期**：站长生成一批兑换码发群里，用户自助兑换延长到期时间，无需人工改库（`internal/services/redemption/service.go` 的 `RedeemCode`）。
3. **求片流程散落 TG 群**：用户在群刷「求 XX」→ 管理员手工找资源 → 手工丢 MoviePilot。Ember 把它结构化为 `PENDING → APPROVED → INGESTED` 的订阅工作流，审批后自动下发 MoviePilot，Emby webhook 入库后自动收口（`internal/services/subscription.go`）。
4. **播放排行无法统计**：Emby 原生不给排行榜，Ember 通过 Playback Reporting 插件的 `submit_custom_query` 直接对 `PlaybackActivity` 表跑 SQL 聚合（`internal/services/playback/ranking.go:168-207`、`integrations/emby/emby.go:836`）。
5. **网盘直连播放**：用户通过 Emby 播放 115 上的文件要走服务器中转，上行吃满。Ember 用 Gateway 拦截 `Videos/{Id}/stream`，命中则 302 到 115 直链，未命中回退 Emby（`internal/playbackgateway/video.go`、`internal/services/directplay/`）。
6. **封禁用户还能登录续费**：Ember 明确区分「登录态」和「资源访问态」——过期用户能登录控制台但不能播放（`internal/models/user.go:53` 的 `IsAccessExpired`、`docs/system-architecture.md:364`）。
7. **改密后旧 Token 仍然有效**：引入 `pwdSig` 指纹进 JWT，改密/重置/停用即时踢下线（`internal/common/jwt.go`、`internal/middleware/password_reset_required.go:36-51`）。

### 1.6 扩展机制

**结论：Ember 没有插件/扩展机制。** 全仓 `grep -riE 'plugin|extension point|hook registry'` 只命中两类无关结果：Emby 的 Playback Reporting 插件调用、路由白名单里的字面量 `"plugins"`。它靠三件事替代扩展性：

1. **配置中心注册表**：`internal/config/config.go`（2240 行）定义 `ConfigDefinition{Key, Group, Label, Type, Validation, DefaultValue, Sensitive, RestartRequired, EmptyValueMode}`，7 个分组 `business / media / email / payment / notification / schedule / deployment`。新增能力 = 新增一个 key。读取优先级固定 `数据库 > 环境变量 > 代码默认`，敏感值用 `CONFIG_ENCRYPTION_KEY` 加密落库，普通 key 走 60 秒惰性 TTL 缓存。
2. **空值语义化**：`ConfigEmptyValueDisable / Fallback / Inherit`，界面上直接告诉运维「填空=关闭该功能」或「回退到 X」（`config.go:857` `normalizeEmptyValueMode`、`buildFallbackHint`）。
3. **集成包边界**：`internal/integrations/<vendor>/` 每个厂商一个包，用编译期接口断言锁定合同（如 p115 的 `CookieProvider` 对 `Provider` 接口做编译期断言）。

可扩展但**非插件**的落点：`plan_group_emby_policy_templates`（每个套餐分组一组 Emby Policy 字段）、`plan_group_media_libraries`（分组可见媒体库白名单）、MediaGap 的 webhook 核销。

### 1.7 亮点设计（值得抄的）

**1. 三态用户模型：登录态 / 资源访问态 / 远端镜像态 解耦**

```go
// internal/models/user.go:45-58
func (u *User) IsExpired() bool { ... return u.ExpiresAt.Before(time.Now().UTC()) }
func (u *User) IsAccessExpired() bool {
    if u.IsAdmin() { return u.IsExpired() }
    return !u.ResourceAccessGranted
}
```
`IsActive`（能不能登录）、`ResourceAccessGranted`（能不能播放）、`EmbyDisabled`/`EmbyAccessDisabled`（远端镜像与闸门）四者分离。好处：过期用户仍能登录去续费，而 `PasswordResetRequired()` 中间件**只校验 `is_active`，不校验 `emby_disabled`/过期**（`docs/system-architecture.md:960`）——这个边界必须显式设计，否则会自己把自己锁死。

**2. `pwdSig` 密码指纹会话失效**
JWT Claims = `{userID, username, role, pwdSig}`，`pwdSig` 由当前密码哈希派生。每请求重算比对，不一致即 401。改密/管理员重置/TG 重置/邮箱找回四条路径共用同一套踢下线语义，不需要维护 session 黑名单。

**3. Emby Policy 单一重算入口 + 任务表 + advisory lock**

```go
// internal/services/policy/effective_policy.go:271-308
func buildManagedPolicyFields(...) map[string]any {
    managed := map[string]any{
        "IsDisabled": isDisabled, "EnableAllFolders": false, "EnabledFolders": enabledLibraryIDs, ... }
    // SimUltaneousStreamLimit 缺失时降级写 MaxActiveSessions
}
```
所有改动用户状态的路径（注册/兑换/支付/后台启停/过期 cron）都收敛到 `ApplyEffectiveUserPolicy(userID, reason)`；失败写 `emby_policy_sync_tasks(status=pending)`，由 `@every 1m` 的 worker 领取，**每用户一把 PG advisory lock** 跨实例串行。这是「最终一致 + 可人工重试」的正确写法。

**4. 不可变订单快照**

```go
// internal/models/entitlement.go
type PlanBenefit struct { PlanGroup, ValidityType string; DurationDays int }
// internal/models/payment.go
Benefits []PlanBenefit `gorm:"column:benefits;type:jsonb;serializer:json"`
```
`Plan` 改价/改编只影响新订单；已支付订单按自己的 `Benefits` + `Amount/Currency/Days` 履约。同时 `CreateCheckoutSession` 用「占位行 + Stripe Idempotency-Key」解决并发重复下单。

**5. Webhook 幂等状态机**
`stripe_webhook_events`：首次 `INSERT ON CONFLICT DO NOTHING` 成功才分发；冲突时回查状态，`processed/skipped` 才是真幂等，`received/failed` 视为上次崩溃，**允许 Stripe 重试驱动履约**并刷新 `receivedAt`。比常见的「见过 event.id 就 200」多了一层「上次没做完要重做」。

**6. 反账号枚举的工程化**
- 忘记密码：除格式错误/SMTP 未配置外，所有内部错误折叠成同一 200 文案；未注册邮箱**照样消耗限流配额**，攻击者无法借 200 vs 429 差异枚举。
- Telegram 绑定：`VerifyBind` 无效码/已绑定统一 400；`GetAccountInfo`/`RedeemByTelegram`/`ResetPassword`/`SubscribeByTelegram` 命中 `ErrTelegramNotBound` 统一返回 `请求参数错误`。

**7. 边界化脱敏纪律**
日志层有明确禁令清单：不输出 Token / Cookie / 完整 SHA1 / 115 URL / 完整响应体 / 上游原始错误。`playbackgateway` 决策日志只用固定 code + 白名单字段。`p115_accounts` 的 GORM 用局部静默 session，避免 PG 失败行把 Cookie 密文带进错误详情。

**8. 「未初始化态 vs 上游错误」的 API 语义**
`/emby/config`、`/media/stats`、`/media/latest` 在 Emby 未配置/用户未绑定时返回 `200 + configured/bound` 业务标志位；只有依赖已配置但调用真失败才 500。前端首屏探测统一带 `silent: true`，避免 fresh-install 场景叠 toast。

### 1.8 缺陷与不足（我们要超越的）

**P0 级**

1. **没有注册审核能力**。`registration_mode` 只有 `invite` / `open`，`User` 无 `status` 枚举，判状态靠 `IsActive + ResourceAccessGranted + EmbyDisabled + EmbyAccessDisabled` 四个 bool 组合。`IsAccessExpired()` 这种语义函数只覆盖一部分场景，跨模块判定分散（`admin.go:555` 的 `adminUpdateChangesEmbyPolicy` 就是补丁式判定）。**想做「注册后人工审批通过才发号」得改模型。**
2. **无单一用户状态机**。没有 `status: pending / active / expired / banned / deleted` 这种权威枚举，也就无法表达「停用原因」。对比 twilight 的 `DisabledReason` + `normalizeUserStateMarkers`（见 2.4），ember 在这里明显更弱：管理员手动停用和系统自动停用不可区分。

**P1 级**

3. **无工单/客服系统**。只有 `media_gaps`（缺集工单，面向内容不面向人）。用户与站长之间没有对话通道。
4. **无站内公告**。运营通知只能靠 TG 群；没有 `announcements` 表、没有已读回执。
5. **无签到/积分**。续期只有「兑换码 + 支付」两条，缺少「每日签到攒积分自动续期」这类留存机制。
6. **无邀请关系树**。只有扁平兑换码（`redemption_codes.maxUses`），没有 `invite_relations`，无法做「谁邀请了谁」的层级、连带封禁、返利。
7. **无 2FA**。管理员账号只有密码 + JWT，无 TOTP/二次验证。
8. **无 IP 黑名单 / 登录日志**。只有 `device_actions`（针对 Emby 设备）和 `client_blacklists`（针对客户端名），没有面向 Web 登录的 `login_logs` / `ip_blacklists`，暴力破解只能靠 Turnstile 和限流。

**P2 级**

9. **无 i18n**。前端与 Bot 文案全中文硬编码。
10. **Webhook 入口单一**。只有 `/webhooks/emby` 一个，交给 `tvCalendar.HandleEmbyWebhook` 处理订阅入库、缺集核销、追剧点亮三种语义，职责重叠。
11. **配置改完需重启**。cron 调度项（`CRON_SCHEDULE` 等）在 API 启动时装配，`restartRequired` 标记存在但需要人工重启（`docs/system-architecture.md:1041`）。
12. **DB 迁移链长**。34 张表 + `schema_migrations` 记账 + `archive/` 边界，直接升级起点被钉在 `2026-06-05`/v1.6.0，老库不能一跳到底。

**架构层面的隐性成本**

13. **`internal/app/cron.go` 是硬编码任务清单**，6 个任务全部写在 `initCronJobs()` 里，没有任务注册表、没有运行时参数、没有单飞锁、没有失败告警（失败只 `log.Printf`）。对比 twilight 的调度器（22 个 job + DB 租约队列 + 心跳 + 重试 + 熔断 + 告警）差距明显。
14. **115 直连播放这条链路极重**：`playbackgateway` 24 个文件 + `directplay` + `p115`，`docs/system-architecture.md` 里 5.24/5.25/5.26/5.27 四节加起来 200 行。它把「用户管理」项目变成了半个播放中间件，维护成本远超用户系统本身。文档自己承认多处「只有 fake/单元证据，尚未执行真实服务或客户端验证」（`docs/system-architecture.md:768`）。

### 2.2 解决的痛点（具体到用户故事）

1. **站长要跟用户对话**：用户「我号被封了/我登不上/帮我查一下」全在 TG 私聊或群里刷。Twilight 做完整工单：`open → in_progress → resolved → closed`，带回复、图片附件、优先级、工单类型，且**支持用户自建工单类型**（`docs/features/tickets.md`、`internal/api/ticket_v2.go`、`internal/store/store_tickets.go`）。
2. **公告发出去没人看**：`Announcement` 带 `ForceRead` + `ForceReadSeconds` + `Pinned` + `Level`，用户必须读满 N 秒才算已读，`SeenAnnouncementIDs` 落用户对象（`internal/store/store.go:331,331-346`）。
3. **注册了但一直不建 Emby 号占坑**：引入「开通资格」`PendingEmby + PendingEmbyDays`，管理员发资格但用户不自建号，`cleanup_pending_emby_entitlements` 定时收回（`internal/api/admin_user_handlers.go:570-655`）。
4. **邀请制拉新要能追责**：`InviteCodes` + `InviteRelations` 形成邀请树，可 `detach`（仅解除关系）/`detach-delete-emby`（连带删 Emby 号）/批量 detach；被邀请者到期可自动脱钩（`internal/api/invite_*.go`、`/api/v1/invite/me/detach-expired`）。
5. **用户不愿付钱但愿意签到**：`Signin` 积分 + `SigninAutoRenewal`，`check_expired` 任务先按签到配置尝试自动积分续期，续不上才禁用（`internal/store/signin.go:44-138`、`internal/api/scheduler_handlers.go:16`）。
6. **TG 群里混进白嫖党**：`enforce_group_membership` 任务校验用户是否仍在要求的群组，退群按配置禁用/封禁/自动解禁，带**熔断**（`breaker_percent` / `breaker_max`，拟停用人数超阈值整轮中止）与 `dry_run` 预览。
7. **Web 停用了但 Emby 还开着**：`emby_state_reconcile` 任务按 Web 状态收敛 Emby 启停。难点在于不能把管理员手动封禁的人顺手解封 → 引入 `EmbyAutoDisabled` 标记（`internal/store/store.go:191-195`）。
8. **数据库怎么备份/迁移/升级**：后台直接提供备份/恢复/迁移/系统自更新（`/api/v1/system/admin/database/*`、`system_auto_update` 任务）。

func normalizeUserStateMarkers(old User, u *User) {
    if old.Active != u.Active && u.DisabledReason == old.DisabledReason { u.DisabledReason = "" }
    if u.Active { u.DisabledReason = "" }

### 2.6 扩展机制

**这是 twilight 相对 ember 最大的结构性优势：它有真正的插件化扩展 —— Goja JS 沙箱。**

`internal/api/telegram_js_*.go` 6 个文件 + `docs/reference/developer-js.md`：

- **开启方式**：仪表盘兑换码框输入 `DEBUGMODE` + 管理员密码二次验证 → 开启开发者模式（`POST /api/v1/admin/developer-mode/activate`）。
- **能力**：管理员写 JS 预设（`DeveloperJSPreset`），在「Telegram 管理 → Bot 指令管理」里挂成自定义指令，格式 `js:preset:<id>`（动态引用，预设更新即生效）或 `js:<code>`（静态快照）。
- **运行模型**：Goja 同步执行，单次 **8 秒墙钟超时**；正则走 regexp2 的有回溯路径另设 **250ms 上限**（超时按「未匹配」处理而非抛异常）；`String.repeat/padStart` 等单次结果 > 1M 字符抛 `RangeError`；进程堆增长 > 256MB 中断（文档自述「这是止损而非隔离」）。
- **注入的 API 命名空间**（`docs/reference/developer-js.md` 全局绑定表）：`ctx / command / input / args / user|me / constants|roles / db / users / admin / regcodes / invites / announcements / system / text|arrays|time|format / interactions`；核心函数 `reply()`（最多 4 段）、`exit()`、`assert()`。
- **安全边界**：`fetch()` 只允许公开 http/https 的 GET/POST/HEAD，阻断 localhost、内网、链路本地、云元数据 `169.254.169.254`、CGNAT `100.64.0.0/10`、`198.18.0.0/15`、`192.0.0.0/24`、`240.0.0.0/4`、广播与组播；NAT64 `64:ff9b::/96`、6to4 `2002::/16`、Teredo `2001::/32` 会解出内嵌 IPv4 再判断；**除发起前域名解析校验，还会在 TCP 拨号阶段对实际连接的 IP 再校验一次，阻断 DNS rebinding**（`internal/api/outbound_url.go`、`developer_js_ssrf.go`）。
- **静态阻断**：`require` / `process` / 浏览器对象 / `constructor.constructor`；`eval` / `Function` / `globalThis` / `setTimeout` 被标记为高风险能力。
- **预览模式**：沙箱预览里 `ctx.preview=true`，所有写操作返回 `dry_run=true`，不落数据。

除此之外的扩展点：
- **工单类型可增删**（`TicketTypes []string` + `/admin/ticket-types` POST/DELETE/PUT）。
- **config schema 可 PUT**（`/system/admin/config/schema`），配置文件结构本身运行期可改。
- **调度任务运行时参数**：`runtime_params` 声明 + 每次运行可传参（见 2.8）。
- **Emby 策略受限键清单**（`internal/api/emby_policy.go:7-27`）—— 一份 17 项的硬编码 `embyRestrictedPolicyKeys`，所有被管理用户强制置 false。

### 2.7 亮点设计（值得抄的）

**1. 单行 JSONB 快照 + 整体导出/导入/回滚**
`twilight_state` 一行装下全站业务数据。直接收益：迁移极简（`migration_export.go` 327 行 + `migration_import.go` 598 行就能整站搬迁）、备份/回滚是行级操作、schema 演进不需要 migration 脚本（新增字段给零值即可）。**代价见 2.8**。

**2. `EmbyAutoDisabled` —— 区分「谁禁用的」**
```

// internal/store/store.go:191-195
// EmbyAutoDisabled 表示当前的 Emby 停用是本系统按 Web 状态（停用/过期）自动做的，
// 而不是管理员单独封禁 Emby。Emby 状态对账任务只会把带这个标记、且 Web 已恢复的
// 账号重新启用；EmbyDisabled=false 时恒为 false。
```
对账/自动化最经典的坑就是「自动恢复误把人工封禁解开」。Twilight 用一个布尔标记解决，比「查审计日志反推」可靠得多。同类设计还有 `RebindEmbySuspended`（换绑期间亲自禁用的才恢复）和 `DisabledReason`（只有 `telegram_membership` 会被回群自动解禁处理）。

**3. 状态标记不变量集中在一次写路径**
`normalizeUserStateMarkers(old, u)` 在每次 `UpdateUser` 时统一维护五个衍生字段的一致性（见 2.4 代码块）。任何路径改状态都不会留下脏标记，不需要在每个业务分支手写清理。**这是我们做用户状态机时应该直接抄的形态。**

**4. 熔断式批量操作**
`enforce_group_membership` 的 `runtime_params`：`dry_run` / `auto_enable_rejoined` / `breaker_percent` / `breaker_max`。描述里写明「群组层级错误或拟停用人数超过熔断阈值时整轮中止」（`internal/api/scheduler_handlers.go:28`）。批量禁用几千账号前先 dry_run + 熔断，这是给运营人用的、不是给工程师用的设计。

**5. 敏感操作确认短语**
`internal/api/confirm_phrases.go`，例 `CLEAR_PENDING_EMBY_OK`。危险接口（清空待开通资格、批量删除）要求请求体带固定短语，防误点、防脚本误调。

**6. 乐观并发用 Revision**
`Ticket{Revision int64}`、`TicketUpdate{ExpectedRevision *int64}`、`MediaRequest{Revision}`、配置也有 `config_revision.go`。多人（多管理员 + 多端）同时改同一条工单时的冲突语义清晰。

**7. 调度器设计（见 2.8，确实值得参考）**

**8. 双数据源自动降级：播放记录**
`internal/api/emby_playback_reporting.go`：优先用 Playback Reporting 插件的 `POST /emby/user_usage_stats/submit_custom_query` 跑 SQL 读 `PlaybackActivity`，**探测失败自动降级到 Emby 活动日志**（`/System/ActivityLog/Entries`，由 `sync_emby_activity_logs` 每 10 分钟拉取）。细节处理很老练：
- 探测结果缓存 10 分钟（`playbackReportingProbeTTL`），避免每次同步都打一次 SQL；
- 单次同步上限 5000 行 × 20 页 = 10 万行（`playbackReportingMaxRows` / `MaxPages`）；
- 时间格式硬钉 `2006-01-02 15:04:05`，因为插件把时间存成 TEXT，字符串比较必须对齐否则 WHERE 直接落空；
- 兼容插件把 `columns` 拼错成 `colums` 的历史 bug —— **两个拼写都接**。

**9. 反 DoS 的边界检查**
`requireAdmin` / `requireAdminForUIDParam`（`app.go:1946-1965`）专门处理「同一 handler 同时挂 AuthUser 和 AuthAdmin 两条路由、路径上有 `:uid`」时普通用户传别人 uid 的场景；`authenticate`（`app.go:1057`）在非 Active 时按 `userExpiredOnly` 分派 `ErrAccountExpired`（引导续费）与 `ErrAccountDisabled`（引导申诉）——**过期和封禁给的是两条不同的用户引导路径**，这是 ember 没做的。

**10. 密码哈希的可演进迁移**
PBKDF2-HMAC-SHA256 / 600000 迭代，但更值得抄的是**迁移路径**：兼容旧 `salt$sha256(salt+password)`、`VerifyPassword` 接受 10000–1000000 的迭代范围、登录路径 `NeedsRehash` 无感重哈希。老库不需要停机刷密码。

**11. CI 文档门禁**
`scripts/check_docs_drift.go` 强制「每个注册路由必须在 docs 里出现」，`scripts/check-frontend-v2-coverage.py` 强制「前端每个 API 调用必须有已注册的 v2 路由」。**这是把「文档会漂移」当成工程问题而不是纪律问题来解的少数案例。**

**12. 资源访问的纵深防御**
受信代理 fail-closed（`trusted_proxy_cidrs` 为空即不消费任何代理头）；上传链路 `限流 → multipart → DetectContentType 嗅探 → 白名单 → 随机文件名 → ResolveWithinRoot(Abs→Clean→Rel + Lstat 拒符号链接) → WriteFileAtomicSync(O_NOFOLLOW|O_EXCL, 0700/0600)`；背景 CSS 白名单只允许 gradient 函数开头。

**13. 反 DoS 的索引化鉴权**
`APIKey` 的 hash 索引进 `State` 的 `apiKeyHashMap`，消除「攻击者用垃圾 key 打鉴权热路径」造成的 O(n) 遍历（`store.go:37-56` 注释直言这一动机）；`RequestCount` 走内存累加 + 30 秒批量落盘。

**14. Emby 改密的「中间态窗口」兜底**
`internal/api/emby.go:299-351`：Emby 改密是两步（`ResetPassword=true` 清空密码 → `NewPw` 设新密码）。第二步失败时会留下「密码为空」的账号——任何人 `AuthenticateByName` 都能进。Twilight 的处理是：用**独立 context（`WithoutCancel`）**绕过请求取消，把账号设成一个**随机门卫密码**把窗口封死，再返回原错误。建号后策略收紧失败也会删号回滚（`:277-289`）。这种「外部系统多步操作的失败态必须显式收口」是我们最容易漏掉的一类 bug。

**15. 路由级隐私红线**
`docs/reference/api-index.md` 明确规定：`/api/v2/emby/play-rank` 是**路由级 `AuthUser`**，不允许在 handler 内判断；曾存在的 `AuthPublic` `/api/v2/emby/now-playing`（会泄露「谁在看什么」）**已删除且禁止恢复**；唯一能看观看者身份的入口是 Admin 的 `GET /api/v2/admin/emby/now-playing`。把隐私决策绑在路由表上而不是散在 handler 里，是能被 CI 门禁检查的形态。

**16. 邮件验证码的存储形态**
只存 `CodeHash = HMAC-SHA256(id｜code)`（密钥由 `[Security].bot_internal_secret` 加前缀派生），常量时间比较；`max_attempts=5` / `resend_cooldown_seconds=60` / `code_ttl_minutes=10`；四类 purpose 隔离；找回密码只认 `EmailVerified=true`。对照 ember 的「明文验证码 + 校验即消费」，twilight 在这里更保守。

**17. 迁移包的纯函数化**
`internal/migration/format.go:26-49` 定义 `twilight-export/v1`：带 manifest SHA-256、文件/字节预算、Argon2id + AES-256-GCM，且不依赖 HTTP/FS。导出/导入这种一次性高风险功能做成纯函数，才可能被真正测到。

### 2.8 缺陷与不足（我们要超越的）

**P0 级**

1. **单行 JSONB `State` 是全站瓶颈与风险源**。任何一次写操作都要读-改-写整个 `State`，并发靠进程内单写锁；用户量到几千、`AuditLogs`/`RuntimeLogs`/`PlaybackRecords` 都是 `[]T` 切片时，单行体积与序列化开销会爆炸。它不可 SQL 查询——想按条件筛用户只能在 Go 里全量遍历（`internal/api/admin_extra.go:667-676` 就是遍历全部 Users 手动过滤）。**也不能做行级权限隔离，一次 bug 就可能全量泄露。**
2. **`internal/store/store.go` 5975 行的 God Object**。整个存储层一个文件，业务方法/序列化/锁/迁移/校验全混在一起。这是 1 的结构性后果，不是纪律问题。

**P1 级**

3. **无付费能力**。全仓 `grep -i "stripe|payment"` 在 `internal/` 无命中。续期只有「兑换码 / 签到积分 / 管理员手动」三条路。想变现得从零做计费。
4. **Emby Policy 授权粒度极粗**。只有一份 17 项的全局硬编码黑名单 `embyRestrictedPolicyKeys`（`emby_policy.go:7-27`）加全库授权 `embyGrantAllLibraryAccess`（:33）。**没有套餐/等级对应的媒体库模板**——无法表达「银卡只看电影、金卡看全部」。对比 ember 的 `plan_group_media_libraries` + `plan_group_emby_policy_templates` + `user_media_library_preferences` 三张表，这是 twilight 最大的功能缺口。
5. **无分级权益模型**。`Role` 只有 4 个整型值（admin/normal/whitelist/unrecognized），`EmbyGrantLocked` 是个布尔锁，没有「订阅等级 / 有效期 / 权益快照」结构。用户等级与到期是绑在 `User` 行上的单一 `ExpiredAt`，无法一个用户同时持有多个组的独立到期时间。
6. **CSRF 防护被禁用，且是文档承认的取舍**。`internal/api/csrf.go.disabled`（改名而非删除）+ `app.go:1492-1508` 整段注销 + `errcode.go:45` 注释掉 `ErrCSRFTokenInvalid`；`app.go:864-866` 硬编码「严禁修改 CSRF/CORS - V1 生产兼容性要求」把技术债升级成了禁令。`docs/guides/security.md` 明写「无 CSRF 令牌、无额外来源校验」，仅靠 `SameSite=lax`。叠加已知边界 M2（`cors_origins` 空或 `*` 时反射任意 Origin + `allow_credential=true`，且启动只打 Info）后，这是一个**可被第三方站点利用的带凭据跨站读写**组合。（同类不一致见架构层面第 20 条。）
7. **无支付/无发票/无退款流**——同上第 3 点的延伸。

**P2 级**

8. **文档漂移是仓库级模式，不是个案**。已核实的硬冲突 ≥ 6 处，且分布在「自称权威」的参考文档之间：

   - 数据库恢复确认短语：`backend.md:295` `RESTORE_DATABASE` ↔ `backend-api.md:1817/1844` `RESTORE_DATABASE_BACKUP`。
   - 默认 API Base URL：`api-index.md:27` `/api/v1` ↔ `backend-api.md:19` `/api/v2`（代码事实：前端 `api-request.ts:12-13` 默认 v2）。
   - 上传限流：`features/background.md:46`、`security.md:138` 60/min ↔ `backend-api.md:286` 10/60s（差 6 倍）。

9. **测试与实现混在同一目录**。`internal/api/` 下 165 个非测试文件 + 111 个测试文件，文件名前缀相同（`admin_user_handlers.go` / `admin_user_v2.go` / `admin_user_refresh.go`）。可读性差。（正面看：35k 行测试对 73k 行产品代码，测试密度高于 ember。）
10. **v1/v2 双套路由并行**，V1 337 条 + V2 380 条 = **717 条**，同一个 handler 常常挂两条路由（`handleUpdateMe` 同时出现在 `/api/v1/admin/me/update` 和 v2）。V2 的「补全段」（`routes_v2.go:417-421`）自述 `handlers are the audited V1 implementations … contract parity, not behaviour change`。两套鉴权口径需同步维护。
11. **主状态文档没有版本化迁移路径**：DDL 靠 `ADD COLUMN IF NOT EXISTS` + `UPDATE ... WHERE` 幂等重放补列，只有 4 个子系统带 `*_schema(version)` 版本表。对比 ember 的 `schema_migrations` 记账 + advisory lock + checksum 防改写，这是明确的退步。
12. **前端 47 个 `page.tsx` 全部 `"use client"`**，完全放弃 RSC/SSR 首屏与 ISR；首屏需 JS 下载 → 水合 → `initialize()` → `GET /users/me` 才出内容。管理端 21 个页面纯靠后端鉴权，layout 的 role 检查仅在客户端。
13. **依赖治理脏**：`@tanstack/react-query` / `framer-motion` / `date-fns` / `recharts` 在 `src/` 全量 grep 命中 0，但 `webui/README.md:11-13` 仍列为技术栈；`typescript: ^6.0.3` 是公开渠道不存在的版本，而 `Dockerfile:32` 用 `--frozen-lockfile` 构建；`next: ^16.3.6` 配 `eslint-config-next: 14.2.35`。CSP `script-src 'unsafe-inline'`（nonce 方案在 Next 16 上三次收紧失败后被放弃）。
14. **前端 API 层与后端耦合靠硬编码**：`/admin/stats`、`/admin/device-audit` 不在 `adminNavItems`，侧栏高亮靠 `sidebar.tsx:167-169` 的特例；`settings/background` 是纯重定向死路由。
15. **配置为 TOML + 可运行期 PUT schema**：灵活但容易与代码期望脱节（`config_revision.go` 的存在说明已踩过坑）。
16. **前端绑 OpenNext/Cloudflare 备份路径**（`open-next.config.ts` + `wrangler.jsonc`），与 Go 单二进制自托管的简洁性不匹配；Docker 构建期/运行期变量分家，漏设 `BACKEND_URL` 时容器内 API 静默打到 `localhost:5000`，无 fail-fast。

**架构层面**

17. **调度任务与实现强耦合**：22 个 job 硬编码在 `scheduler_handlers.go` 的字符串表里，新增任务要改 4 处（handlers 表、`runner` switch、`defaultTriggerSpec`、前端页面），`enabled` 默认值也写死在源码。这不是「插件式调度」，是「有 UI 的硬编码」。
18. **没有服务分层**。`internal/api/` 165 个非测试文件里 handler、业务、Emby 客户端、JSON 工具混在一起，光 Emby 就散成 `emby_client.go` / `emby_service.go` / `emby_policy.go` / `emby_reconcile.go` / `emby_activity.go` / `emby_inventory.go` / `emby_media.go` / `emby_play_rank.go` / `emby_sessions.go` / `emby_device_*`。难以为单点做替换测试，也难以约束依赖方向。
19. **Emby 与 Jellyfin 兼容是口号级的**。只在一处注释提到 Jellyfin（`emby_policy.go:3`、`config_admin.go:1076`），代码里没有 Jellyfin 适配分支；认证头固定 `X-Emby-Token`（`emby_client.go:77`）。
20. **同仓两套 SSRF 标准**：JS 沙箱的 `fetch` 有 DNS + 拨号双阶段 IP 校验（防 rebinding），但服务端出站 HTTP 只拦链路本地与云元数据，放行 RFC1918/CGNAT/ULA。同一个安全目标两套标准，说明「沙箱」是专门加固的、而通用出站没跟上。

| 在线支付与 Webhook 幂等 | 1/2（ember） | 🟢 | 占位行 + Idempotency-Key 是好解法；`paid_review` 人工兜底不可省 |
| 签到 / 积分 / 活跃换时长 | 1/2（twilight） | 🟢 | 免费用户留存的关键机制 |
| 设备信任 / 免密续期 | 1/2（twilight） | 🟢 | 减少登录摩擦 |
| 设备与客户端黑名单 / 强制下线 | 2/2 | 🟢 | 共享账号治理的必要手段 |
| 验证码的安全存储（哈希 + 常量时间比较） | 1/2（twilight） | 🟢 | 明文验证码落库时，一次只读泄漏即可撞开所有未验证邮箱 |
| 最后管理员保护（禁止删/降最后一个 admin） | 1/2（twilight） | 🟢 | 自锁死是自部署系统最常见的翻车方式 |
| 路由级隐私红线（谁在看什么只允许 Admin） | 1/2（twilight） | 🟢 | 把隐私决策绑在路由表才能被 CI 检查 |
| 外部系统多步操作的失败态收口 | 1/2（twilight，Emby 改密） | 🟢 | 建号/改密/授权都是多步，中间失败必须显式封口或回滚 |
| IP 黑名单 / 登录日志 / 反暴力破解 | 1/2（twilight） | 🟢 | 无此为裸奔（ember 仅靠 Turnstile + 限流） |
| 2FA / 二次验证 | 1/2（twilight） | 🟢 | 管理员账号是最高价值目标 |
| 审计日志（谁在什么时候改了什么） | 1/2（twilight 完整 + ember 部分） | 🟡 | 多管理员场景下是问责基础 |
| 管理 API Key（外部集成） | 2/2 | 🟢 | 权限位 + 限速 + 禁止自提权（twilight `handleForbiddenSelfPermission`）都要有 |
| 插件 / 扩展机制 | 1/2（twilight Goja） | 🟢 | **本领域最被低估的需求**：站长需求千差万别，硬编码功能永远追不上 |
| 定时任务可配置（调度/参数/重试/熔断/告警） | 2/2（twilight 明显更强） | 🟡 | ember 是硬编码 cron 表达式 + 改完要重启；twilight 是 DB 队列 + 运行时参数 + dry_run + 熔断 |
| 数据库备份 / 恢复 / 迁移 | 1/2（twilight） | 🟢 | 自部署用户的刚需，缺它一次误操作就毁站 |
| 配置中心（运行期可改、敏感值加密、空值语义） | 2/2 | 🟢 | ember 的「空值=关闭/回退/继承」语义与分组连通性测试是好设计 |
| 数据模型可选 SQL 查询 | — | 🔴 | twilight 的单行 JSONB 是反面教材；必须有可索引的关系模型 |
| 反枚举 / 反账号探测 | 1/2（ember，做得很好） | 🟢 | 登录/注册/找回/TG 绑定四条路径都要统一文案 + 统一限流消耗 |

### 3.4 给本项目的结论

1. **必须做的重合项**：账号生命周期自动化、兑换码/邀请（且要**带关系树**）、到期与封禁、邮箱/TG 通知、求片+自动下载、播放记录与排行、设备管理、API Key、审计、可配置调度器。
2. **两者都没做对、我们要做得对的两件事**：
   - **单一用户状态机**。定义 `status: pending | active | expired | banned | deleted` + `statusReason`（区分 `manual` / `system:expiry` / `system:telegram_membership` / `system:invite_detach`），并提供 twilight 式的不变量归一化函数。同时保留 ember 的正确洞察：**「能不能登录」与「能不能播放」必须是两个独立字段**。
   - **按等级控制 Emby 媒体库可见性**。抄 ember 的三表结构（分组媒体库模板 / 分组 Policy 模板 / 用户偏好），因为这是唯一能卖出差价的机制。
3. **插件机制的取舍**：Twilight 的 Goja 沙箱方向对，但「进程堆 256MB 中断 + 单次 8s + 内存交互状态 512 条上限」这套是止损不是隔离。更好的形态是 **Webhook + 事件总线 + 独立进程脚本**，而不是在同进程内跑第三方 JS。
4. **持久化形态**：走 ember 的关系模型 + SQL migration，不要走 twilight 的单行 JSONB。但可以吸收 twilight 的「整体快照导出/导入」作为**运维功能**（备份/搬迁），而不是作为**存储形态**。
5. **要超越的具体短板**：注册审批档位、状态原因、邀请关系树、按等级媒体库授权、工单/公告、签到积分、2FA、IP 黑名单与登录日志、备份/迁移、可配置调度器（含 dry_run 与熔断）、敏感操作确认短语、Revision 乐观并发。
6. **状态标记不变量要集中**。twilight 的 `normalizeUserStateMarkers(old, new)` 值得直接借鉴：所有衍生标记（停用原因、自动禁用标记、解绑时间、资格发放时间）在**唯一写路径**上维护，任何业务分支改状态都不会留脏数据。我们对「过期 / 封禁 / 到期回退 / 邀请连坐」这些多来源状态，必须一开始就这么做。
7. **多进程共享状态必须上乐观并发**。twilight 因为拆了 api/bot/scheduler 三进程，被迫在单文档上加 `version` 列并在 UPSERT 命中 0 行时回滚重试（`store.go:58-65`，注释里的根因是「用户建了工单、TG 也收到了，工单却后来凭空消失」）。只要我们的部署形态允许 api 与定时任务分进程，这一层就必须有——无论是在单文档上还是按行做 `WHERE updated_at = ?`。
8. **文档必须能被验证，否则必然是负担**。twilight 有 9403 行文档、两条 CI 门禁，仍然出现了 ≥6 处硬冲突，其中 `/admin/whitelist` 一处会直接导致实现错误。结论：文档的每一节都要带**源码位置索引**（像 ember 的 `docs/system-architecture.md` 那样逐条写 `services/xxx/yyy.go`），并且**状态、路由、数据模型这三类事实只允许有一个出处**，其他文档一律引用而不复述。
9. **安全边界不要同仓两套标准**。twilight 的 JS 沙箱 `fetch` 有 DNS + 拨号双阶段 IP 校验，而服务端通用出站 HTTP 只拦链路本地（放行 RFC1918/CGNAT/ULA）。这种不一致本身就是攻击面提示：**把出站校验做成一个共享的 `validateOutboundURL` 组件，所有出口（沙箱、探测、webhook 回连、代理）都必须走它。**
