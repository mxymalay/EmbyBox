### 1.2 解决的痛点

1. **Emby 多站点的反代配置分散**：传统做法是每个站点一段 Nginx `location`，改一次要动 Nginx 并 reload。meridian 把每条线路的协议/地址/端口/UA/限速/配额变成面板里的一行数据，落 SQLite，运行时动态起停。
2. **Emby 播放链的「真实后端 URL」泄漏**：Emby 的 `/Items/{id}/PlaybackInfo`、`.m3u8`、`.mpd` 会返回第三方 CDN/直链地址，客户端直连即绕过限速、配额和审计。meridian 用同源加密 capability（`/_meridian/d/<capability>`）把这些地址重写并代理（`cmd/meridian/dynamic_rewrite_core.go`、`dynamic_capability_issuer.go:85`）。
3. **共用一个入口时 Host/路径冲突**：一台机器一个 443 要给多个站点。meridian 提供四种入口模式：独立端口、共享 Host、路径前缀、域名前缀（`site_routing.go:455-493`），共享入口只接受精确 Host（`app_core.go:96-159`）。
4. **UA/身份策略需要按站点分化**：Infuse、Emby Web、Emby Theater 拿到的转码/直链策略不同，meridian 内置 UA 预设并支持自定义三元组（UA + Client + Version）与透传（`site_config.go:17-21`、`site_config.go:100-145`）。
5. **无法回答「谁在占流量」**：按站点流量、限速、配额、请求日志分类统计、SSE 实时大盘（`traffic_quota.go`、`request_logs.go:418`、`app_traffic.go:172`）。
6. **证书自动化**：面板内置 Cloudflare DNS-01 泛域名证书申请与 12h 轮询续签（`panel_acme.go:325`、`panel_certificate_renewal.go`）。
7. **流媒体场景下不能有整体写超时**：`ReadTimeout/WriteTimeout = 0`，靠 per-endpoint body 上限和请求头上限保护面板（`main.go:288-291`）。

### 1.4 反代核心实现（关键代码逻辑）

**入口分流在面板 listener 内完成，站点可不占端口。** `main.go:283` 把整棵 mux 包进 `publicHostRouter`：

```
main.go:281  srv.Handler = publicHostRouter(panelBodyReadDeadline(securityHeaders(mux, trustedProxies)))
app_core.go:96-159  按 Host 查 publicHosts → 站点 handler；否则按 pathPrefixes 匹配 → strip 前缀后转发；
                    都不是且 host != panelHost → 421
```

关键点：**共享 Host 模式下站点流量和面板流量共用同一个 `http.Server`**，所以 `ReadTimeout/WriteTimeout` 必须为 0（`main.go:288-289`），否则长视频流会被 30s 掐断。站点级超时保护改由 per-endpoint body 上限与 `securityHeaders` 承担。

**ReverseProxy 装配**（`proxy_start.go:163-294`）：

```
163  proxy := &httputil.ReverseProxy{Transport, Rewrite, ModifyResponse, ErrorHandler}
150  proxyTransport = http.DefaultTransport.Clone()
151  TLSClientConfig = secureTLSConfig("")          // TLS1.2+、校验证书链/有效期/主机名
152  ResponseHeaderTimeout = 30s
153  MaxIdleConnsPerHost  = 32
```

`Rewrite`（`proxy_start.go:165-229`）按顺序做六件事：判定是否命中动态发现 → 选 upstream（主站 / 播放回源）→ `applyUpstreamURL` 拼接 base path 与 query（`site_routing.go:121-132`）→ `Out.Host = upstream.Host` → 客户端 IP 与 UA 策略（`proxy_headers.go:119`）→ 跨 authority 时重建精简头（`crossAuthorityRedirectHeadersWithClientIPMode`）；命中备份线路时再注入 failover plan（`proxy_start.go:201-204`），并对 PlaybackInfo 类请求删 `Accept-Encoding/Range/If-*` 以便改写正文（`proxy_start.go:224-228`）。

`ModifyResponse`（`proxy_start.go:231-259`）承担 URL 回写与 **入口前缀的反向改写**：`prefixPathIngressResponse` 同时改 `Set-Cookie` 的 `Path` 和 `Location`（`site_routing.go:341-406`），并处理 Emby/Jellyfin 把 `X-Forwarded-Prefix` 放在自身 app base 之后导致的 `/emby/<prefix>/...` 错位（`site_routing.go:251-279`）。

**流式转发的计费链**是一层层 `http.ResponseWriter` 包装，顺序为：`requestLogResponseWriter` → `rateLimitedWriter`（有站点限速时）或 `meteredWriter` → 可选 imageCache / progressCoalescer → ReverseProxy。

- `meteredWriter.Write`（`proxy_io.go:75-96`）：先向 `trafficQuotaState.reserve` 申请字节，写完后 `settle` 归还差额；被截断时返回 `errTrafficQuotaExceeded`。**计费发生在内核 write 之后，而不是等 io.Copy 收尾**，所以中断的流也能精确入账。
- `rateLimitedWriter.Write`（`proxy_io.go:157-233`）：以 `start` 时刻为基准算「本请求已允许字节 = elapsed × bytesPerSec」，超出则 `time.After(10ms)` 或 `ctx.Done()` 轮询等待，**只有下行被限速，上行不限**（`websocket_proxy.go:166-171` 注释同义）。
- `trafficQuotaState.reserve`（`traffic_quota.go:67-100`）在 `trafficBillingModeOutbound` 下对入站直接放行不计数，其余情况 `usage += allowed` 并对超额返回 `allowed < requested + errTrafficQuotaExceeded`。
- 请求体方向用 `meteredReader`（`proxy_io.go:114-143`）对称处理。

**WebSocket 完全绕过 ReverseProxy**，手工实现（`websocket_proxy.go`）：先拒绝带 body 的升级（`:24`）→ `Hijack` 并登记到 `hijackedConns` 以便停机时强关（`:33-47`）→ 按 `ws/wss` 直连后端（`:50-71`）→ 自己写 request line 和头（`:78-101`）→ **必须读到 `101 + Upgrade: websocket + Connection: upgrade` 才继续**（`:130-139`），否则回 502 且不转发 body——注释明确说明这是为了不把这条路径变成「无限速无限额的裸通道」；→ 双向 `io.Copy`，每块经 `tunnelWriter` 计量，下行限速，先关闭的一侧触发对方 teardown，两条 goroutine 都退出后请求才离开 `activeRequests`（`:164-181`）。

**跨 authority 信任域剥离**是反复出现的模式：主站 → 播放回源、重定向跳转、动态发现目标，只要 `redirectHostKey` 不同就删 `Cookie`、`Authorization`、Emby token、固定上游 Header、转发头（`site_routing.go:63-88`、`proxy_start.go:190-195`、`upstream_headers.go:289-299`）。`stripCookieByName` 对畸形 Cookie **整体丢弃**而不是保留未匹配项（`proxy_headers.go:86-113`）。

**动态发现 capability** 是这套代码里最重的一块。`newDynamicTransportWithDialerTimeout`（`dynamic_network.go:544-634`）建一个「一连接一 host、禁 keepalive/压缩/HTTP2」的 Transport，`DialContext` 会校验 authority 与 `expectedHost/expectedPort` 完全一致，然后只在**预先解析并校验过的 pinned IP 列表**里按 `network`（tcp4/tcp6）筛族重试，任一失败即报错。`resolveDynamicURLIPs`（`dynamic_network.go:487-527`）用 30 余条 forbid 前缀（`dynamic_network.go:20-52`）拒绝私网/回环/链路本地/CGNAT/metadata，并对 host 做 IDNA Lookup + PublicSuffix 校验（`dynamic_network.go:64-129`）。

### 1.5 线路调度与探活算法

这是 meridian 与「延迟优先调度」的最大分歧点，需要精确描述。

**调度是「顺序 + 冷却 + 粘滞 + 恢复探测」，与延迟无关**（`upstream_failover.go:23-132`）：

```
upstreamFailoverState{ preferred, preferredUntil, failedUntil[map], primaryProbeAt }
failoverCooldown          = 30s
failoverPreferredLifetime = 5min
maxFailoverTargets        = 8            // 1 主 + 7 备
```

`ordered(targets, now)` 把目标分三类重排：`preferred`（当前粘滞的成功线路）→ `healthy`（无冷却）→ `cooling`（冷却期内，最后才试）。同时它用 `primaryProbeAt` 做**限流式回切探测**：只有当当前有 preferred 备线、主线路不在冷却、且距上次探测超过 30s 时，才「预订」一次请求去打主线路；并发请求继续走备线，避免主线路半死不活时被雪崩打回。

`failoverTransport.RoundTrip`（`upstream_failover.go:194-261`）只在请求「可重放」时逐条重试：

- `isFailoverRequestEligible`（`:163-179`）：GET/HEAD 恒真；POST 仅限 PlaybackInfo 且 body 可 replay、长度 ≤ `limits.MaxBodyBytes`、无 chunked/trailer；带 Upgrade 意图一律不重试。
- 重试判定用 `isRetryableUpstreamStatus`：仅 500/502/503/504（`:134`）。成功（2xx/3xx）调 `markSuccess` 写 preferred；失败调 `markFailure` 写 30s 冷却并清 preferred。
- 不可重放的请求走 `preferredTarget` 单次切换（`:199-221`）：不重试，但如果当前有健康备线就直接换过去。
- 客户端主动取消（`isClientRequestCancellation`，`proxy_io.go:22`）**不记失败**，避免用户拖进度条把线路打进冷却。

**探活与测速是两件不同的事，都被做成了「手动/一次性」**：

- `/api/upstream-test`（`app_sites.go:15-43`）→ `probeSiteHealth` → `probeTargetHealth`（`diagnostics.go:267`）：顺序尝试候选 URL（`healthProbeURLs`），`time.Since(start).Milliseconds()` 记为 `latency_ms`（`diagnostics.go:308-310`）；无 2xx 时按 `probeStatusRank` 选最佳可达；播放回源收到任意 HTTP 响应即标 `reachable` 并带状态码 warning。前端按 <200ms / <800ms 分好/警告/差三档（`web/static/js/pages/sites.js:1660`），诊断页用 <100/<300 另一套阈值（`web/static/js/pages/diag.js:343`）。
- 前端「线路测速」按钮是**串行** for-await 逐行打 `/api/upstream-test`（`sites.js:1684-1697`），本质是 N 次 TCP+TLS+HTTP 往返，没有持续采样、没有滑动窗口、没有自动选线。
- **注意**：`pingCache`（`legacy_ping_cache.go`）名字有误导性，它缓存的是 Emby 的 `/System/Ping` 响应（2s TTL、256 条 LRU、含 inflight coalescing），目的是削掉 Emby 客户端的高频心跳，不是探活。

**IPv4/IPv6 双栈支持下放在 dial 层**：`newDynamicTransport` 的 `DialContext` 里 `(network == "tcp4" && ip.To4() == nil) || (network == "tcp6" && ip.To4() != nil)` 会跳过不匹配的族（`dynamic_network.go:600-606`），并在整个 pin 列表上轮询直到 `totalDialTimeout` 用尽。站点主回源走的是 `net/http` 默认 Happy-Eyeballs，没有显式双栈偏好配置。

- **加速**：`ping_cache_enabled`、`image_cache_enabled`、`progress_coalescing_enabled`、`asset_cache_enabled/ttl/max/rules`
- **配额**：`traffic_quota`、`traffic_used`、`traffic_used_in`、`traffic_used_out`、`speed_limit`

`traffic_used_in/out` 是从旧字段 `traffic_used` 拆分的：迁移时先 `ADD COLUMN ... DEFAULT -1`，再 `UPDATE sites SET traffic_used_in=traffic_used/2, traffic_used_out=traffic_used-(traffic_used/2) WHERE traffic_used_in<0`（`:370-390`）——老库的「总流量」被对半拆成入出，语义上不可还原，属于兼容性妥协。

`dynamic_observations` 由 `dynamic_observation_schema.go` 单独管理（有 `ensure` / `validate` / `prune` 三步），记录动态发现的目标、决策、reason code、3xx 状态，保留 30 天、每站点 500 条、全局 10,000 条（`README.md:321`）。

内存态与持久态严格分离：`upstreamFailoverState` 注释明确「进程本地，瞬时网络故障不得改写数据库里的线路优先级」（`upstream_failover.go:21-22`），`ProxyInstance` 里 `bytesIn/Out`（当前周期累计）、`cumulativeBytesIn/Out`（进程累计）、`persistedBytesIn/Out`（已落库）三套计数器并存（`proxy_manager.go:44-48`）。

### 1.7 亮点

1. **默认拒绝的入口安全模型**。`host` 模式并不只是「多走一层 Host 判断」——它强制要求 `PANEL_BIND_ADDR` 回环、或有非空 `TRUSTED_PROXY_CIDRS`、或面板 TLS 已启用，否则直接拒绝启动（`main.go:185`、`proxy_manager.go:418-429`）。运行期还有第二道：非回环 peer 且直连非 TLS 且 Host 命中站点时返回 403（`app_core.go:113-118`）。第三道是 TLS SNI 必须等于 Host，否则 421（`app_core.go:100-108`），且回环健康探针若带任何转发头就不放行（`app_core.go:65-94`）。

2. **capability 机制把「SSRF 面」压缩成「可审计的加密令牌」**。外部 URL 不会被原样透出，而是被换成 AES-GCM 加密的 `/_meridian/d/<capability>`；capability 绑定站点、策略版本、过期时间，并且客户端附加的 query（例如 `X-Emby-Token`）**不改变签名目标**（`README.md:315-317`）。这是把开放代理风险转成密码学问题，而非靠黑名单。

3. **三档 Profile 是完整可审计预设，而不是复选框集合**。V1.12 明确移除了前端的来源勾选与 HTTPS 降级开关，改由后端按 profile 统一决定来源与网络边界（`README.md:306`、`dynamic_policy.go:163-233`）。Safe=仅 https:443 / 3 跳 / 256 authority；Compatible=http(s) 任意端口 / 5 跳 / 1024 authority / 允许 HLS+DASH；Extreme=10 跳 / 4096 authority / 允许 303 与扩展结构兼容（`dynamic_policy.go:169-231`）。还有全局硬上限（16384 authority、131072 capability、1024 stream、每分钟 2400 新 authority、32 DNS worker、256MB 解析内存，`dynamic_policy.go:47-72`），并暴露 `rollback_readiness` 用于降级前自检（`README.md:380`）。

4. **流量计费用「预留-结算」而不是「累加」**。`trafficQuotaReservation.settle` 按实际写入量返还差额，并且**代际检查**（`generation`）保证周期翻转后老的预留不会污染新周期计数（`traffic_quota.go:30-65`）。配额判定在 `Write` 内做，超出即截断，避免「先写满再 403」的经典问题。

5. **限速实现只有下行、无缓冲放大**：按「自请求开始以来的时间预算」放行，延时用 `ctx.Done()` 可中断，避免进程退出时挂住（`proxy_io.go:180-198`）。

6. **备份恢复是一套有回滚的协议而非一次文件覆盖**：`MRDBKP01` 魔数 + 16B salt + scrypt(32768,8,1) + AES-GCM（AAD 绑定头部）→ ZIP 内白名单 entry 表并各自限长（`backup_restore.go:26-55`）；恢复走 `.restore-pending` → 启动时 `applyPendingRestore` → 打开数据库失败则 `rollbackAppliedRestore` → 全部初始化成功才 `finalizeAppliedRestore`（`main.go:94-116`、`main.go:308-319`）。恢复后强制 `InvalidateAllSessions`（`main.go:112-116`）。

7. **凭据三层密钥分离并带迁移路径**：`JWT_SECRET` / `UPSTREAM_HEADER_KEY` / `DYNAMIC_ROUTE_KEY` / `MERIDIAN_SECRET_KEY` 必须两两不同，启动期强制校验（`main.go:87-92`）；`storedCredentialSecrets()` 保留 `[新key, 旧JWT派生key]` 以便一次性迁移历史密文（`credential_secrets.go:5-9`）。

8. **停机语义严谨**：`siteIngressClosedError` 区分「闸门已关但 drain/flush 未完成」，要求调用方不得把 DB 行留成 enabled（`proxy_manager.go:93-101`）；替换实例时先 flush 旧实例再停，停完再 flush 尾部字节，失败则保留旧实例在 map 里等重试（`proxy_start.go:545-576`）；进程退出前还有第三次 `GracefulShutdown(2s)` 兜底尾部计数（`main.go:377-383`）。

9. **对 Emby 客户端怪异行为的实战适配**：`/emby/<prefix>/...` 与 `/jellyfin/<prefix>/...` 双向归一（`site_routing.go:213-298`）、保留 `/videos` 等易冲突路由名（`:281-298`）、`normalizeEmbeddedDynamicCapabilityRequestPath` 接受客户端自行补 `/emby` 前缀（`site_routing.go:538-554`）、`isKnownMediaApplicationRoute` 白名单。这些是只有真跑过 Emby 才会写出来的代码。

10. **日志脱敏是默认行为**：`redactUpstreamURL` 只留 `scheme://host`（`site_routing.go:56-61`），请求日志有独立的写入字段与展示字段两组开关（各自 10+ 开关位），可在「记录得动」与「少暴露」之间取舍（`database_migrations.go:203-220`）。

### 1.8 缺陷

1. **没有延迟感知调度，也没有主动探活**。`failover` 只认 500/502/503/504 这类硬失败（`upstream_failover.go:134`），对「能连上但慢 10 倍」的线路毫无反应；延迟数据只存在于「管理员手点一次测速」的那一瞬（`app_sites.go:35`），既不落库也不参与 `ordered()`。对比 `bubble-emby-admin` 的线路管理（最近 10 次检测 → 正常/离线/波动），meridian 反而落后。

2. **单管理员、无 RBAC、无审计**。`SECURITY.md` 明写「任何持有有效会话的请求都可以执行所有管理操作」「没有审计日志，操作不可追溯」。对多人运维的 Emby 站来说这是硬伤，而它偏偏是最需要「谁改了回源地址」这类溯源的系统。

3. **`traffic_used` 对半拆分的迁移不可逆**，老库升级后入/出站拆分必然错误，只能等新周期自然翻篇。

4. **无通用 API 限流**。频率限制只覆盖登录入口（`SECURITY.md`）：`maxLoginFailures=5 / 1min / lock 60s`（`main.go:29-33`）。备份导出、诊断探针、`/api/upstream-test` 这些重操作没有节流。

5. **共享 Host 模式下站点与面板共用 Server 的连接与超时预算**。`limitListener(2048)` 只对独立端口站点生效（`proxy_start.go:510`），共享 Host 站点没有连接闸门；面板的 `ReadHeaderTimeout=10s`/`IdleTimeout=120s` 也同时约束了站点流量。

6. **`main.go` 没有路由分组与中间件链**，30+ 个 `mux.HandleFunc` 平铺，每个都手写 `cors(app.authMiddleware(...))`（`main.go:238-270`）。漏写一个 `csrfMiddleware` 不会有编译期错误。

7. **`app_sites.go:15` 的 `handleUpstreamTest` 会把探针结果里的错误字符串直接回给前端**（`:41`），同时 `probeSiteHealth` 对管理员可控的 URL 发起服务端请求——虽然有 `normalizeTargetURL` 与 codeql 注释，但它接受**任意 host:port**，是一个面向已认证管理员的开放探针（在单管理员模型下影响有限）。

8. **诊断语义容易误导**。`player_reachability` 探针收到 4xx/5xx 也判 `reachable`（`diagnostics.go:323-331`），README 自己也承认「探针可达不等同于完整 Emby 播放可用」（`README.md:359-366`）。运维人员看到绿色很容易误判。

9. **缓存功能互斥约束靠前端拦截**：「备用线路不能与主回源固定请求头同时使用」（`sites.js:2027`），后端只是不注入 failover plan（`proxy_start.go:201-202`），配置组合面上并不可解释。

10. **`dynamic_*` 系列复杂度极高**（capability issuer/service、rewrite core、hls/dash/playbackinfo rewrite、observations、network，合计 8,000+ 行）。这是一台真正的流媒体代理，但也意味着任何改动都可能触碰 HLS 属性解析或 DASH 模板这类高副作用代码，回归成本高（因此测试文件也最厚）。

### 2.4 核心实现：双擎数据路由

这是整个项目最值得学的一块，`app/core/database.py:91-187` 用一个**SQL 拦截器**把「上层业务写标准 SQL」与「底层数据从哪来」彻底解耦。

```python
def query_db(query, args=(), one=False):
    mode = cfg.get("playback_data_mode", "sqlite")
    is_playback_query = "PlaybackActivity" in query or "PlaybackReporting" in query
    if mode == "api" and is_playback_query:
        full_sql = _interpolate_sql(query, args)                    # :78 参数内联
        url = f"{host}/emby/user_usage_stats/submit_custom_query"    # :104 插件端点
        payload = {"CustomQueryString": full_sql}
        ...
```

工作流：业务层（`stats.py`、`report_service.py`）永远只写 `SELECT ... FROM PlaybackActivity WHERE ...`；`query_db` 判断「模式 == api 且查询触达播放表」，就把 SQL 内联参数后 POST 给 **Playback Reporting 插件的 `submit_custom_query`**，其余查询（`users_meta`、`media_requests`、`tv_calendar_cache`、`gap_records` 等本地表）继续走 SQLite。

API 返回格式兼容做了三层兜底（`:112-160`）：

1. 插件返回 `{"colums": [...], "results": [[...]]}`（连作者的拼写错误都兼容了）：按表头 zip 成 dict，并对纯数字字符串做类型推断回 `int`（`:135-144`）。
2. 返回 `{"results" | "Items": [...]}` 的正常结构。
3. 直接返回 list 或标量。

随后用 `APIRow`（`:56-76`）包装成「伪 `sqlite3.Row`」：同时支持 `row[0]` 下标访问、忽略大小写键名访问、缺失键返回 `None`。这样 `stats.py:92` 的 `query_db(...)[0]['c']` 这种调用在两种引擎下**完全不需要分叉**。

值得单独指出的设计细节：

- `get_base_filter(user_id)`（`:189-204`）统一注入 `UserId` 过滤与 `hidden_users` 排除，两种模式下行为一致。
- API 失败时**静默降级**到 SQLite（`:172-176`），SQLite 文件不存在时返回 `None` 而非抛异常，配合上层大量 `try/except: return {"status":"error", ...}` 形成「永不 500」风格。
- 但降级是隐式的：`query_db` 只 `print` 不告警，且 API 分支失败后**不 fallback 回 SQLite**——如果 `emby_host` 可达但插件未装，返回空结果而不是本地数据。

`media_adapter.py:28-46` 是配套的第二层适配：`_build_url` 处理 `/emby` 前缀差异（Jellyfin 剥掉、Emby 补上），`_get_headers` 处理 `X-Emby-Token` vs `Authorization: MediaBrowser Token="..."`，并**主动从 query params 里删掉 `api_key`**，只用 Header 鉴权。

### 2.5 缺集补货与求片流转闭环

**缺集扫描**（`gaps.py:84-139`）的算法：

```
1. GET /System/Info/Public → server_id，并判定是否新版路由 (/item?id=)
2. 建表 gap_perfect_series（完结免检）、gap_scan_cache（结果缓存）
3. 读 gap_records 造 lock_map，key = "{series_id}_{season}_{episode}" → status
4. 拉全库 Series（Fields=ProviderIds 取 Tmdb），剔除已有「免检金牌」的
5. 一次性拉全库 Episode（Fields=IndexNumberEnd），构建 global_inventory[series][season] = {ep...}
   —— 支持 IndexNumberEnd 把 E01-E02 合并文件展开成 {1,2}
6. 10 线程并发 process_single_series：TMDB 查季列表 → 逐季查集列表 →
   只比 air_date < today（未播不算缺）且不在 local_inventory 且 lock_map 未标记的
7. 结果写 gap_scan_cache（单行 id=1 JSON blob）
```

`process_single_series`（`:42-82`）里有两个值得注意的判断：`if not air_date or air_date >= today: continue` —— **未来集不算缺集**；`tmdb_status in ["Ended","Canceled"] 且无缺集` 时写入 `gap_perfect_series`，之后该剧永久跳过，这是对「完结老剧重复全量扫」的优化。

**核销**用 `run_verify_task`（`:164-213`）：重新按 `ParentId` 拉该剧 Episode，凡 gap 里已存在本地集的，删 `gap_records` 并把 status 清 2；全部清空且 TMDB 状态为完结则升级为「免检金牌」。前端 `GET /scan/progress` 每次轮询都会动态剔除忽略名单（`:148-163`），所以「入库后零延迟自动核销变色」实际是**前端轮询 + 后端过滤**的组合效果，不是推送。

**下载截胡**（`:400-517`）是全项目最硬核的一段：

```
download_gap_item:
  POST {MP}/api/v1/download/add  {"torrent_in": <原始种子对象>}
  仅当 is_pack（整季包）且配置了 client_type/client_url 时进入截胡

hook_qbittorrent:
  登录 /api/v2/auth/login
  轮询 20 次 × 3s：
    找 added_on 距今 < 300s 的种子
    优先按 |total_size - expected_size| < 10MB 匹配，否则首条
    等 files[0].size > 0（元数据就绪）
  对每个文件：非图像扩展名（mp4/mkv/avi/ts/iso）→ 剔除；
    extract_episodes_from_filename(name) → 与 target_episodes 求交 → wanted/unwanted
  安全阀：if not wanted: return False, "⚠️ 正则未能识别出视频集数，为防误杀已放行"
  POST /api/v2/torrents/filePrio  unwanted→priority 0，wanted→priority 1
```

`extract_episodes_from_filename`（`:376-398`）覆盖 5 类命名：`S01E01`/`S01E01-E02`、`EP01`/`E01`、`第1-3集`、`第1集`，全部失败时回落到「裸数字」并用年份/分辨率/编码白名单（480/720/1080/2160/264/265/2020-2027）排除干扰。这是把「种子文件名考古」问题工程化，**并且用「识别不出就放行」而不是「识别不出就全删」**做失败安全——这个方向是对的。

Transmission 实现（`:436-472`）走 RPC：先取 `X-Transmission-Session-Id`，再 `torrent-get(fields=[id,addedDate,totalSize,files])` 锁定，最后 `torrent-set` 用 `files-wanted`/`files-unwanted`。

**MP 检索与配型**（`:290-374`）：

```
1. 从库内已有该剧的 Episode 取 MediaSources[0].MediaStreams 里的视频流：
   Width>=3800 → "4K"；>=1900 → "1080P"；VideoRange/DisplayTitle 含 HDR → "HDR"；
   DisplayTitle 含 DOVI/VISION → "DoVi"；都没有 → ["无明显特效"]
   —— 即「配型」= 用已有集的实际画质反推要下的版本
2. 单集：搜 "{剧名} S01E01"；无结果或本身是多集：搜 "{剧名} S01"（is_pack=True）
3. deep_extract 递归在 torrent/torrent_info/detail/data/info 子对象里取字段，
   解决 MP 返回结构不稳定的问题
4. 打分：4K+50、1080P+50、DoVi+30、HDR+20、WEB+10，按 score 降序取前 10
5. 保留 org_payload 供回传 MP 用（避免重新构造种子对象）
```

**求片流转**（`media_request.py`）与缺集模块是两套独立工单，但共享同一批数据源：

- 提交时 `check_emby_exists`（`:97-113`）按 `AnyProviderIdEquals=tmdb.{id}` 查库，电影命中即拒；剧集再查 `/Shows/{sid}/Seasons` 比对季号。
- 表结构演进直接在模块导入时用 `ensure_db_schema()`（`:17-75`）做：检测 `media_requests` 主键是否含 `season`，不含就 RENAME→CREATE→INSERT OR IGNORE→DROP；`request_users` 同理补 `UNIQUE(tmdb_id,user_id,season)`。**没有 Alembic/Flyway**，全是「导入即迁移」。
- 主键设计 `PRIMARY KEY (tmdb_id, season)` 天然实现「同一剧同一季只能有一条工单」，而 `request_users` 的 UNIQUE 三元组实现「同一用户对同一季只能支持一次」——用主键/约束承担业务去重，比应用层查重可靠。
- Telegram 侧 `/userlf <TMDB链接>` 支持「已创建 / 已重新打开 / 已支持 / 你已支持过」四种回执（`README.md`、`bot_service.py`），说明状态机在两端共用。

**追剧日历**（`calendar_service.py`）是三层缓存：

```
内存 dict{offset: {data, time}}  →  SQLite tv_calendar_cache(air_date 索引)  →  TMDB
get_weekly_calendar: 内存命中 → 计算周一~周日 → _get_emby_continuing_series（Emby 连载剧）
  → 查 tv_calendar_cache 该周数据（用 DB status 覆盖 JSON 里的旧 status）→ 无数据才 20 线程抓 TMDB
  → 回写 SQLite → 同剧同季连号集合并
后台守护线程 sleep 60s 首启，之后每 12h 强刷 week_offset 0 和 1
```

它的实时性来自 `mark_episode_ready`（`:56-77`）：Webhook 收到入库事件时直接 `UPDATE tv_calendar_cache SET status='ready'` 并清空内存缓存——**状态与数据分离存储**，DB 里的 `status` 是唯一真相，`data_json` 只是渲染载荷。

**报表**（`report_service.py:43-128`）是纯 PIL：800×1200 画布，主题取 `config.py:29-38` 的 8 套 RGB 元组，按 period 生成对应 SQL 时间过滤，画 2 张统计卡 + Top8 榜单（名称截断 20 字符，空值兜底「未知内容」）。字体在初始化时从 GitHub 拉 NotoSansCJK，失败则 `ImageFont.load_default()`。

### 2.7 亮点

1. **双擎路由是数据库无关性的正确解法**。不是抽象出 Repository 接口，而是在最底层做 SQL 拦截 + 结果集伪装（`APIRow`）。业务层 0 改动即可在两种部署形态间切换，迁移成本几乎为零。工程上这比「双实现 + 抽象层」粗暴得多，但**对存量代码的侵入性也是最小的**——对已经写了 200 处 `query_db` 的项目来说，这是唯一可行的路径。

2. **失败安全方向一致且正确**。截胡正则识别不出集数 → 放行而不误删（`gaps.py:427`、`:467`）；TMDB 无 `air_date` 或未播 → 不算缺集（`:65`）；图片代理有 TMDB 兜底池（`config.py:21-27`）。

3. **用主键/唯一约束承担业务去重**：`media_requests(tmdb_id, season)`、`request_users(tmdb_id, user_id, season)`、`gap_records(series_id, season, episode)`、`invitations.code`。这类「重放安全」是并发下最省心的做法，也解释了为什么它敢用 `INSERT OR IGNORE` / `ON CONFLICT DO UPDATE` 而不担心重复。

4. **10308 物理隔离的求片门户**（`main.py:36-70`）。用同一个 ASGI app 加一层 scope 过滤：根路径强制改写成 `/request`，白名单外一律 404 并返回明确文案「非法越界，后台管理界面已被物理阻断」。**不依赖反代规则**就做到了「用户入口」与「管理台」的暴露面隔离（`SO_REUSEPORT` + 独立 socket）。

5. **事件总线解耦 Webhook**（`event_bus.py:8-25`）：`publish` 时对每个 handler 起 daemon 线程，注释写明「确保发布者（如 Webhook）瞬间返回，绝不阻塞」。Emby 的 Webhook 有超时重试，让回调快速 200 是正确取舍。

6. **风控是「实时扫描 + 执法」而非只出报表**：`scan_playbacks_and_alert` 用 `_last_playback_state` 记忆上次并发态来防刷屏（`risk_service.py:75-78`），命中并发上限即 `kick_session`（`:15`），可升级为 `ban_user` 直接改 Emby `Policy.IsDisabled`（`:28`），并落 `risk_logs` + 更新 `users_meta.risk_level`。

7. **客户端黑名单是「击杀链」而非「拒绝登录」**：命中后依次 `DisplayMessage` 弹窗 → `Playing/Stop` 停播 → `DELETE /emby/Devices?Id=` 删设备（`webhook.py:30-46`）。对已经在播的违规客户端，这是唯一有效的处置。

8. **策略克隆的键分类未来安全**：`clone_policy`（`users.py:78-93`）排除 `IsAdministrator/IsDisabled/LoginAttemptsBeforeLockout` 三个危险键，把剩余键按 `LIBRARY_POLICY_KEYS` / `PARENTAL_POLICY_KEYS` / 其余 三类分流，注释直言「无需枚举，兼容未来所有 Emby 新权限字段」。未知字段默认归入「基础策略」——比白名单式枚举更抗 Emby 升级。

9. **去重打分可解释**（`dedupe.py:75-128`）：6 维权重按策略切换（quality/subs/size/custom），分辨率 40 分、HDR/DoVi 15 分、中文 10 分、ASS 字幕 15 分，码率 `min(20, Mbps/2)`，「size」策略下大文件**倒扣** `GB×2`。既给出分数也返回结构化标签（`res/has_hdr/has_dovi/has_chi/has_ass/v_codec/a_codec`），前端能解释「为什么推荐这个版本」。

10. **报表生成的取巧**：不引入 matplotlib/pyecharts，纯 PIL 画圆角矩形+文字，把依赖面压到 `requirements.txt` 的 8 行。

### 2.8 缺陷

1. **双擎路由的隐性行为差异没有护栏**。`query_db` 在 API 模式下只把「查询播放表」的 SQL 转发出去，`_interpolate_sql`（`:78-89`）用字符串拼参数**手工转义**（仅 `'` → `''`）。这既绕过了参数化（在服务端插件执行），又把 SQL 语义依赖绑死在 Playback Reporting 插件的 SQLite 方言上——`date('now','localtime')`、`LIMIT 5000`、`GROUP BY` 等散落在 20+ 处调用点（如 `stats.py:105`、`report_service.py:78`），插件换实现即全站失效。而且**API 分支失败不回落 SQLite**，只 `print` 且返回空。

2. **`print` 即日志**。`database.py` 用 emoji 前缀 print 到 stdout（`[API 引擎] ❌ ...`），`config.py` 亦然；只有部分模块用 `logging.getLogger("uvicorn")`。容器里无法按级别过滤，也没有脱敏——异常文本可能带上 Emby 主机信息。

3. **`except: pass` / `except: return {"status":"error"}` 密度极高**。`stats.py` 几乎每个 handler 都是 `try: ... except: return {"status":"error","data":[]}`。结果是「永不 500」也「永不报错」：一个 SQL 语法错误在 API 模式下会静默变成空列表，前端显示「暂无数据」。**这是本项目最大的可运维性缺陷**——双擎路由带来了部署自由度，同时把故障可见性也一起归零了。

4. **绝对路径与硬编码**。`config.py:5` `CONFIG_DIR = "/app/config"`、`DB_PATH` 默认 `/emby-data/playback_reporting.db`，非容器部署直接失败；`FONT_URL` 指向 GitHub raw，`REPORT_COVER_URL`/`TMDB_FALLBACK_POOL` 都是外链，内网部署要么超时要么降级。

5. **`media_api` 无超时默认值**。`MediaServerAdapter.request`（`media_adapter.py:55-67`）不设 `timeout`，全靠调用点逐个传（有大量 `timeout=2`、`timeout=5`，但 `dedupe.py` 里的分页拉取用 30s、`insight.py:105` 用 60s）。漏传一处就会挂住整个请求线程。

6. **无鉴权分层**，全部是 `if not request.session.get("user"): return {"status":"error"}` 逐 handler 手写（`users.py:126`、`users.py:339`、`insight.py:80`…）。没有依赖注入守卫，新增路由容易漏。求片门户另有独立密码体系（`/api/requests/auth`）。

7. **扫描状态是进程内全局单例**（`gaps.py:19` 的 `scan_state` + `state_lock`）。多 worker 部署（`uvicorn --workers N`）下进度与结果必然错乱；`scan_state["results"]` 还可能因内存压力丢历史，靠 `gap_scan_cache` 兜底但不完整。

8. **季度语义歧义**：`media_requests` 用 `season=0` 表示电影、正整数表示季，而「整剧」也是以每季一行落库（`seasons: List[int]`，`media_request.py:116`）。加上 `PRIMARY KEY (tmdb_id, season)`，电影与「第 0 季」不可区分。

9. **报表/日历/缺集三条链路各自独立抓 TMDB**，没有共享缓存层，`tmdb_api_key` 的配额在多模块并发下容易打满（日历 20 线程 + 缺集 10 线程 + MP 检索）。

10. **运维能力薄弱**：无备份/恢复界面（备份 = 拷容器卷）、无操作审计（谁改了哪个用户的到期日无记录）、无版本迁移工具（`ensure_db_schema` 是即席的）、无指标导出（Prometheus/健康检查端点）。对比 meridian 的 `/api/diagnostics` 与 backup_restore，emby-pulse 在这一维度是缺失的。

### 3.2 从文档反推出的需求体系

按「文档篇幅 × 约束密度」排序，可以读出这套系统的真实优先级：

**第一层：账号生命周期是主干，不是附属。** `system-settings.md`（249 行，全仓库最长）里 `账号策略` 一个 Tab 就占了 150 行，覆盖访问开关、签到、注册三约束、保号三规则、到期删除七档、客户端黑名单五种匹配。`watch-keepalive.md` 单独 173 行写「观看规则叠加在会员规则之上」的口径，并明确状态转移表（`watch-keepalive.md:129-140`）。这说明目标用户的核心诉求是**「按行为自动裁决账号」**，而不是「看统计」。

**第二层：状态必须可解释、可回溯。** 系统的状态不是布尔值，而是「状态 + 禁用原因」（`watch_requirement` / 手动禁用 / 客户端黑名单，`system-jobs.md:30`、`membership-groups.md:42`）、「状态 + 最近同步时间」（`system-jobs.md:59`）、「操作 + 结果 + 请求 ID」（`operation-logs.md:11-19`），且请求 ID **跨操作日志与运行日志可串**（`operation-logs.md:35-39`）。这是把「排障」当成一等需求来做。

**第三层：集成必须优雅降级而非硬失败。** 大量「不满足条件时」的显式声明：Mini App 受 Telegram 总开关约束但网页侧独立（`system-settings.md:39`）；恢复秘钥只受自身开关控制，不受 `开放网页使用` 影响（`system-settings.md:48`、`login-entry.md:38`）；`用户端显示商城入口` 只控显示不删数据（`points-shop.md:15`）；模板媒体库「未配置」表示不修改（`emby-policy-templates.md:17`）。系统的默认哲学是「开关控制可见性，不控制数据存在」。

**第四层：并发与重放在设计期就被处理。** 这一点文档里反复出现：卡密「同一用户并发兑换/调整有效期」修复（`changelog.md:66`）、TG 绑定码「并发使用被重复消费」修复（`:69`）、权限同步「按用户串行执行，不会相互覆盖」（`emby-policy-templates.md:31`）、商城「重新提交同一笔购买不会重复扣积分」（`points-shop.md:54`）。加上 `notification-webhook.md:29` 明确要求接收端用 `sourceId+deliveryId` 去重——**幂等性是这套系统的硬约束**。

**第五层：破坏性操作必须有原子性协议。** 只有备份恢复一节配了 5 篇独立实测文档（`testing/`），含 10 万用户的容量实测（导出 49s / ZIP 3.38MB / 暂存 40 万行 / 恢复流程 23 分钟）与灾后重建演练。文档自己也坦白「MySQL `information_schema` 的 data/index 字节未刷新…显然不应作为真实占用或峰值」「不能作为严格性能基准」（`testing/backup-restore-capacity.md`）。**这种对测量局限性的自陈，是这个仓库文档质量最高的地方**，也说明作者把「恢复流程可验证」当成了功能而非辅助。

**第六层：可配置性是核心卖点，但需要防配置地狱。** 配置项数量极大（配置中心 7 分区 + 通知三渠道 + 模板变量 + 卡密规则 + 流量防护 12 项）。作者用三种手法收敛：配置分组折叠（`changelog.md:333`）、策略概览前置确认（`system-settings.md:29`）、规格预设一键套用（`system-settings.md:202`）。

**明显缺失的需求（文档里找不到）：**
- 无 Emby 侧反代/线路分发能力（线路只是「展示与健康检查」，不做流量转发）——与 meridian 恰好互补。
- 无播放器/客户端的兼容性重写（`/emby` 前缀、HLS/DASH 改写、WebSocket 代理一概没有）。
- 无流量计费、限速、配额概念（只有「流量防护」= 请求频率限制，`system-settings.md:198`）。
- 无多租户/多站点（单 Emby 实例）。
- 无开放 API / 无 Webhook 入站之外的程序化接口。

### 4.2 通病与超越点

**通病一：探活是「一次性快照」，不是「持续状态」。**
- meridian：延迟只存在于手点测速的瞬间（`app_sites.go:35`），不落库、不参与调度；failover 只认 5xx（`upstream_failover.go:134`）。
- emby-pulse：`/check` 是请求即刻探测（`bot_service.py:1426`）。
- bubble：唯一做对 —— 「后台按最近 10 次检测结果展示正常/离线/波动」（`changelog.md:174`），滑动窗口落在服务端。
- **超越点**：线路状态应当是 `(滑动窗口成功率, P50/P95 延迟, 最近失败原因, 冷却截止时间)` 的持续对象，落库 + 定时探测（例如每 30s 一次轻量 HEAD），并让调度真正消费它。meridian 已经有关键部件（`failedUntil` map、`primaryProbeAt` 预留探测），只是没把延迟接进去。

**通病二：失败被吞掉。**
- meridian：`log.Printf` 之后返回 502 JSON（`proxy_start.go:270-273`），可接受；但 `probeTargetHealth` 把 4xx/5xx 判 `reachable`（`diagnostics.go:330`），存在误导。
- emby-pulse：`except: pass` / `except: return {"status":"error"}` 遍布（`stats.py` 几乎每个 handler、`dedupe.py`），加上双擎路由静默降级（`database.py:160-163`），**故障表现为「数据为空」而非「报错」**。
- bubble：文档层面反而最严 —— 备份恢复有 8 类失败码处置手册（`backup-restore.md:101-110`），并强调「提交结果不明确时，系统不会自动重复导入」（`:112`）。
- **超越点**：区分「无数据」与「取数失败」两种空结果；把降级/回退事件当一等指标暴露（计数器 + 大盘展示 + 通知）。

**通病三：调度与容灾的语义边界含糊。**
- meridian 的 failover 只在「请求可重放」时逐条重试（`upstream_failover.go:163-179`），POST 非 PlaybackInfo 一律不重试；但 UI 上没有把这条规则表达出来，运维看到「配了 7 条备线」会以为都能切。
- 「备用线路不能与主回源固定请求头同时使用」（`sites.js:2027`）这类互斥只在前端拦截。
- **超越点**：把「哪些请求会走备线」做成可查询的决策解释（类似 meridian 已有的 `dynamic_observations`），或者至少在 UI 上标出「当前线路已切换至备用 3 / 已持续 12 分钟」。

**通病四：单实例假设贯穿全部三个项目。**
- meridian：`upstreamFailoverState` 进程本地（`upstream_failover.go:21-22`）、流量计数器进程内、`scan` 类状态本地。
- emby-pulse：`scan_state` 是模块级全局（`gaps.py:19`），多 worker 必然错乱；日历/风控/告警全用 module 级单例与 daemon 线程（`calendar_service.py:16`、`risk_service.py:75`）。
- bubble：备份恢复明确要求「恢复只支持单应用实例」（`backup-restore.md:9`）并配 `single_instance_confirmed` 开关——**这是唯一把单实例约束显式化的做法**。
- **超越点**：把「需要单实例」的地方显式声明并在启动时自检（数据库锁 / advisory lock），而不是让它成为运行时偶发 bug。

**通病五：配置爆炸后缺少「当前生效态」视图。**
- meridian：有 `rollback_readiness`（`README.md:380`）和 `dynamic_observations`，方向是对的。
- emby-pulse：`gap_config` 是裸 K/V 表（`gaps.py:276-288`），配置项没有类型、没有校验、没有默认值记录。
- bubble：`当前策略概览`（`system-settings.md:29`）在做这件事，但只是汇总，不解释冲突。
- **超越点**：给每个配置项加类型/约束/默认值/最后修改人与时间；对互斥组合在保存时给出「实际生效值预览」。

**超越点总结（可直接借鉴的六个具体做法）**

1. **meridian 的 capability 令牌**（`dynamic_capability_issuer.go:85`）：把「需要代理的外部 URL」变成同源加密令牌，用密码学替代黑名单/白名单，同时天然获得过期、策略版本绑定、审计能力。任何要代理第三方直链的系统都该这样做。
2. **meridian 的预留-结算配额**（`traffic_quota.go:30-100`）：配额在写入路径内按字节申请与退还，配合周期代际号防止跨周期污染。比「累加后判断」精确得多。
3. **emby-pulse 的 SQL 拦截式多引擎路由**（`database.py:91`）+ 结果集伪装（`APIRow`，`:56`）：对已有大量 SQL 调用点的存量系统，这是侵入性最低的「数据来源可切换」方案。
4. **emby-pulse 的下载截胡失败安全**（`gaps.py:427`、`:467`）：文件级筛选在解析不确定时选择放行。所有「自动删/自动改」的动作都该有这样一个显式出口。
5. **bubble 的滑动窗口健康状态**（`changelog.md:174`）：最近 N 次结果聚合为正常/离线/波动三态，是线路类功能的最低门槛。
6. **bubble 的通用 Webhook 投递协议**（`notification-webhook.md`）：`X-Notification-Timestamp` + `HMAC-SHA256(timestamp + "." + rawBody)` + `sourceId+deliveryId` 幂等 + `Retry-After` 优先的 5 次退避。这是一份可以直接照抄的通知投递规范。

**三者互补关系（对自建方案的直接启示）**

```
meridian  ── 网络层：入口/反代/线路/capability/字节计费/证书   ← 只有它掌握字节与连接
emby-pulse ── 数据层：双擎取数/播放分析/缺集补货/内容运营      ← 只有它掌握内容与播放语义
bubble    ── 运营层：账号生命周期/权限/积分/工单/通知/备份      ← 只有它把「人」管到底
```

三者的能力几乎不重叠（唯一的交集是「流量统计」，但口径一个是字节、一个是时长/次数）。一个完整的 Emby 运维平台 = meridian 的代理内核 + emby-pulse 的双擎数据层 + bubble 的账号与运营层，而三者的公共短板也都是同一个：**探活/降级/单实例这些「非功能性需求」被当成实现细节而不是产品能力**——这恰好是自建方案最容易一次性做对的部分。
