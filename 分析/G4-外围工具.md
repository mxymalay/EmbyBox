## 1. emby-tools

### 定位与技术栈

Emby 周边工具的**一体化（all-in-one）**应用：Vue3 + Vite + Element Plus + Pinia 前端，Node.js + Express 5 后端，生产模式下后端直接托管前端打包产物（`backend/src/app.js` 的 `express.static` + SPA history fallback），单容器单端口 3001。定位是"运维者自用的工具箱"，不是多用户门户。

### 解决的问题

1. 媒体库封面难看 → 提供"随机抽图 → 生成渐变背景海报 → 一键替换 Emby 库封面"流水线。
2. 文件命名混乱 → 提供剧集文件批量重命名（4 种模式）+ 批量删除。
3. 想看片库现状 → 统计面板（数量、最近入库、播放时长、存储占用、磁盘容量）。
4. 想看新片 → TMDB 每日推荐（趋势/热门/高分/题材发现）。
5. TMDB 国内不可直连 → 内置 http/socks 代理配置 + 图片代理。

### 功能清单

前端路由（`frontend/src/router/routes.ts`）只有 4 个菜单页：首页、每日推荐、emby 媒体库封面、emby 批量重命名（`seriesTracker` 追剧页已注释下线）。另有设置入口（Emby 连接设置、TMDB 代理设置）。

后端 API 清单（`backend/src/app.js` 挂载 4 个路由前缀）：

```
POST /emby/login                    # AuthenticateByName，登录后把 token/user 写进全局单例
GET  /emby/mediaCount               # 电影/剧集/音乐计数 + 总计
GET  /emby/latestAdd                # 最近入库 10 条（含封面 URL 拼接）
GET  /emby/storage                  # 电影/剧集/音乐体积 + 总计 + 磁盘容量
GET  /emby/playTime                 # 播放时长（小时）
GET  /emby/mediaLibraryList         # 媒体库列表（仅 tvshows/movies）
GET  /emby/radomEmbyPosterList      # 随机 N 张库内封面
POST /emby/embyReplacePoster        # base64 封面写回 Emby
GET  /rename/folder-content         # 磁盘/目录浏览
POST /rename/batch-rename           # fs.renameSync 循环
POST /rename/batch-delete           # fs.unlinkSync 循环
GET  /theMovieDB/todayTrending|weekTrending|movieNowPlaying|moviePopular
     |tvPopular|movieTopRated|tvTopRated|discover
GET/POST /theMovieDB/proxy          # 运行时读写 TMDB 代理
GET  /proxy/image                   # 图片代理（白名单 image.tmdb.org，防 canvas 污染）
```

重命名引擎（`frontend/src/stores/rename.ts`）的解析链值得单独记一笔 —— 7 条正则按顺序兜底：

```js
const EPISODE_PATTERNS = [
  /[Ss](\d{1,2})[Ee](\d{1,2})/,        // S01E02
  /(\d{1,2})x(\d{1,2})/,               // 1x02
  /[第](\d{1,2})[季集].*?(\d{1,2})/,   // 第1季第2集
  /[Ee][Pp]\.?(\d{1,2})/,              // EP02
  /第(\d{1,2})期/,                      // 第12期（综艺）
  /[\[\(](\d{1,2})[\]\)]/,             // [02] / (02)
  /\b(\d{1,2})\b/                      // 纯数字兜底
]
```

配套 `IParseResult.confidence`（0–1 置信度）与 4 种模式（`tv` 剧集 / 顺序 / 替换文本 / 插入文本），顺序模式支持 `startEpisode` 为 0 或负数。剧集名提取（`frontend/src/utils/utils.ts` 的 `getSeriesNameFromPath`）会识别末级目录是否为 `season|第X季|新建文件夹|^s\d{1,2}$` 而回退到上一级，并剥掉 `(2025)` 或尾随 `2023` 年份。

### 数据模型要点

**没有数据库，也没有持久化。** 全部靠模块级单例：

```js
// backend/src/store/embyStore.js
const embyStore = { url: '', accessToken: '', user: { Id, Name, ServerId, ... } }
// backend/src/store/tmdbStore.js
{ proxy: '' }
```

HTTP 响应格式由中间件统一（`backend/src/middleware/response.js`）：`{ code: 200, message, data }`，成功用 `res.success(data, msg)`、失败用 `res.error(msg, code)`。

### 值得借鉴的设计

- **七段正则兜底链 + 置信度**：真实文件名格式极杂，单正则必然漏；按特异性从高到低排序、最后用纯数字兜底，是很实用的工程折衷。
- **图片代理白名单防 canvas 污染**：`GET /proxy/image` 只允许 `image.tmdb.org`，并在 axios 请求里伪造 UA 与 `Referer: https://www.themoviedb.org/` 绕过 403，同时设置 `Cache-Control: public, max-age=86400, immutable`。前端注释明确写出动机："避免前端 canvas 污染与跨域"。HTTPS 门户 + HTTP Emby 的部署里，这个代理是必修课。
- **代理配置的双栈实现**：`createAgentByProxyUrl` 按前缀分流 `HttpsProxyAgent` / `SocksProxyAgent`，并用 `cachedProxyKey` 缓存 axios 实例，避免每次请求重建连接池。
- **磁盘容量与媒体体积对照**：`systeminformation.diskLayout()` 求磁盘总容量，与 Emby `/Items?Fields=Size` 求和的媒体体积一起返回，前端可算占用率 —— 这是六个项目里唯一给出"占用率"的做法。
- **播放时长的业务口径**：不是简单 `RunTimeTicks * PlayCount`（注释里的旧写法被删掉了），而是"有 `PlaybackPositionTicks` 用进度位、若 `Played=true` 用整片时长、否则不计"：

```js
if (PlaybackPositionTicks > 0) return total + PlaybackPositionTicks
if (PlaybackPositionTicks === 0 && Played === true) return total + RunTimeTicks
return total
```

这个口径能同时覆盖"看了一半"和"看完"两种场景，比 `PlayCount` 累乘准。

### 明显缺陷

1. **TMDB Bearer Token 硬编码在源码里**（`backend/src/services/theMovieDBService.js` 的 `Authorization` 头，是一段完整 JWT，含 aud/nbf/sub）。任何拿到源码的人可直接盗用配额。
2. **全局单例 = 多用户串号与越权**：`embyStore` 是进程级变量，A 登录后 B 访问即拿到 A 的 token；且后端所有 `/emby/*` 接口**零鉴权**，任何人 curl 就能读片库、改封面、列目录、删文件。
3. **文件系统接口无路径白名单**：`GET /rename/folder-content?dirPath=/` 可枚举整个容器文件系统，`POST /rename/batch-delete` 传绝对路径即 `fs.unlinkSync`。这是本组最严重的越权面。
4. **全量拉取导致大库不可用**：`/emby/storage` 并发三次 `/Items?IncludeItemTypes=X&Recursive=true&Fields=Size` 把所有条目拉回进程内累加 `Size`，几十万条目会超时或 OOM（对比 gaodong 的 `Limit=0&EnableTotalRecordCount` 只取计数）。
5. `/emby/playTime` 的 URL 末尾是 `&Limit`（空值），客户端会忽略但暴露了未完成实现。
6. TMDB 代理存内存，重启即丢；多副本部署不共享。
7. 前端 `utils/request.ts` 只在 `res.code === 500` 时弹提示，其余错误码静默失败。

## 2. emby-request-ui

### 定位与技术栈

**纯求片站**。Next.js 15 App Router + React 18 + Prisma 6 + PostgreSQL 16 + Tailwind，Docker Compose 一键部署（`scripts/install.sh` 会在 Ubuntu/Debian 上装 Docker、自动 `openssl rand` 生成 `POSTGRES_PASSWORD` / `ADMIN_SESSION_SECRET` / `TELEGRAM_CONFIG_SECRET` 并写入 `.env`）。它**完全不接触 Emby** —— 没有 Emby API 调用、没有用户绑定，是一个"公告板 + 工单流转"。

### 解决的问题

观众想看的片子片库里没有 → 提供一个公开表单，填片名/类型/年份/TMDB 链接/备注提交 → 管理员在后台改状态 → 所有人可在 `/progress` 页看公开进度。

### 功能清单

页面：`/`（提交表单）、`/progress`（公开进度，带 `?requestId=` 高亮）、`/admin/login`、`/admin`（求片列表 + 状态下拉 + 删除）、`/admin/settings/security`（改密码）、`/admin/settings/notifications`（Telegram 配置 + 测试发送）。

API 清单（Next.js Route Handlers）：

```
POST   /api/requests                     # 公开，创建求片 + 触发 TG 通知
GET    /api/requests                     # 公开，全量列表（无分页）
PATCH  /api/requests/:id/status          # 需登录
DELETE /api/requests/:id                 # 需登录
GET    /api/requests/progress            # 410 Gone（查询码模式已下线）
POST   /api/admin/login                  # scrypt 校验 → 签 session cookie
POST   /api/admin/logout
PATCH  /api/admin/password               # 需登录，改密
GET    /api/admin/settings/telegram      # 需登录
PATCH  /api/admin/settings/telegram      # 需登录
POST   /api/admin/settings/telegram/test # 需登录，发测试消息
GET    /api/health                       # database up/down + telegram configured
```

状态机（`lib/request-domain.ts`）只有三态，且与进度条耦合：

```ts
export const REQUEST_TYPES = ["电影", "电视剧", "动漫", "纪录片"] as const;
export const REQUEST_STATUSES = ["待处理", "已完成", "已拒绝"] as const;
// app/progress/progress-content.tsx
const progressMap = { 待处理: 35, 已完成: 100, 已拒绝: 100 };
```

### 数据模型要点

`prisma/schema.prisma` 三张表：

```prisma
model Request {
  id Int @id @default(autoincrement())
  title String
  normalized_title String?
  type String
  year Int?
  note String?
  tmdb_url String?
  contact String?
  status String @default("待处理")
  progress_token String? @unique
  created_at DateTime @default(now())
  updated_at DateTime @default(now()) @updatedAt
  @@unique([type, normalized_title])     // 去重唯一索引
  @@map("requests")
}
model AdminCredential { id, username @unique, passwordHash, ... }
model AppSetting { key String @id, value Json, ... }
```

去重逻辑（`lib/services/request-service.ts`）是"归一化 + 唯一索引 + 查询三重保险"：`normalizeTitle` 做 `trim().toLowerCase().replace(/\s+/g, "")`，先 `findFirst` 查 `normalized_title` 或 `title`（不区分大小写），命中直接 409 并给进度页引导语；DB 层再用 `@@unique([type, normalized_title])` 兜底并发。

校验有三处值得注意：年份限定 1888–2100；`tmdb_url` 必须解析成 URL 且 hostname 含 `themoviedb.org` 或 `tmdb.org`；类型必须在四类枚举内。所有错误通过 `AppError(message, status, code)` + `handleApiError` 统一成 `{ error }` 结构。

认证（`lib/admin-auth.ts`）是自制无状态 session：`scryptSync(password, salt, 64)` 加盐哈希，`timingSafeEqual` 定时安全比较；session token 是 `base64url(payload).HMAC-SHA256(payload, secret)`，cookie `httpOnly + secure(prod) + sameSite=lax + 7天`。`ensureDefaultAdminCredential()` 会懒创建默认账号 `amdin` / `admin`。

Telegram 配置（`lib/telegram-settings.ts`）实现了**DB 优先 / env 兜底的双源策略**，并用 AES-256-GCM 加密 botToken 后存 `AppSetting.value`：

```ts
// lib/crypto.ts
const ALGORITHM = "aes-256-gcm"; const IV_BYTES = 12;
// 密钥 = sha256(TELEGRAM_CONFIG_SECRET ?? ADMIN_SESSION_SECRET ?? 开发默认值)
return `${iv.toString("base64url")}.${tag.toString("base64url")}.${encrypted.toString("base64url")}`;
```

### 值得借鉴的设计

- **KV + Json 表承载"运行时可改配置"**：`AppSetting(key, value Json)` 一张表就够，配合 DB→env 的读取顺序，让运维既能在部署时用 env，也能在后台热改，且不破坏容器化惯例。
- **敏感配置加密落库**：AES-256-GCM（带 authTag）而不是裸存或 base64，密钥从独立 secret 派生并逐级兜底。这是本组唯一做了凭据加密的项目。
- **`install.sh` 消灭弱默认**：用 `openssl rand -hex 32` 自动生成全部三个密钥，配合 `ensure_env_var` 幂等写入 `.env`，把"默认口令"这类问题在部署层解决掉。
- **迁移的幂等写法**（`prisma/migrations/20260407193000_sync_requests_schema/migration.sql`）：用 `ADD COLUMN IF NOT EXISTS` + `DO $$ ... IF NOT EXISTS(pg_indexes) ...` 判断"无重复数据才建唯一索引"，能安全兼容已经 `db push` 过的环境。
- **前端的乐观更新 + 回滚**（`app/admin/status-select.tsx`）：先 `setStatus(next)`，PATCH 失败再 `setStatus(previous)` 并显示错误。这是三态流转里最舒服的交互。
- **`/api/health` 语义化健康检查**：返回 `{ ok, database: "up"|"down", telegram: "configured"|"disabled" }`，DB 不通时给 503，直接可用于编排探针。

### 明显缺陷

1. **`GET /api/requests` 完全公开、无分页、无字段裁剪**。进度页需要全量列表，于是接口就是全量 `findMany()`；`contact` 字段（schema 里 `String?`）一旦被填就会对公网暴露。这是"公开进度"设计的直接副作用。
2. **无提交限流/验证码**：`POST /api/requests` 公开且无任何频率限制，可刷单。
3. **默认凭据硬编码且用户名拼错**：`DEFAULT_ADMIN_USERNAME = "amdin"`、`DEFAULT_ADMIN_PASSWORD = "admin"`，README 里还明写了。虽然提供了改密页，但 `ensureDefaultAdminCredential` 会在每次登录时懒创建，等于常驻后门。
4. **状态机太窄，无法对接自动化**：只有三态且无 `downloading` 中间态，也**没有 `tmdb_id` 字段**（只存 URL 字符串），因此无法与 MoviePilot/下载器/Emby 入库检测任何一环联动。它是闭环上的一段，但不是闭环。
5. **`progress_token` 字段是死代码**：schema 里有 `@unique` 的 token，`/api/requests/progress` 也返回 410 说"查询码模式已下线"，说明原设计有"凭码查私有进度"能力但被砍掉了，字段残留。
6. 前端 `app/page.tsx` 提交 payload 里已无 `contact`，但 DB 列仍在且 migration 专门 `DROP NOT NULL` —— 遗留字段。
7. 后台功能极薄：只有 2 个设置页 + 一个列表，没有统计、没有导出、没有操作日志。

## 3. embyforge

### 定位与技术栈

**面向多服务器的 Emby 综合管理系统**，是六个项目里架构最完整的：Go + gin + gorm + PostgreSQL，Telegram Bot（`go-telegram-bot-api`），进程内事件总线，四个外部适配器（Emby / TMDB / MoviePilot / 下载器），Next.js 前端。设计目标明确写在 README：用户生命周期 + 播放统计 + 求片 + 缺集 + 自动化运维。

### 解决的问题

这是唯一试图回答"Emby 站点怎么运营"的项目：邀请码发号 → TG 绑定 → 到期自动封禁 → 积分经济（签到/求片消耗/转账/排行）→ 播放统计与报表推送 → 求片工单 → 缺集补货 → 追剧日历。

### 功能清单

主入口 `cmd/embyforge/main.go` 的启动顺序本身就是一份架构说明：加载配置 → 初始化 DB → **把 config 里的服务器同步进 DB** → 为每台服务器建 Emby 客户端并探活 → 建 TMDB / MoviePilot / 下载器客户端 → 建事件总线并 `Start()` → 建 Service 层 → 启动 Scheduler → 启动 TG Bot → 启动 HTTP Server → 优雅退出。

路由（`internal/server/server.go`）：

```
GET  /health
POST /api/auth/login                       # 公开，走 Emby AuthenticateByName
POST /webhook/:token                       # token 校验替代 JWT
# 以下全部经 JWTAuthMiddleware
GET  /api/dashboard/overview | sessions
GET  /api/stats/trend | ranking | latest
GET|POST|PUT|DELETE /api/users[/:id][/:id/status]
GET|POST|DELETE /api/invitations[/:id]
GET|POST|PUT /api/requests[/:id/status]
GET|PUT /api/settings
GET  /api/servers
```

Bot 命令（`internal/bot/bot.go` 的 `registerCommands`）：用户侧 `/start /help /me /checkin /search /stats /request /transfer`；管理员侧 `/ban /unban /renew /coins /gencode /report`（经 `adminOnly` 装饰器）。同时向 Telegram 注册命令菜单。

Webhook 事件映射（`internal/api/webhook.go`）：

```go
case "playback.start":      return event.EventPlayStart
case "playback.stop":       return event.EventPlayStop
case "library.new", "item.added": return event.EventItemAdded
case "user.authenticated":  return event.EventUserAuth
```

事件总线（`internal/event/bus.go`）是 channel + handler map：`Publish` 非阻塞（缓冲满则**丢弃**并打日志），`dispatch` 里每个 handler 起独立 goroutine 并 `recover()`。Bot 订阅了 `PlayStart/PlayStop/ItemAdded`，把播放与入库事件播报到服务器关联的 TG 群（`handlePlayEvent` / `handleItemAddedEvent`）。

四个适配器的能力边界：Emby（510 行，用户 CRUD、Policy 启停、Sessions、Items、Shows/Episodes，以及 Playback Reporting 插件的 `/user_usage_stats/*`）、TMDB（search/multi、tv 详情、season 详情、on_the_air/upcoming）、MoviePilot（search、download/add、subscribe CRUD、system）、下载器（qBittorrent 完整实现；**Transmission 只返回"开发中"错误**）。

### 数据模型要点

8 张表（`internal/model/models.go`），全部 gorm AutoMigrate 创建（`internal/repository/db.go`，先 `CREATE EXTENSION pgcrypto` 以支持 `gen_random_uuid()`）：

```go
Server{ID uuid, Name, EmbyURL, APIKey(json:"-"), DataMode, DBPath, PublicURL, TGChatID}
User{ID, TGID uniqueIndex, TGName, EmbyID, EmbyName, ServerID, Status(active/banned/expired),
     Role(user/admin/owner), Coins, ExpireAt *time.Time}
Invitation{Code uniqueIndex, ServerID, CreatorID, Type(code/link), MaxUses, UsedCount,
           Duration *int(账号有效天数), ExpireAt *time.Time(码自身有效期)}
CoinTransaction{UserID, Amount(正收负支), Type(checkin/request/transfer/admin), Memo}
Request{UserID, ServerID, Title, TMDBID *int, MediaType, Season *int,
        Status(pending/downloading/done/rejected), AdminNote}
PlaybackStat{ServerID, EmbyUserID, ItemName, ItemType, PlayDuration, DeviceName,
             ClientName, IPAddress, PlayedAt}
EventLog{ServerID, EventType(index), Payload(text 原始 JSON)}
Setting{Key string PK, Value text}
```

几个设计密度高的点：

`Invitation` 把「码的时间轴」和「账号的时间轴」分开 —— `ExpireAt` 管码本身何时作废，`Duration` 管兑换出的账号能用多少天（NULL 为永久）。`InvitationService.GetActiveInvitations` 用 `used_count < max_uses AND (expire_at IS NULL OR expire_at > now)` 过滤。`handleBindCode` 里 `used_count` 用 `gorm.Expr("used_count + 1")` 原子自增，避免读-改-写竞态。

`CoinTransaction` 是流水账而非只改余额：签到、求片、转账、管理员调账都留一条带 `Memo` 的记录，`GetTransactionHistory` 可查。

用户生命周期闭环在 `UserService.CheckExpiredUsers`（定时 1 小时）：查 `status='active' AND expire_at < now` → 调 Emby `DisableUser` → 本地置 `expired`。反向的 `/renew` 会把过期时间基于 `max(now, 原过期时间)` 顺延（不会吃掉已过期的时间）。

建号回滚（`handler_user.go` 的 `handleBindCode`）顺序是"Emby 建号 → 落本地 User → 落库失败则 `client.DeleteUser` 回滚 + 回复失败"，成功后才 `used_count+1`。Emby 用户名固定 `tg_{tgID}`，密码 `generateRandomPassword(8)`（`crypto/rand` + hex），并在 TG 消息里把账号密码直接发给用户。

### 值得借鉴的设计

- **多层适配器 + 工厂**：`adapter/{emby,tmdb,moviepilot,downloader}` 各自独立 client，`downloader.NewClient(type,...)` 做工厂分发。新增外部系统只动一个包，不动业务层。
- **事件总线 + Webhook 驱动**：Emby 主动 POST → 映射内部事件类型 → 持久化原始 payload 到 `EventLog` → 发布到总线 → 各订阅者（TG 通知、未来的积分/入库回填）并行消费。这是"实时播报"最省资源的正路，避免轮询。
- **`EventLog.Payload` 存原始 JSON**：排障时能重放，不必猜字段映射。
- **报表引擎把"取数"与"渲染"分开**：`GenerateReport(serverID, periodType)` 返回结构化 `ReportData`（Summary/TopUsers/TopMedia/NewUsers），`FormatReportText` 单独负责渲染成 TG Markdown。同一份数据可以换渲染器输出到网页或邮件。
- **积分作为行为闸门**：`handleRequest` 先查 `user.Coins < cfg.Coin.RequestCost` 再放行，扣分与建单同时进行且都写流水。把"求片"变成有成本的行为，天然抑制刷单。
- **`Server.DataMode` 字段（api / sqlite）**：为"直读 Playback Reporting 的 SQLite"预留了配置位，说明作者研究过插件的数据落盘位置。
- **`/gencode` 与 `/renew` 用 reply-to 定位目标用户**（`resolveTargetUser`）：先看 `msg.ReplyToMessage.From.ID`，再退回解析参数里的 TG ID 或 Emby 用户名。TG 场景下 reply-to 是最自然的目标选择方式。

### 明显缺陷

1. **`playback_stats` 表只读不写 —— 表结构完备但全项目无任何写入路径**。grep 全仓只有五处引用：`db.go` 的 AutoMigrate、`models.go` 的定义、`stats.go`/`handler_coin.go`/`report_service.go` 的**读取**。没有 Create、没有 Save、没有 Upsert。后果：Bot `/stats` 命令的"总播放次数/总观看时长"永远返回 0；而报表走的是 Playback Reporting 插件的**实时查询**，两条数据路径互不相干，同一系统里两套统计口径。
2. **JWT 密钥硬编码默认值**：`internal/api/auth.go` 顶部 `var jwtSecret = []byte("embyforge-secret-change-me")`，配置为空时即用此值。配合 `config.example.yaml` 里 `jwt_secret: "your-random-jwt-secret-change-me"`，默认部署可被伪造 token。
3. **邀请码生成器有两个实现，一个不安全**：`internal/bot/handler_admin.go` 的 `generateInviteCode` 用 `crypto/rand`（正确）；但 `internal/api/handlers.go` 的 `generateCode` 用 `time.Now().UnixNano()` 派生索引（**可预测**），且 REST 层 `/api/invitations` 走的正是后者。同一项目两种实现并存。
4. **Webhook 的 ServerID 匹配逻辑必然失败**：`webhook.go` 里用 Emby payload 的 `Server["Id"]` 去 `repository.DB.Where("id = ?", serverID)` 查本地 `servers` 表，但本地 `id` 是 `gen_random_uuid()` 生成的，与 Emby 的 ServerId 无任何关系。结果 `EventLog.ServerID` 恒为空、`event.ServerID` 恒为空，而 `getChatIDForServer("")` 返回 0，`sendToChat` 里 `if chatID == 0 { return }` 直接静默丢弃 —— **整个 TG 播放/入库播报链路实际不工作**。
5. **大量组件"初始化了但没接线"**：`main.go` 里 `_ = mpClient`、`_ = dlClient`、`_ = service.NewGapService(...)`、`_ = service.NewCalendarService(...)`。即 MoviePilot、下载器、缺集管理、追剧日历四条能力**没有任何路由或 Bot 命令暴露**，全部悬空。这是本项目最大的完成度缺口 —— 四个 adapter 写得挺完整（qBittorrent 有登录/pause/resume/delete，MoviePilot 有订阅 CRUD），却没有一条从求片到下载的调用链。
6. **求片状态机无法自动收敛**：`Request.Status` 定义了 `pending/downloading/done/rejected`，但没有任何代码根据 Emby 入库事件或下载器进度自动推进状态，只能靠管理员 `PUT /api/requests/:id/status` 手改。
7. **字符串拼 JSON 建号**：`emby/client.go` 的 `CreateUser` 用 `fmt.Sprintf(`{"Name":"%s"}`, name)`、`SetUserPassword` 用 `{"NewPw":"%s"}`。用户名含引号即注入，且没有 `json.Marshal` 的转义保护。
8. **两个入口的积分策略不一致**：Bot `/request` 会校验并扣 `RequestCost` 积分 + 写流水；REST `POST /api/requests` **完全不碰积分**。同一个业务两种计费行为。
9. **多服务器下的登录目标不确定**：`Login` 未指定 `server_id` 时"遍历所有服务器取第一个能用的"，用户被静默绑到某台机器，没有选择或告知。
10. **前端是未接线的设计稿**：`web/src/app/movie/page.tsx` 写死了标题 "Aether Continuum" 和 `lh3.googleusercontent.com` 的占位图；`web/src/app/dashboard/page.tsx` 的 TS 类型定义为 `{total_users, active_sessions, total_movies, total_series}`，而 Go 端 `DashboardHandler.Overview` 返回的是 `{servers: [{server_id, server_name, movies, series, episodes, users, playing}]}`；`requests/page.tsx` 的状态映射是 `pending/approved/downloading/available/rejected`，与后端 `pending/downloading/done/rejected` 对不上。前端基本是模板产出，未与后端对齐。
11. `GetSeriesEpisodes` 的 `Limit=1000` 硬编码，长剧集会截断；`GetDailyPlayCounts` 依赖插件返回 `Date`/`Count` 字段名，脆弱。
12. `users` 索引：`Nickname`/`EmbyName` 无索引但 `List` 支持 ILIKE 搜索，大表会全扫。

## 4. emby-register-enhanced

### 定位与技术栈

Flask 单体应用，Jinja2 服务端渲染 + SQLite + APScheduler + Telegram Bot 长轮询，基于 [guowanghushifu/emby-register-service](https://github.com/guowanghushifu/emby-register-service) 二次开发。定位是"**注册发号 + 数据大盘 + 多渠道推送**"，比 embyforge 轻得多，但注册链路和推送覆盖面做得更细。

### 解决的问题

1. 怎么安全地把注册链接发给用户 → HMAC 签名 token + DB 双校验。
2. 怎么让新用户在 Emby 里拿到正确的权限 → 模板用户复制 + 主动覆盖 Policy。
3. 怎么知道服务器现状 → 数据大盘（实时播放流、30 天注册趋势、媒体类型分布）。
4. 怎么批量管到期用户 → 列表 + 批量续期 + 锁定/解锁 + 一键处理到期。
5. 怎么把日报推给自己 → 五渠道广播 + APScheduler。

### 功能清单

路由清单（`app.py` 的 `@app.route`）：

```
GET  /                                  重定向到 /login
GET|POST /login | /logout               管理员登录（IP 限流 10次/300s）
GET  /admin                             后台首页（Token 管理）
POST /admin/generate                    批量生成 Token（最多 50）
POST /admin/delete/<token_id>
GET|POST /emby                          用户自助注册（唯一对外入口）
GET  /dashboard                         + /api/dashboard/stats、/api/dashboard/trend
GET  /users                             + /api/users/list
POST /api/users/renew                   批量续期（单次上限 500）
POST /api/users/lock                    批量锁定/解锁
POST /api/users/auto-lock-expired       一键锁定所有到期
GET  /notify                            + /api/notify/test、/api/notify/report
```

Bot 指令（`tgbot.py` 的 `dispatch`）：`/start /help /status /online /users /expiring /renew <用户名> <天数> /lock <用户名> /unlock <用户名> /lockexpired /report`，只响应 `TG_ADMIN_CHAT_ID`。

注册链路（`emby_register`）值得逐步拆开：

```python
# 1. HMAC 签名校验：token 格式为 "<payload>.<hmac_sha256(payload)>"
token_payload = _verify_signed_token(full_token_str)   # hmac.compare_digest 定时安全比较
# 2. DB 复核：未使用 + 未过期
token_data = db.execute('SELECT * FROM tokens WHERE token = ? AND is_used = 0', (token_payload,))
# 3. 输入白名单：用户名 ^[a-zA-Z0-9]{4,32}$、密码 6-32 位
# 4. 密码强度：zxcvbn score >= 2，ImportError 时退回 15 条弱口令黑名单
# 5. 建号
user_id, error_msg = create_emby_user(username, password)
# 6. 消费 token + 落 registered_users
db.execute('UPDATE tokens SET is_used = 1, registered_username = ? WHERE id = ?', ...)
db.execute('INSERT OR IGNORE INTO registered_users (emby_user_id, username, token_used) VALUES (?,?,?)', ...)
```

`create_emby_user` 里藏着 Emby 建号的实战坑修复（README 的 v1.0.1 更新日志正是这些）：

```python
user_data = _emby_request('POST', '/Users/New', json={
    "Name": username,
    "CopyFromUserId": COPY_FROM_USER_ID,
    "UserCopyOptions": ["UserConfiguration", "UserPolicy", "UserData"]
})
# 主动从模板用户同步 Policy 和 Configuration，防止 Emby 静默忽略 CopyFromUserId
template_user = _emby_request('GET', f'/Users/{COPY_FROM_USER_ID}')
if template_user:
    policy = template_user.get('Policy', {})
    policy['IsDisabled'] = False        # 新用户强制启用
    _emby_request('POST', f'/Users/{user_id}/Policy', json=policy)
    configuration = template_user.get('Configuration', {})
    _emby_request('POST', f'/Users/{user_id}/Configuration', json=configuration)
```

另有启动期 UUID 归一：`COPY_FROM_USER_ID = str(uuid.UUID(_raw_copy_id))`，把无连字符的 UUID 转成标准格式，否则 Emby API 会失败。

### 数据模型要点

SQLite 两表（`init_db()`），并且有 `ALTER TABLE ... ADD COLUMN` 的兼容升级块（用 try/except OperationalError 吞掉"列已存在"）：

```sql
CREATE TABLE tokens (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  token TEXT NOT NULL UNIQUE,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  expires_at TIMESTAMP,
  is_used BOOLEAN DEFAULT 0,
  registered_username TEXT,
  note TEXT
);
CREATE TABLE registered_users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  emby_user_id TEXT NOT NULL UNIQUE,
  username TEXT NOT NULL,
  registered_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  expires_at TIMESTAMP,
  is_locked BOOLEAN DEFAULT 0,
  last_renewed_at TIMESTAMP,
  token_used TEXT
);
```

注意：**`registered_users` 没有「到期后该做什么」的状态字段** —— 只有 `is_locked` 布尔。过期判定靠每次查询时用 `expires_at < now` 现算（`api_users_list`、`api_auto_lock_expired`、`reporter._expiring_soon` 各算一遍），口径分散在三处。

推送抽象（`notify.py`）是"一个渠道一个函数，返回 bool"：

```python
def send_telegram(text, parse_mode="HTML") -> bool    # TG_BOT_TOKEN + TG_ADMIN_CHAT_ID
def send_wecom(text) -> bool                          # WECOM_WEBHOOK
def send_dingtalk(text, title="Emby 通知") -> bool     # DINGTALK_WEBHOOK + DINGTALK_SECRET（加签）
def send_serverchan(text, title) -> bool              # SERVERCHAN_KEY
def send_feishu(text) -> bool                         # FEISHU_WEBHOOK
def broadcast(text, title) -> dict                    # 汇总 {渠道: bool}
```

报表（`reporter.build_report(period)`）输出的是**HTML 文本**（`<b>` 标签），因为五渠道里 TG/企微/钉钉/飞书都吃 HTML 或 Markdown，纯文本最安全。内容包含：在线播放路数 + Top5 在播、用户总数/正常/待处理到期/已锁定、本周期新增注册、Token 有效/总数、3 天内到期用户名清单（`_expiring_soon(days=3)`）。

调度（`scheduler.py`）用 APScheduler `BackgroundScheduler(timezone="Asia/Shanghai")` + `CronTrigger`，由 `REPORT_SCHEDULE`（`daily,weekly,monthly` 组合）和 `REPORT_HOUR` 驱动：日报 `hour=REPORT_HOUR`、周报 `day_of_week="mon"`、月报 `day=1`。

安全栈（`app.py` 头部）是本组最完整的一份：`ProxyFix(x_for=1, x_proto=1, x_host=1, x_prefix=1)` 取真实 IP、`CSRFProtect(app)` 全局保护（API 走 `X-CSRFToken` 头，从非 HttpOnly 的 `csrf_token` cookie 读）、`SESSION_TYPE='filesystem'` 服务端 session（登出真失效）+ `SESSION_USE_SIGNER`、`SESSION_COOKIE_HTTPONLY/SameSite=Lax`、`@app.after_request` 加四个安全响应头、内存 IP 限流（`defaultdict(list)` + `threading.Lock`）。

并且它是六个项目里**唯一对密钥做强制校验**的：

```python
SECRET_KEY_FROM_ENV = os.getenv('FLASK_SECRET_KEY')
if not SECRET_KEY_FROM_ENV:
    raise ValueError("错误: 必须设置 FLASK_SECRET_KEY 环境变量!")
if len(SECRET_KEY_FROM_ENV) < 32:
    raise ValueError("错误: FLASK_SECRET_KEY 长度不能少于32位!")
```

### 值得借鉴的设计

- **HMAC 签名 token + DB 双校验的双层结构**：签名层保证"不可篡改"（无状态、无需查库即可快速拒绝伪造），DB 层保证"不可重放、可查有效期、可追溯归属"。比纯随机 UUID 存库强（DB 泄露也无法伪造有效 token），也比纯无状态 JWT 强（可强制作废）。
- **`CopyFromUserId` 失效的补偿写法**：这是 Emby 建号的一手实战坑 —— 接口接受参数但不生效，必须主动 GET 模板用户再 POST `Policy` / `Configuration` 覆盖。任何要做"模板发号"的项目都会踩。
- **渠道抽象 + `broadcast` 汇总**：加一个新渠道只需写一个 `send_x(text) -> bool` 函数并挂进 `broadcast`，渠道启用与否由 env 是否存在决定（`notify_page` 里 `bool(os.getenv(...))` 就是状态表）。
- **钉钉加签实现**：`timestamp + secret` → HMAC-SHA256 → base64 → urlencode，是接入企业 IM 的通用套路。
- **输入层三重防护**：用户名正则白名单、密码长度上下界、zxcvbn 强度 + 黑名单兜底（且 ImportError 时降级而非放行）。
- **token 长度截断防 ReDoS**：`full_token_str = full_token_str[:300]  # cap length to prevent ReDoS`，并在注解里写明动机 —— 很少见有人对输入长度做这种考虑。
- **报表是"纯文本可推"格式**：不做图表、不做附件，只拼一段结构化文本，因而能同时被五渠道消费。低成本高覆盖。

### 明显缺陷

1. **SQLite 无并发控制**：`get_db()` 裸 `sqlite3.connect`，没有 `PRAGMA journal_mode=WAL`、没有 `busy_timeout`、没有连接池；`gunicorn` + `gevent`（requirements 里有 gevent 25.5.1）多 worker 下写操作会 `database is locked`。
2. **连接泄漏**：全项目靠手工 `db.close()`，且大量提前 return 路径（`emby_register` 里就有 8 处 `db.close()` 散落在 error 分支），没用 `try/finally` 或 contextmanager。异常路径必然泄漏。
3. **Token 一次性，无次数概念**：`tokens` 表没有 `max_uses`/`used_count`，`is_used=1` 后不可复用；`/admin/generate` 批量最多 50 个也只能逐个分发。对比 embyforge 的 `Invitation.MaxUses` 是明显能力缺失。
4. **到期锁定不自**动：`scheduler.py` 只注册了报表任务，**没有任何任务做"到期用户自动禁用"**。`api_auto_lock_expired` 和 Bot `/lockexpired` 都要人点。这意味着如果不主动操作，过期用户能一直看 —— 与 embyforge 的「1 小时定时扫过期」形成鲜明对比。
5. **明文密码回显**：`render_template('success.html', username=username, password=password, ...)` 把用户刚设的密码原文渲回页面；README 里"建议尽快修改默认密码"依赖用户自觉。
6. **`ProxyFix(x_for=1)` 硬编码**，注释里也承认"如果你有 Cloudflare → Nginx → app 应改成 x_for=2"。取不到真实 IP 时，登录限流（`_check_rate_limit` 按 IP）可被绕过。
7. **`EMBY_API_KEY` 全局单例**，`_emby_request` 只认 `EMBY_SERVER_URL`，不支持多服务器；`reporter.py` 和 `tgbot.py` 又各自复制了一份 `_emby_request`（三处重复实现，改一处要改三处）。
8. **`tokens` 表缺 `created_by`**：无法知道哪个邀请码是谁生成的，无归属与追责。
9. **Bot 用长轮询**（`_poll_loop` 调 getUpdates），相比 webhook 有延迟且占用一个线程；`dispatch` 是一长串 `if text.startswith('/xxx')` 的字符串前缀匹配，无参数校验框架。
10. 后台无用户搜索/分页（`api_users_list` 全量返回，虽然引入 `flask-paginate` 但只用在前端模板）。

```python
                runtime_ticks, is_paused, transcoding_info(Text), bandwidth, last_activity, synced_at}
MediaLibrary{emby_id unique, name, collection_type, item_count, path, synced_at}
MediaItem{emby_id unique, name, original_title, item_type(index), overview, production_year,
          community_rating, official_rating, runtime_ticks, genres,
          library_emby_id, image_primary, image_backdrop, premiere_date,
          date_created(index), date_added(index)}
InviteCode{code unique, max_uses, used_count, is_active, note, created_by(FK users.id), expires_at}
SystemSetting{key unique, value(Text), description}
WikiPage{slug unique, title, content, category, sort_order, is_published}
```

**注意 `User` 没有 `expire_at`** —— 这是与 embyforge 的关键差异：gaodong 的邀请码能设有效期（`InviteCode.expires_at`），但注册出来的账号**没有到期字段**，只能靠管理员手动 `is_active` 开关。

设置系统（`backend/app/services/settings_service.py`）用一个 `DEFAULT_SETTINGS: dict[str, tuple[str, str]]` 同时承载"默认值 + 中文描述"，`ensure_defaults` 幂等补插，并明确区分**公开**与**私有**字段：

```python
DEFAULT_SETTINGS = {
  "site_name", "site_description", "emby_url", "emby_api_key", "emby_public_url",
  "allow_register", "require_invite", "announcement", "contact_info", "wiki_enabled",
}
# get_settings_out()  → 含 emby_api_key + emby_api_key_set: bool（管理员）
# get_public_settings() → 只暴露 site_name/announcement/emby_public_url/allow_register 等
```

`emby_url` / `emby_api_key` 因此可运行时热改（DB 优先，env 兜底），不必重建容器 —— 这是 gaodong 相对 emby-tools 和 register-enhanced 的显著优势。

### 值得借鉴的设计

- **海报同源代理 `GET /api/media/image/{item_id}/{image_type}`**（`backend/app/api/media.py`）：服务端带 `X-Emby-Token`（构造 URL 时也会附 `api_key` 参数）去 Emby 拉图并 `Response(content=..., media_type=ctype, headers={"Cache-Control": "public, max-age=86400"})` 回吐。解决三件事：HTTPS 门户加载 HTTP Emby 的**混合内容阻断**、浏览器端**不暴露 API Key**、图片类型做**白名单**（`{Primary, Backdrop, Thumb, Logo, Banner, Art}`）+ `maxWidth∈[40,2000] quality∈[20,100]` 参数约束。所有 `MediaItemOut` 的 `image_primary` 都指向这个代理路径（`_proxy_image_url`）。
- **服务器状态的双源融合降级**（`fetch_server_status`）：先算本地缓存计数（`MediaItem`/`PlaybackSession`/`User` 的 `select(func.count())`）填进 `ServerStatus`；再 try 调 `/System/Info/Public`（**无需 API Key**）判定 `online`；有 key 时继续追加 `/System/Info`、`/Items/Counts`、`/Sessions` 覆盖；任何一步异常都 `except: pass` 保留已有值，最后 `status.message = f"无法连接 Emby: {e}"`。**Emby 挂了门户照样能看缓存数据**，这是很实用的可用性设计。
- **计数只取总数，不拉实体**：`EmbyClient.count_items` 用 `{"Recursive": "true", "IncludeItemTypes": types, "Limit": 0, "EnableTotalRecordCount": "true"}`，只读 `TotalRecordCount`。对比 emby-tools 的 `/emby/storage` 把全库条目拉回内存累加 `Size`，这是数量级的差别。
- **`CollectionType → IncludeItemTypes` 映射表**：

```python
mapping = {"movies":"Movie","tvshows":"Series","music":"MusicAlbum","musicvideos":"MusicVideo",
           "homevideos":"Video","boxsets":"BoxSet","books":"Book","photos":"PhotoAlbum,Photo",
           "livetv":"LiveTvChannel","playlists":"Playlist"}
return mapping.get(ct, "Movie,Series")
```

配合 `get_media_folders_with_counts()`（并发对每个库做递归计数），是"每个媒体库到底有多少片"的正确算法。

- **同步的对账式失效**（`sync_sessions`）：先收集本轮见到的 `seen_ids`，循环里 upsert；最后 `update(PlaybackSession).where(session_id.not_in(seen_ids)).values(is_active=False)`。用"差集"批量失效，天然不需要 TTL 或清理任务。
- **注册流程的事务顺序**：`backend/app/api/auth.py` 的 `register` 顺序是「校验 allow_register → 本地唯一性 → 邀请码各项校验（大小写两种查法 + `is_active` + `used_count >= max_uses` + `expires_at` 时区归一）→ **先建 Emby 账号**（失败按 `ValueError`/`ConnectionError`/`httpx.HTTPStatusError` 三类分别给 400/503/502）→ 成功后才 `invite.used_count += 1` 并在用尽时 `is_active=False` → 最后落本地 User」。把"外部副作用"放前面、把"消耗凭证"放后面，避免"码废了但账号没建出来"。
- **建号策略：不用模板，显式设权限**（`create_emby_account`）：先 `find_user_by_name` 查重，再 `create_user` → `set_user_password` → `policy.update({IsAdministrator: False, IsDisabled: False, EnableRemoteAccess/EnableMediaPlayback/EnableAllFolders/EnableAllChannels/EnableAllDevices/EnableContentDownloading: True})` → 异常时 `delete_user` 回滚。与 register-enhanced 的"复制模板用户"是两条路线，gaodong 这条更自主但要有默认权限清单。
- **非管理员防提权**（`update_user`）：`if not current.is_admin: data.pop("is_admin"/"is_active"/"emby_user_id"/"emby_username")`，在数据落库前剪掉敏感字段，比逐个 if 拦截更不易漏。
- **Wiki 内置 seed**（`backend/app/services/seed.py`）：直接写入"快速开始""客户端推荐"等页面内容（含客户端推荐表：Hills / 网易爆米花 / Yamby / Infuse / SenPlayer），开箱可用的站内帮助。这是"减少客服"的低成本手段。
- **前端路由守卫三档 meta**（`requiresAuth` / `requiresAdmin` / `guest`）+ admin 路由懒加载 + NProgress，结构清晰。

### 明显缺陷

1. **图片代理接口无鉴权**（`backend/app/api/media.py` 的 `proxy_media_image`，签名里只有 `db: AsyncSession = Depends(get_db)`，**没有 `Depends(get_optional_user)`**）。任何知道 item_id 的人都能无限拉图，把 Emby 的转码/带宽当免费 CDN 刷；且无速率限制。对比同文件的 `/media/latest` 至少用了 `get_optional_user`。
2. **全局关闭 TLS 校验**：`EmbyClient._get/_post/_delete` 里所有 `httpx.AsyncClient(..., verify=False)`，`fetch_item_image` 同样。若 Emby 走 HTTPS，等于放弃中间人防护。
3. **默认凭据/密钥全在默认值里**：`backend/app/config.py` 的 `JWT_SECRET_KEY = "change-me-in-production-use-long-random-string"`、`ADMIN_PASSWORD = "admin123"`、`ADMIN_EMAIL = "admin@localhost"`；`.env.example` 沿用；README 还明示默认邀请码 `WELCOME2024`。对比 register-enhanced 的启动期强制校验，这里没有任何保护。
4. **无 Token 刷新与吊销**：JWT 有效期 7 天（`JWT_ACCESS_TOKEN_EXPIRE_MINUTES = 60*24*7`），logout 靠前端清 `localStorage`，服务端无黑名单/版本号，改密后旧 token 依然有效。
5. **无播放历史，只有活跃快照**：`playback_sessions` 每次同步覆盖同一 `session_id` 行，`is_active` 失效后不再更新，也没有 `playback_history` 表。因此**做不出"观影时长排行""观看趋势"** —— 面板只能显示"此刻在播什么"。这与 embyforge 走 Playback Reporting 插件、emby-tools 走 `/Items?Fields=RunTimeTicks,UserData` 形成能力梯度。
6. **CORS 配置组合可疑**：`CORS_ORIGINS` 默认 `"*"`，而 `allow_credentials=True`；浏览器规范下 `Access-Control-Allow-Origin: *` 与 credentials 不能共存，属于"要么无效要么过宽"的配置。
7. **同步覆盖面窄且统计有偏差**：`full_sync` 只 `sync_latest_items(limit=200)`，媒体库 `item_count` 在同步后被"按类型近似重算"（`sync_latest_items` 末尾的注释 `# Approximate from item types / names - use total items if no better mapping` 自己承认了）。`library_emby_id` 对 Series 取自身 `Id`、对其他取 `ParentId`，语义不统一。
8. **天气模块与 Emby 无关**（300+ 行的 Open-Meteo 封装 + WMO 码中文映射 + 24 城 lat/lon 兜底表），明显是作者本机定制件；`AGENTS.md` 里"用户说『修面板 / 加天气 / 热播 / 导航』→ 改这里"也印证了这一点。对通用产品是噪音。
9. **`get_public_info()` 与 `_get()` 各建一个 `httpx.AsyncClient`**，没有连接池复用；每个图请求也新建 client（`fetch_item_image`）。
10. **无邀请码使用记录关联**：`InviteCode` 有 `used_count` 但没有"哪个用户用了哪个码"的关联表（`User` 表也没有 `invite_code_id`），无法追溯。
11. **重复的计数实现**：`sync_latest_items` 里对每个 `MediaItem` 先 `select` 再判空（N+1 查询），大库同步会慢。

## 6. usersvr

### 定位与技术栈

**只有 README，无源码可考**。git 历史仅两个 commit（`c520dc8`、`c520dc8` 均只含 `README.md`），无分支、无其它文件。因此这一节提炼的是**功能设想与其相对其它五个项目的增量价值**，不含代码依据。

按 README，技术栈只能从部署方式反推：单容器 `docker run -p 505:505`，挂载 `/data` `/configs` `/logs` 三个卷，`TZ=Asia/Shanghai`。三卷分离（数据/配置/日志）是比 emby-register-enhanced 的单 `/app/data` 更规范的布局。镜像 `xieburouzzz/usersvr:latest`。文档里写的是 `505` 端口，大概率是 `5050` 的笔误。

### 解决的问题

README 的一句话定位最准确："支持用户管理 卡密系统 点播请求 工单系统和实时监控"。它要解决的是**运营侧**的问题：怎么卖号（卡密/余额）、怎么让用户自己推广（推广计划）、怎么处理用户诉求（工单）、怎么看服务器在发生什么（实时监控）。

### 功能清单（按 README 提炼）

用户管理：批量用户操作、设备限制管理、用户状态管理、用户账号创建。

卡密系统：卡密筛选搜索、卡密状态追踪、**多类型卡密生成**。

推广计划：**余额系统**、邀请码管理、推广卡密兑换。

点播工单：工单状态管理、影片点播请求、问题工单提交、**管理员回复系统**。

实时监控：播放设备信息、在线用户统计、正在播放监控。

系统配置：**限制规则设置**、TMDB API 配置、**自动化任务配置**。

日志管理：操作日志追踪、点播记录查看、工单记录管理。

### 数据模型要点（推断）

无源码，但从功能清单可以反推至少需要这几组实体：

`users`（含余额、设备数上限、到期时间、来源推广人）、`cards`（卡密：code/类型/面值或天数/状态/使用记录）、`promotion/affiliate`（推广人 → 被邀请人 → 分润流水）、`orders_or_tickets`（工单：类型=点播/问题、状态、主题、**回复消息列表**）、`sessions/monitor`（播放设备实时快照）、`rules`（限制规则：最大设备数/并发数/流量）、`logs`（操作日志、点播记录、工单记录）。

关键结构差异在于**"卡密" ≠ "邀请码"**：embyforge / gaodong / register-enhanced 的邀请码是"一次性或限次的凭证"，用完即废；usersvr 的卡密是"**可兑换的资产**"，带有面值/天数并可被兑换成余额，余额再消费（开通时长/增加设备数）。这需要"卡密表 + 余额流水表"两级结构，而不是"邀请码表 + used_count"。

另一处差异是**工单是双向的**：emby-request-ui 只有三态单向流转（用户提交 → 管理员改状态），usersvr 的"工单状态管理 + 管理员回复系统"意味着需要 `ticket_messages` 子表（谁、何时、说了什么），这是客服系统而非公告板。

### 值得借鉴的设计

- **卡密 + 余额双级模型**：码是资产、余额是账户、消费是流水。相比"限次邀请码"，这套能支撑"卖号"和"赠送/补偿/退款"等运营动作。
- **推广计划（分销）**：用户生成自己的邀请码并获分润，与 embyforge 的 `Invitation.CreatorID` 字段是同一个方向的延伸 —— embyforge 只记录"谁生成的"，usersvr 设想的是"生成者从中获益"。
- **工单回复链路**：把"求片"和"问题反馈"统一进工单模型（类型区分），并要求带回话。这是 emby-request-ui 最大的缺口（无沟通、无备注回传）。
- **限制规则作为一等配置**：设备数/并发数上限做成可配置的规则表而非硬编码，与 Emby 的 `Policy` 联动（Emby 侧有 `MaxActiveSessions`、`EnableAllDevices` 等策略位，可以在建号/续期时同步下发）。
- **三卷分离部署**（/data /configs /logs）：数据、配置、日志分开挂载，便于分别备份与审计。
- **日志管理独立成模块**：操作日志 + 点播记录 + 工单记录三类留存。六个项目里只有 embyforge 有 `EventLog`、emby-register-enhanced 只有 stdout，日志留存普遍是空白。

### 明显缺陷

- **零代码可验证性**：仓库只有 README，无法确认任何一条设想是否实现、如何实现。README 里的 `-p 505:505` 与常规端口不符，疑似 `5050`，说明文档本身未经校对。
- 无 API 文档、无数据模型、无截图、无配置文件示例 —— 相比其它五个项目的 README（emby-register-enhanced 甚至有完整 docker-compose 示例和 FAQ），usersvr 的文档只到"功能列表"层级。
- 未提及任何鉴权方案（多管理员？角色？）、未提及备份策略、未提及 Emby 版本兼容范围（register-enhanced 明确写了"Emby 4.7.0+"）。
- 功能面铺得最宽（用户/卡密/推广/工单/监控/规则/日志 七块），按单容器项目的常规体量判断，落地深度大概率不及 embyforge。

**综合判断**：usersvr 的价值不在"可复用代码"，而在于它指出了五个成熟项目共同忽略的一层 —— **运营与客服**（资产化凭证、分销、工单回话、规则配置、操作审计）。这五点在后文「共同短板」里会被反复引用。

## 7. 横向归纳

### 7.1 求片（Request）需求的完整闭环应该长什么样

`emby-request-ui` 提供了**入口与状态展示**（表单校验、去重、公开进度），`embyforge` 提供了**运营与执行骨架**（积分闸门、工单表、四层适配器、webhook 事件总线）。两者互补，但都只覆盖了闭环的一段。把两边的正确部分拼起来，闭环应该是七段：

**① 提交与去重**（emby-request-ui 已做好）
表单项：类型（电影/电视剧/动漫/纪录片）+ 片名 + 年份 + TMDB 链接/ID + 季号 + 联系方式/备注。去重走 `normalizeTitle`（trim + lower + 去所有空白）+ 唯一索引 `(type, normalized_title)` + `findFirst` 预查，命中返回 409 并**直接给进度页链接**而不是干巴巴报错。emby-request-ui 的 `lib/services/request-service.ts` 已完整实现，可直接照搬。

**② TMDB 归一化**（两边都缺，各自只做了一半）
emby-request-ui 只校验 URL host 属于 tmdb.org，**不解析出 `tmdb_id`**；embyforge 的 `Request` 表有 `TMDBID *int` 字段，但 `RequestHandler.Create` **不做任何校验或补全**，用户传什么存什么。正确做法：提交时调 `TMDB.SearchMulti(query)`（embyforge 的 `adapter/tmdb/client.go` 已有）→ 拿到 `id / media_type / poster_path / release_date|first_air_date / vote_average` → 落库。这是后续所有自动化的前提（没有 tmdb_id 就无法调 MoviePilot 订阅，也无法做缺集比对）。

**③ 受理与成本**（embyforge 的 Bot 路径已做好，REST 路径缺失）
embyforge 的 `handleRequest`（`internal/bot/handler_coin.go`）做了正确的三件事：校验 `user.Coins >= cfg.Coin.RequestCost` → 建单 → 扣分并写 `CoinTransaction` 流水（`Type: "request"`）。但 REST 的 `RequestHandler.Create` 完全不碰积分。**同一业务必须收敛到同一个 service**，而不是 Bot 和 API 各写一份。

**④ 执行：接下载器**（embyforge 有能力但未接线，这是最大缺口）
`main.go` 里 `_ = mpClient` 和 `_ = dlClient` 把两个客户端直接丢弃了。已有能力：`moviepilot.AddSubscription(title, tmdbID, mediaType, season)` / `AddDownload(req)`、`downloader.Client`（qBittorrent 的 `GetTorrents/GetSpeed/Pause/Resume/Delete`）。需要补的是：管理员把状态改为 `approved` 时调用 `AddSubscription`，并把 `Request.Status` 推进到 `downloading`，同时把 `MP/下载器的任务 hash` 存回 Request 或关联表。

**⑤ 回流：入库自动闭环**（全组最缺的一环，embyforge 有全部零件但没接对）
embyforge 已有：Emby webhook（`/webhook/:token`）→ 事件映射（`library.new`/`item.added` → `EventItemAdded`）→ 持久化 `EventLog`（含原始 JSON）→ 事件总线广播 → Bot 播报。缺的是**匹配与回填**：订阅 `EventItemAdded` → 从 payload 取 `Item.Name`/`Item.ProductionYear`/`Item.Type` → 用与提交时相同的 `normalizeTitle` 规则去匹配 `status IN ('pending','downloading')` 的 Request（电影比片名+年份，剧集比片名+季号）→ 命中则置 `done` → 给求片人私聊推"你要的 X 已入库"。

另外 embyforge 的 webhook 有个**必须先修的 bug**：`webhook.go` 用 Emby 的 `Server["Id"]` 去匹配本地 `servers.id`（`gen_random_uuid()`），永远匹配不上，导致 `EventLog.ServerID` 恒空、`getChatIDForServer("")` 返回 0、`sendToChat` 静默 return —— 整条播报链实际不工作。修法：给 `Server` 表加 `emby_server_id` 字段，或改用 request 的 `Server` 头/路径参数标识来源。

**⑥ 通知：双通道而不是单通道**
emby-request-ui 是"提交即推管理员群"（`sendNewRequestTelegramNotificationWithConfig`）；embyforge 是"群广播报表 + 播报"。理想是**两条线**：管理员群收"新单 + 待处理积压"，求片人收"受理/拒绝/已入库"的私聊。这要求 `User` 表有可寻址的 IM 身份（embyforge 用 `TGID` 满足），而 emby-request-ui 连用户概念都没有（只有管理员），所以它的通知只能是单向的。

**⑦ 查询进度**
emby-request-ui 的做法是公开全量列表 + `?requestId=` 高亮（`app/progress/progress-content.tsx`），代价是 `GET /api/requests` 无分页、无字段裁剪、`contact` 可能外泄；它自己也知道这点 —— schema 里留了 `progress_token String? @unique`、`/api/requests/progress` 返回 410 "查询码模式已下线"，说明"凭码查私有进度"的原设计被砍了。更稳的做法是二选一：要么**只公开脱敏后的进度页**（去掉 `contact`/`note`，`select` 白名单字段），要么**恢复 token 模式**给每人一条私有链接（`progress_token` 字段现成）。embyforge 的"工单号 + 私聊查询"是第三条路。

**状态机建议**（合并两家的枚举）：`pending（待处理）→ approved（已受理）→ downloading（下载中）→ done（已入库）`，旁路 `rejected（已拒绝）` 与 `duplicate（重复单，被 409 拦截时可落此态以便统计需求热度）`。emby-request-ui 的三态缺 `downloading`，无法对接执行层。

### 7.2 报表/统计需求的数据来源

这是六个项目技术分歧最大的一处。可归纳为四条路线，各有明确的适用边界。

**A. Emby 原生 REST 的聚合端点 —— "此刻快照"**

```
GET /System/Info                → ServerName / Version / OperatingSystem / HasPendingRestart
GET /System/Info/Public         → ServerName / Version（无需 API Key）
GET /Items/Counts               → MovieCount / SeriesCount / EpisodeCount / SongCount
GET /Sessions                   → 实时会话（过滤 NowPlayingItem != nil 得"在播"）
GET /Users                      → 用户数（含 Policy，可判断 IsAdministrator/IsDisabled）
GET /Library/MediaFolders       → 媒体库列表（Id / Name / CollectionType）
```

四个项目全都用了这条（emby-tools 的 `mediaCount`/`mediaLibraryList`、embyforge 的 `GetLibraryCounts`、register-enhanced 的 `/Sessions`、gaodong 的 `fetch_server_status`）。**优点**：零依赖、秒级。**缺点**：只有"此刻"，没有历史；`/Items/Counts` 不带 `userId` 时是服务器级。

gaodong 在此路线上做了一个细节优化值得抄：判定在线用 `/System/Info/Public`（**无需 API Key**），这样"Emby 是否需要 key"和"Emby 是否在线"两个问题解耦；拿计数用 `Limit=0&EnableTotalRecordCount=true` 只读 `TotalRecordCount`，不拉实体。

**B. Emby 原生 REST 的逐项聚合 —— "精确但昂贵"**

```
GET /Users/{userId}/Items?IncludeItemTypes=X&Recursive=true&Fields=Size
GET /Users/{userId}/Items?IncludeItemTypes=X&Recursive=true&Fields=RunTimeTicks,UserData,DateLastPlayed
```

emby-tools 的 `/emby/storage` 与 `/emby/playTime` 走这条：把全部条目拉回 Node 进程，`Items.reduce` 累加 `Size`；播放时长按"`PlaybackPositionTicks > 0` 用进度位，`Played === true` 用 `RunTimeTicks`，否则不计"的口径求和。

emby-tools 的时长口径值得保留（同时覆盖"看一半"和"看完"），但**全量拉取的方式不可取**：几十万条目会超时或 OOM，且每次请求都重算。这条路线只适用于**单条或小范围**的精确查询，以及**首次全量建库**（配合分页 + 增量）。

**C. Playback Reporting 插件 —— 唯一能出"真实历史时长与趋势"的路径**

```
GET /user_usage_stats/PlayActivity?days=N&data_type=duration   # 每日时长
GET /user_usage_stats/PlayActivity?days=N&data_type=count      # 每日播放次数
GET /user_usage_stats/UserPlaylist?days=N&user_id={embyUserId} # 单用户明细
```

全组**只有 embyforge** 走了这条（`adapter/emby/client.go` 的 `QueryPlaybackStats` / `GetUserPlaybackDuration` / `GetDailyPlayCounts`），因此也只有它能做日/周/月报与"观影排行"。代价有三：必须装插件；返回结构会变（`QueryPlaybackStats` 里写了兼容 `wrapped["colums"]` 的分支 —— 注意是 `colums` 的拼写，说明作者踩过返回键名不规范的坑）；`days` 上限与精度受插件实现影响。

结论很明确：**要做"用户观看时长排行""播放趋势曲线""自动日报/周报"，插件是绕不开的**。没有它，只能退化成"此刻在播几个人"（emby-tools、gaodong、register-enhanced 都停在这一层）。

**D. 自建落库 —— "业务数据必须自己存"**

三类数据只能自建：

一是**业务实体**（邀请码、到期时间、积分流水、求片工单），这是系统自己的状态，Emby 不知道。embyforge 的 `Invitation`/`CoinTransaction`/`Request`、gaodong 的 `InviteCode`、register-enhanced 的 `tokens`/`registered_users` 都属于此类。值得注意：register-enhanced 的 `registered_users` 是**唯一被真正用于报表的自建表**（`reporter._reg_count_since` 算注册趋势、`_expiring_soon` 查 3 天内到期）—— 它证明了"注册/到期/趋势"这类数据必须自己存，因为 Emby 不记录"这个账号是什么时候通过什么渠道开通的"。

二是**实时会话快照**。gaodong 的 `playback_sessions` 是正确形态：以 `session_id` 为唯一键做 upsert，并在每轮同步后用 `session_id.not_in(seen_ids)` 把没再出现的会话批量置 `is_active=False`（对账式失效，不需要 TTL 清理任务）。Emby 侧的 `/Sessions` 只给当前状态，历史靠 webhook 补。

三是**事件原文**。embyforge 的 `EventLog(EventType index, Payload text)` 存 webhook 原始 JSON，排障时可重放、可事后补解析器。

**一个必须点名的反例**：embyforge 的 `playback_stats` 表**结构完备但全项目零写入路径**。grep 全仓只有 AutoMigrate 声明、model 定义，以及 `stats.go`（Bot `/stats`）、`handler_coin.go`、`report_service.go` 三处读取。结果是 Bot `/stats` 命令的"总播放次数/总观看时长"**永远返回 0**，而报表走的是插件实时查询 —— 同一系统内两套统计口径、其中一个恒为 0。这是"建了表忘了写"的典型，也说明**报表模块必须与数据落库模块同批次实现与验收**。

**推荐的分层策略**：

用 A 做骨架（在线状态、片库计数、用户数 —— 秒级、零依赖、失败可降级）；用 C 做时长与趋势（可选依赖，未装插件时该模块整体降级隐藏而不是显示 0）；用 D 做全部业务数据（邀请/到期/积分/求片/事件原文/会话快照）；B 保留给单条详情与首次全量建库（必须分页 + 增量，禁止每次请求全量）。

补充一点：**磁盘占用率**只有 emby-tools 做了（`systeminformation.diskLayout()` 拿整机磁盘总容量 vs Emby 媒体 `Size` 之和）。如果门户要展示"还剩多少空间"，这是唯一现成的做法；结合 gaodong 的 `Limit=0` 计数思路，可以用 `/Items/Counts` 拿数量、再用带 `Fields=Size` 的**分页**查询按批累加（而不是一次全拉）。

### 7.3 注册/邀请体系的关键设计点

按"必须做对否则会出事"的顺序排列，每条都标注了六个项目里的正反例。

**① 码的两条时间轴必须分开**
`Invitation.ExpireAt`（码自身何时失效 — 防止链接被长期转发）与 `User.ExpireAt` / `Invitation.Duration`（兑换出的账号能用多少天，NULL 为永久）是两个正交维度。embyforge 两者齐全；register-enhanced 的 `tokens` 只有 `expires_at` 且一次性；gaodong 的 `invite_codes` 有 `expires_at` 但 **`User` 表没有到期字段**，注册出来的账号只能靠管理员手动 `is_active` 开关 —— 这是 gaodong 相对 embyforge 的能力缺口。

**② 次数与并发要原子化**
`max_uses` / `used_count` 是基本盘（embyforge、gaodong 有，register-enhanced 无 —— 它的 token 一次性）。递增必须原子：embyforge 用 `gorm.Expr("used_count + 1")`，gaodong 用 ORM 的 `invite.used_count += 1`（flush 时才写，靠事务隔离），两者都比"读出来 +1 再写回"安全。gaodong 还多做一步：用尽时自动 `is_active = False`。

**③ 消费时机：先建外部账号，成功后才扣码**
这是**顺序问题**，做反了会造成"码废了账号没建出来"的客诉。gaodong 在 `auth.py` 的 `register` 里明确按"先建 Emby 账号 → 成功后才 `invite.used_count += 1`"排列；embyforge 在 `handleBindCode` 里是"建号 → 落本地 → 落库失败则 `client.DeleteUser` 回滚 → 成功后才 `used_count+1`"。两条路都正确（一个靠顺序、一个靠补偿），关键是**不能在建号之前消费凭证**。

**④ 外部建号的三个已知坑**（register-enhanced 的 v1.0.1 更新日志就是这三条实战记录）
`CopyFromUserId` 会被 Emby **静默忽略** —— 必须回读模板用户再主动 POST `Policy` 和 `Configuration` 覆盖。新用户建出来可能带 `IsDisabled=True` —— 必须显式设 `IsDisabled=False`。UUID 格式不统一 —— 无连字符的 UUID 会导致 API 调用失败，需 `str(uuid.UUID(raw))` 归一。
gaodong 选的是另一条路：不用模板用户，建号后直接 `policy.update({IsAdministrator: False, IsDisabled: False, EnableRemoteAccess/EnableMediaPlayback/EnableAllFolders/EnableAllChannels/EnableAllDevices/EnableContentDownloading: True})`。两条路都可行，但**都必须显式处理 Policy**，不能依赖 Emby 默认值。

**⑤ 码的随机性必须用 CSPRNG**
这是本组唯一能在同一项目内看到正反例的地方：embyforge 的 `handler_admin.go` 里 `generateInviteCode` 用 `crypto/rand` + 去混淆字符集 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`（排除了 I/O/0/1），完全正确；但同一个项目的 `handlers.go` 里 `generateCode`（REST `/api/invitations` 走的正是它）用 `time.Now().UnixNano()` 派生索引 —— **可预测、可爆破**。gaodong 的 `_gen_code` 用 `secrets.choice`（正确）。register-enhanced 用 `secrets` + HMAC 签名（正确）。

**⑥ 签名 vs 纯随机：可权衡的两条路**
register-enhanced 用 `HMAC-SHA256(FLASK_SECRET_KEY, payload)` 让 token 自带完整性证明，配合 DB 复核"是否已用/是否过期"，形成双层校验：签名层无状态快速拒伪，DB 层管重放与归属。好处是"数据库泄露也无法伪造有效 token"；代价是换 secret 后所有未用链接全废。纯随机 + 存库（embyforge、gaodong）实现简单，但库泄露 = 链接全泄露。

**⑦ 注册入口的加固清单**（register-enhanced 做得最全，可直接照搬）
用户名白名单正则 `^[a-zA-Z0-9]{4,32}$`；密码长度上下界（6–32）；zxcvbn 强度 `score >= 2` 且有 ImportError 时的弱口令黑名单兜底（降级**不放行**）；单 IP 限流（10 次 / 300 秒，内存 `defaultdict` + `threading.Lock`）；CSRF（Flask-WTF，API 走 `X-CSRFToken` 头）；HttpOnly + SameSite Cookie；服务端 session（登出真失效）；安全响应头四件套；输入长度截断防 ReDoS（`full_token_str[:300]`）。
这里还有一个易踩的坑：`ProxyFix(x_for=1)` 只在"一层代理"时取得到真实 IP；Cloudflare → Nginx → app 的部署要改成 `x_for=2`，否则限流按 CF 的 IP 计，等于没限流（register-enhanced 的注释自己提醒了）。

**⑧ 到期处理必须自动化**
embyforge 用 `SchedulerService` 每小时跑 `CheckExpiredUsers`：查 `status='active' AND expire_at < now` → 调 Emby `DisableUser` → 本地置 `expired`。register-enhanced 的 `scheduler.py` **只注册了报表任务**，锁定过期用户需要人点 API 或发 Bot 命令 —— 也就是说不主动操作的话，过期用户能一直看。这是"注册体系"最容易漏的一环：**发号容易，收号容易忘**。

**⑨ 归属与推广**
embyforge 的 `Invitation.CreatorID` 记录了"谁生成的码"。usersvr（README 层面）把这件事推进一步：**推广计划 = 用户生成自己的码 + 从中获分润 + 卡密/余额两级资产**。如果目标是"运营"，这是必然要补的一层。register-enhanced 的 `tokens` 表连 `created_by` 都没有，无法追责。

**⑩ 凭证的存储形态**
emby-request-ui 的 `AppSetting(key, value Json)` + AES-256-GCM 加密落库，配合"DB 优先 / env 兜底"的双源读取，是本组最好的凭据管理。gaodong 的 `SystemSetting(key, value Text, description)` 结构类似但 `emby_api_key` **明文入库**且 `get_settings_out()` 会把 key 原样返回给管理员前端（虽然 `get_public_settings()` 做了裁剪）。EMBY_API_KEY 是全权限凭证，应当加密存储且只在写入时接受、读取时只返回 `emby_api_key_set: bool`（gaodong 其实已经有这个字段了，只是同时也返回了明文）。

### 7.4 这六个项目的共同短板

**① 求片与入库不闭环 —— 没有一个项目能端到端跑通"请求 → 下载 → 入库 → 通知求片人"。**
embyforge 零件最全（MoviePilot 订阅、qBittorrent 控制、webhook 事件、`done` 状态枚举）但 `main.go` 里 `_ = mpClient` / `_ = dlClient` 直接把客户端丢弃，`GapService`/`CalendarService` 同样只 `_ =` 初始化；emby-request-ui 连 Emby 都不碰。六个项目里**零个**做到自动推进状态。

**② 播放历史普遍缺位 —— 只有"此刻"，没有"过去"。**
唯一能出时长的路径是依赖 Playback Reporting 插件（仅 embyforge 走）。自建 `playback_stats` 表（embyforge）**零写入路径、读数恒为 0**；gaodong 的 `playback_sessions` 只是活跃快照（`is_active` 失效后不再更新），没有历史表；emby-tools 每次请求全量拉取重算；emby-register-enhanced 只统计"在线路数"。结论：**"观影时长排行""播放趋势""自动月报"这些需求，没有插件就得自己从 webhook 攒**——而六个项目都没做这件事。

**③ 多服务器支持几乎是空白。**
只有 embyforge 有 `Server` 表和 `embyClients map[string]*emby.Client`（且在 `Login` 里的多服务器选择逻辑还是"取第一个能用的"）。其余四个全是单服务器全局变量：emby-tools 的 `embyStore` 模块单例、register-enhanced 的 `EMBY_API_KEY` 全局常量、gaodong 的 `system_settings` 里单份 `emby_url`/`emby_api_key`、emby-request-ui 无 Emby。对"运维多台 Emby"的场景，只有 embyforge 可用。

**④ 鉴权粒度粗，且有几处是敞开的。**
emby-tools 后端**完全零鉴权**（`/emby/*` 可读可改、`/rename/*` 可列目录可删文件）；emby-request-ui 的 `GET /api/requests` 公开且无分页无字段裁剪（`contact` 可能外泄）；gaodong 的 `/api/media/image/{item_id}/{image_type}` **无任何依赖注入的鉴权**（同文件其它接口至少用了 `get_optional_user`）；embyforge 有 JWT + role 但 `/api/servers` 不校验角色、`/api/invitations` 的 `CreatorID` 解析依赖 `emby_id` 查 `User`（逻辑可疑）；register-enhanced 只有单管理员密码 + session（反而最扎实，因其入口最少）。

**⑤ 默认凭据与硬编码密钥贯穿全组。**
emby-tools：**硬编码真实的 TMDB Bearer Token（完整 JWT）在源码里**；embyforge：`var jwtSecret = []byte("embyforge-secret-change-me")`；gaodong：`JWT_SECRET_KEY = "change-me-in-production-use-long-random-string"` + `admin/admin123` + README 明示默认邀请码 `WELCOME2024`；emby-request-ui：`amdin`/`admin` 硬编码并懒创建；emby-register-enhanced：**唯一例外**，`FLASK_SECRET_KEY` 缺失直接 `raise ValueError`、长度 < 32 也拒绝启动。

**⑥ 可审计性弱 —— 只有一处像样的流水。**
embyforge 的 `CoinTransaction`（带 `Type` + `Memo` 的流水表而非直接改余额）是唯一可审计的设计。register-enhanced 的"操作日志"只是 stdout 日志；gaodong/emby-tools/emby-request-ui 无操作日志；usersvr 的 README 提到"操作日志追踪"但没有实现可考。**没有任何项目记录"谁在什么时候改了哪个用户的状态/邀请了谁/删了什么"**。

**⑦ 零测试。**
六个项目都没有测试目录、没有 CI 测试步骤（embyforge 的 `.github/workflows/docker-build.yml` 只构建镜像）。考虑到这些系统直接操作 Emby 的用户权限与文件系统（emby-tools 的 `fs.unlinkSync`），这个空白风险很高。

**⑧ 前端成熟度两极分化且技术栈分裂。**
Vue3 两个（emby-tools、gaodong）、React/Next 两个（emby-request-ui、embyforge）、Jinja2 SSR 一个（emby-register-enhanced）。gaodong 的 21 个视图最完整，embyforge 的 Next.js 前端是**未接线的设计稿**（`movie/page.tsx` 写死 "Aether Continuum" 和 Google 占位图；`dashboard/page.tsx` 的类型定义与 Go 响应结构对不上；`requests/page.tsx` 的状态枚举 `pending/approved/downloading/available/rejected` 与后端 `pending/downloading/done/rejected` 不一致），emby-request-ui 的后台只有两个设置页。前端没有事实标准，如果要做统一门户，需要自己定规范而不是照抄。

**⑨ 运营与客服层完全缺失。**
六个项目里没有任何一个做：用户自行续费/充值、卡密/资产化凭证、分销分润、双向工单（用户提问 → 管理员回复）、设备数/并发数的规则化限制、操作审计留痕。usersvr 的 README 把这一整层列了出来 —— 它是这六个项目里唯一指向"运营"的，却是唯一没有代码的。这恰恰说明这一层在现有生态里是空白，也是本项目 G4 最可能形成差异化的位置。

**⑩ 落地质量的共性细节问题。**
建号用字符串拼 JSON（embyforge 的 `fmt.Sprintf(`{"Name":"%s"}`, name)`）；密码明文回显给用户（embyforge 的 TG 消息、register-enhanced 的 `success.html`）且不强制首登改密；全局 `verify=False` 关 TLS 校验（gaodong）；`CORS_ORIGINS="*"` 与 `allow_credentials=True` 冲突配置（gaodong）；SQLite 无 WAL/无 busy_timeout 且连接靠手工 close（register-enhanced）；`/emby/playTime` 的 `&Limit` 空参（emby-tools）；`GetSeriesEpisodes` 的 `Limit=1000` 硬编码截断长剧集（embyforge）。
